# 100. Every release of both games beside NTSC-U

**Status:** open · decided, nothing built yet; the mechanism first, on the disc machine, then the releases one at a time · **Effort:** large (one census and build that any release runs through, a viewer layer, the Japanese character tables) · **Where:** `tools/build_map.py` and `tools/oddmap/` for the release build, a hand-curated release table under `tools/data/`, an overlay and its art per game and release under `public/`, the viewer's datasets, permalinks, edit store, marks and clock, and `public/sw.js`

**Filed:** 2026-10-20, from a census of every retail release of both games against the North American ones.

## What and why

The map draws the North American releases: Oddysee's third US pressing (Redump's Rev 2, the Greatest Hits) and Exoddus. Redump lists fourteen more retail releases of the two games: Oddysee's two earlier US pressings, five European editions of each game (one in English, one each in French, German, Italian and Spanish), and a Japanese release of each. A visitor who played one of them played a game that differs from the map in places nobody had listed. Some differences are gameplay (Oddysee's English European edition moves hundreds of collision lines, Exoddus's Japanese release adds floors and objects, Oddysee's first US pressing lacks fixes the base has), some are artwork (signs, story screens and captions painted in four languages and in Japanese), some are the engine (every European edition runs at 25 frames a second), and some are nothing at all (Exoddus's English European edition is byte-identical to the base inside every level).

Fourteen releases are too many to carry by hand, and an overlay assembled by hand is one nobody can check again. So this item plans a mechanism: one census and one build that read any release off its own discs, compare every layer with the base by bytes or by pixels, and write that release's overlay, every judgment either read off the disc or held by a check that fails loudly. A prototype of it, the census below, covers all fourteen releases in under a minute. NTSC-U stays the base, each release is an overlay of final values over it, and which releases the site carries is a list, so adding one is an addition alone.

## Census

Measured 2026-10-20 against every release in the table, with throwaway scripts that are the mechanism's prototype; each method is stated with its finding, so the census can be run again from them.

- **Archives:** every member of every level archive hashed, taking the largest copy of each level across a game's discs as the builder does.
- **Paths:** each `Path` chunk decoded with the builder's own `resolve_path_meta`, `tlv_header_ok` and `object_fields`. Objects were grouped by camera through the index table at the chunk's end, the filing the game itself builds from, then aligned per camera by type with a longest-common-run diff. A matched pair counts as changed where its rect or a field differs; the TLV header's end-of-list bit is left out, since it only follows the list's length. Collision lines were aligned the same way on their coordinates and type.
- **Path dimensions:** read from each disc's own executable, which holds the PlayStation's path table (a collision record and a path record per path, the grid in world units, the collision offset and count, the object and index offsets, and on Exoddus Abe's start), found by its shape.
- **Cameras:** decoded through `cam2rgba` and compared by pixel. The foreground went through `decode_fg1`, compared by coverage and by pixel. Whether a camera *looks* different was measured as the largest change, over every 4×4 window, of the window's mean luma (*the window measure* below).
- **Messages:** the tables found by shape (a pointer table whose entries land on a run of 31 lead characters, or the builder's `string_table` where an English anchor exists), from every overlay that carries one.
- **Fonts and glyph tables:** the font files parsed and rendered; the glyph tables found by their shape in each executable.
- **Sprites:** every animation `tools/data/sprite_anims.json` lists decoded through `build_sprites` per release, frames compared by pixels, offsets and timing.
- **Code:** a throwaway MIPS R3000 disassembler. Executables and overlays were split into functions at `jr ra`, and every address-bearing word was masked (jump targets, `lui` halves and their partners, pointers in data tables), so a function that only moved compares equal. `VSync` was found through the function that prints `VSync: timeout`, `SetVideoMode` by its shape (a setter and a getter of one word), and every call site's first argument was read.

What every release shares: the camera grids and the 368×240 window, the TLV formats, every path's grid, the 256-byte random table `read_dice` finds, the FG1 render-layer tables (the halfword runs 37, 18 and 4, 18, 23, 37 sit in all sixteen executables), and the frame pacing itself: every executable flips its frame on `VSync(2)`, two vertical blanks a frame, so a release runs at 30 Hz where it calls `SetVideoMode(0)` and at 25 Hz where it calls `SetVideoMode(1)`, as every European edition does.

### Where each release's levels come from

Oddysee's level data falls into four families, read off which `Path` chunks each release shares byte for byte. Rev 1, Rev 2 and the Japanese release share theirs: the Japanese release holds every one of Rev 1's 74 chunks. The first pressing, France and Germany share theirs: France holds all 74 of the first pressing's and Germany 73. Italy and Spain share theirs with each other and 69 of the 74 with the first pressing. The English European edition's is its own, sharing 8 to 11 chunks with any other, though its art keeps the first pressing's on the two screens Rev 1 redrew (D2P10C04 and F1P02C04). So the base's levels are Rev 1's, a revision of the first pressing's that the localized editions, built from the first pressing, never received; and Oddysee's English European edition reworked them again on its own. Exoddus's localized editions keep the base's levels, French and German moving two lines in one path, and three of them (French, Italian and Spanish) carry on disc 1 the test level the Japanese release carries, which the others do not.

### Oddysee `eu`

- **Archives.** 13 of the 14 path files differ, and D1, E2, F1, L1 and R1 change size. Beside them: the menu's `STARTANM.BND` and its `ABEINTRO.BAN` and `ABESPEAK.BAN`, two of the attract-mode demo recordings (`PLAYBK12.JOY`, `PLAYBK14.JOY`), the movie indexes, and 35 cameras. The sound banks, fonts and every other sprite file are identical.
- **Path dimensions** are unchanged. The executable's path table moves only where the chunks do: six collision counts (D1 P6 79 to 78, E2 P3 34 to 35, F1 P2 24 to 23, F1 P7 15 to 14, L1 P1 48 to 47, R1 P20 31 to 30) and the object and index offsets behind them.
- **Collision lines** differ in 64 of the 74 paths. 385 lines keep their place in the list with an endpoint moved; 8 NTSC-U lines are gone and 4 are new, one pair of those a line moved within the list. 144 of the moves are of two units or less, walls nudged a unit or two either way; the rest trim or extend floors and ceilings, by up to 356 units (D1 P3's floor at y 316 ends at 3879 rather than 4009). 226 of the 385 moved only an end lying in the slack outside the 368×240 window, where nobody stands; 159 moved an end inside it.
- **Objects** differ in 20 paths: 51 changed, 2 removed, 1 added. A Slig in R2 P4 moves 51 units left with its right bound moved 75, its right pause going from 60 frames to between 90 and 180, its shoot-on-sight delay from 30 to 60 and its chase-when-spotted from 0 to 1. D1 P7's continue zone and point are renumbered 31 to 29 (`clear_to_id` 80 to 60), and another continue point moves 272 left and 134 down. Eight Scrabs (D2 P2, D7 P11) drop `disable_resources` from 1 to 0, and four Sligs and their bounds change `disabled_resources` (707 to 963, 124 to 125). Six bird portals shift by 2 to 27 units, five death drops are trimmed, F1 P5's two death drops become one, hoists lengthen, F1 P2's edge moves 97 right with its path transition and death drop reworked, R2 P20's security claw moves 279 left, three mines in E1 P3 are respaced, and R6 P6's hoist flips its grab direction.
- **Cameras.** Of the 35 files, 2 change pixels: D2P10C04, the Scrabania map screen, redraws two rows of its path blocks, and F1P02C04 loses a leaning stake from the scene, the screen whose edge, death drop and path transition Europe also reworks. 8 change their foreground coverage: blocks added on four screens (the Paramite story screen and the Board Room's two ending text screens among them, where a tile of the screen's own pixels draws nothing new), removed on three, cut on one. 20 more carry FG1 bytes that draw the same masks. 4 preload a different set of camera-resident resources: Europe adds a 4×16 resource, id 1000, to cameras in D1 and F1, and its D1 and F1 copies differ. S1P01C23 differs only past its last chunk. The menu path drops three cameras from its name table and the disc: the Shaman's bio screen (C11) and the base disc's two Exoddus promo screens (C32, C33).
- **Messages.** The LCD table (37 of 90 filled) and the hint fly table (36) are identical in every overlay of a level the map draws. `D6.OVL`, the overlay of a level the builder never reads, carries an older LCD table with one space more in message 58, which `extract_messages`'s rule that every copy agrees refuses.
- **Fonts and sprites.** The LCD font and its glyph table are identical; so are all 267 animations. The release still fails `gather_chunks`, which holds every camera's copy of a resource id to the first and meets id 1000 differing between D1 and F1, although no listed animation reads it.
- **Code.** `SetVideoMode(1)` where NTSC-U calls it with 0, and `VSync(2)` at the same three sites, so a frame is 1/25 s. The save screen's play time divides elapsed frames by 25 where NTSC-U divides by 30, so a PAL save shows real hours and minutes; the Board Room's gas countdown still computes 120 less the elapsed frames over 30, so on a PAL console its 120 shown seconds last 144. Otherwise this is a revised build, not a port: 79 blocks of the executable differ with addresses masked, and every level overlay differs, by 5 to 32 functions (the unused `D6.OVL` by 242). The changes read as logic: an attached object's release dropped from a routine, branches restructured. None of it is catalogued.

### Oddysee `jp` (Abe a GoGo)

- **Archives.** Of the path files only the menu's `S1PATH.BND` differs, so every level's paths, lines and objects are NTSC-U's byte for byte. Beside it: 189 cameras, `LCDFONT.FNT` in every level, `ABEOMM.BAN` in every level (Abe's chant, 13 frames redrawn around the hands), 14 of the 15 sound banks (the voices), and the movie indexes. The menu drops the base disc's two promo cameras (C32, C33), and its C11 holds the GameBank logo where NTSC-U has the Shaman's bio.
- **Cameras.** 188 of the 189 change pixels; the other differs only in a `Font` chunk. 186 are edits. Text is replaced on signs, the story and level-map screens, the menus, the credits, every tally board's caption, and the exit prompt (✕ EXIT becomes ✕ 戻る). The hand print is redrawn on every hand stone and bell song stone, all 27 and all 17 of their cameras, and every one of the 29 tally board cameras carries an edit. 2 are re-encodes alone (E2P04C01, D1P07C17). On the window measure the two re-encodes sit at 2.8 and 3.6 and the edits at 6.0 and above, the hand prints lowest (6.0 to 10.5, D2P03C03's bell song stone the 6.0). The edits are spread 61 in R2, 26 in L1, 21 in R1, 15 each in S1 and D2, 10 in F2, 9 in C1, 8 in D1, 7 each in E1 and F1, 6 in R6 and 1 in E2. 58 cameras re-cut their foreground's partial blocks, whose own pixels follow the new art; no coverage changes.
- **Messages.** The LCD table has the same 90 slots, the same 37 filled, in the same 8 overlays, its text in the JP font's own code page: single bytes from 0x14 to 0xDB, the button codes 0x08 to 0x13 as in NTSC-U. The hint fly table has the same 36 entries at the same place, re-encoded; entries 2 and 4, which no hint fly names, hold a placeholder.
- **Font.** The LCD font is 240×182, 9×12 glyphs: katakana, hiragana, about a hundred kanji, digits and the PlayStation's buttons. Its glyph table has 224 entries, and `glyph_table_windows`, which looks for a table whose lowercase letters repeat its uppercase ones, finds none.
- **Sprites.** 266 of 267 identical; L1P01's camera animation `bg:5007` draws the same pixels 2 units further left.
- **Code.** `SetVideoMode(0)` and `VSync(2)`, so 30 Hz. 52 blocks of the executable differ, and at most 4 functions of each level overlay (22 of the menu's), the paths that draw text.

### Exoddus `eu`

- **Archives.** Every member of every level archive is byte-identical to NTSC-U's: 1,155 cameras, 182 sprite and path files, 1,146 animation banks, the fonts, the sounds and the saves. The LCD table is identical too.
- **Code.** Identical with addresses masked, but for: `SetVideoMode(1)`; the display window placed 24 lines down and 236 tall; the save screen's play time dividing elapsed frames by 25 where NTSC-U divides by 30, in both places it turns frames into hours and minutes, so a PAL save shows real time, while the gas countdowns keep dividing by 30, so a countdown of 7200 frames shows 240 seconds and lasts 288; two resource ids in the boot sequence; and in some overlays one or two words of stale padding. `VSync(2)` at the same four sites, so 25 Hz.
- So the European Exoddus map is the NTSC-U map on a 25 Hz clock.

### Exoddus `jp` (Abe '99)

- **Archives.** 6 path files differ (BM, BR, BW, FD, MI, ST), every camera, `LCDFONT.FNT` and `ABE2.FNT`, 16 sound banks, the Brewery's two `NXTP0888.SAV`, and the menu's movie index. 156 members are new: disc 1 carries the test level `TL.LVL` as a 3.2 MB archive of 155 members where the base carries the 68-byte boot stub, and the menu gains STP01C52, the ABE '99 title logo.
- **Path dimensions** are unchanged. Three rows of the path table follow the chunks: MI P4's collision count 153 to 157, FD P5's 93 to 94, and BM P1's index offset.
- **Collision lines** differ in 5 paths: MI P4 gains four floors (y 2140 from 375 to 1125, y 1120 from 2950 to 3250, y 840 from 3850 to 4150, y 3480 from 3000 to 3350), FD P5 a wall (x 1075, y 940 to 1017), BR P14's floor at y 580 extends 375 left, and lines in FD P11 and MI P10 move 2 units. MI P4's four added lines are past what `audit_path_meta` would recover: it searches two lines either side of the tabulated count.
- **Objects** differ in 8 paths: 15 changed, 3 added. The Brewery Ender (BM P1) gains three gas countdowns (start switch 5, 7200 frames) on screens C01, C19 and C21, which NTSC-U leaves without one beside its twelve; its first door loses its switch, target and movie (3, 1 and 1 to 0), a reset-switch range widens and a slam door's flip clears. BR P14's two death drops are reshaped to the extended floor; a BW P4 status light is rewired (switch 133 to 250, its other three ids shifted); two BW P7 levers' action goes from 2 to 0; an FD P3 door moves a unit; an FD P5 door's target goes from 0 to 30003 beside the new wall; an FD P10 door closes on exit; three FD P11 security orbs move and a Glukkon switch's `x_position` goes from 2060 to 2062.
- **Cameras.** Every one of the 1,155 is re-encoded, its MDEC stream 17% smaller on average. 351 are edits: zone and tunnel numbers on signs (ZULAG, ANNEX and TUNNEL become ブロック), MINE CAR, the story stones, the tally boards' captions (147 of the 187 tally board cameras; the rest show a hidden board or none of its caption), the menus (19), the credits (6), and the exit prompt. The edits are spread 85 in BR, 65 in MI, 46 in FD, 41 in BW, 40 in BA, 19 in ST, 15 in NE, 12 in BM, 11 each in PV and SV, and 6 in CR. The other 804 are re-encodes alone. On the window measure they reach 11.1, while the edits start at 22.0. MIP04C35 is the one edit as small as a touch-up: a few pixels of a ledge's highlight, at 23.6. Hand stones keep their print here: 50 of the 73 hand stone cameras are re-encodes alone, and the print compared by eye is unchanged. 12 cameras change their foreground coverage, 5 of them among the re-encodes: blocks moved between render layers, pillars added or cut. 197 more re-cut their partial blocks' own pixels with the same coverage.
- **Messages.** The LCD table has the same 101 slots, the same 70 filled, in the same 10 overlays. A space is 0x02 and the scroll-in lead is 31 of them; single bytes from 0x02 to 0xFE are glyphs, and 0xFF escapes to a second byte for the glyphs past them, so the button codes are no longer 0x08 to 0x13.
- **Fonts.** The LCD font is per level. The five levels with LCD screens (BR, BW, FD, MI, ST) carry a 208×192 texture of 12×12 glyphs; the five without (BA, BM, NE, PV, SV) carry a 104×12 strip of the digits and a colon, which the tally boards draw; TL carries a 256×256. The strip's glyphs sit where the full font's first row puts them, so one glyph table serves both: 327 entries in the executable, 277 distinct. `ABE2.FNT`, the menu font, differs too; the map draws neither menu.
- **Sprites.** All 202 animations identical.
- **Code.** `SetVideoMode(0)` and `VSync(2)`, so 30 Hz. 36 blocks of the executable and 1 to 20 functions of each level overlay differ, the text paths and whatever fixes go with the data above; uncatalogued.
- **The test level.** `TL` holds two paths and 13 cameras: three brewery screens (P1, 3×1, two Fleeches, five hoists, a lever, two explosion sets, a colourful meter) and ten developer screens (P2, 5×7), checkerboards with the camera's number drawn on them, holding nine doors and two express wells whose destinations were never set. No executable of any release holds a path record for it, so nothing in the PlayStation code can load it. Only the decomp's PC table has rows for it, and those say P1 holds 20 collision lines with its objects at 424, where the chunk holds 14 and its objects elsewhere.

### Oddysee's other US pressings

- **`us-r1`** is the base without the two Exoddus promo screens the menu shows (C32, C33): beside its menu path and those two cameras, its archives differ only in two menu cameras' foreground bytes, which draw the same masks. Its code differs in 34 blocks of the executable and in 0 to 14 functions of a level overlay (the menu's 14), 18 of the 28 level overlays matching the base's.
- **`us-r0`** is the first pressing, and its levels are the ones the base revised. 11 collision lines move and 3 more are gone, in 8 paths; 28 objects change in 14 paths. 43 cameras differ: 3 change pixels (the Scrabania map screen and F1P02C04's stake, which Rev 1 redrew, and a credits screen naming another QA team), 4 change their foreground coverage, and the rest differ in foreground bytes, camera-resident resources or a font chunk. 52 animation banks differ, and 22 of the animations the map draws with them: the background Glukkons' idle and gestures in both their palettes, the green glow and the crouching chant among them. The LCD font, the messages and the voices are the base's. Its code differs in 45 blocks of the executable and 5 to 31 functions of every level overlay.

### Oddysee's localized editions

- **Levels.** France's and Germany's are the first pressing's (Germany's R2 apart), Italy's and Spain's their own variant of it, as *Where each release's levels come from* sets out, so each carries the first pressing's collision and object differences against the base, not the English European edition's rework.
- **Cameras.** 147 to 177 look different: the signs, the story and level-map screens, the tally boards' captions and the exit prompt are translated (SLOG KENNELS becomes SLOG-ZWINGER), and the three screens where the first pressing differs from the base come along in all four. Each has one re-encode alone or none, at 3.0 to 4.8 on the window measure.
- **Text.** The LCD table has the base's 90 slots and 37 filled, translated, its letters beyond ASCII in IBM code page 437: é, à, ç, ê, è, ô and û in French, Ä, Ö and Ü in German, é, à, è, ò and ù in Italian, é, á, í, ó, ú and ¡ in Spanish. The font is redrawn in every level with those glyphs in the slots the base's glyph table already holds (0x80 to 0xAF reach its entries 97 to 144), and the table itself is found by the base's shape.
- **Sprites.** Spain differs from the base in the same 22 animations the first pressing does, France in 14 (13 of them the first pressing's, and the flint glow), Italy in one camera animation, Germany in none.
- **The rest.** The voices differ in 14 of the 15 sound banks; the menu drops the same three cameras as the English European edition; no overlay is byte-identical to the English European edition's.

### Exoddus's localized editions

- **Levels.** The base's, but for two collision lines moved in one path in French and German. French, Italian and Spanish carry the test level on disc 1, as the Japanese release does.
- **Cameras.** 355 to 359 look different, translated as Oddysee's are (MAP becomes PLAN on the Brewery's signs, the tally boards' captions in French); none is a re-encode alone, and the smallest edit sits at 26.3 on the window measure. One camera in each changes its foreground coverage.
- **Text.** The LCD table has the base's 101 slots and 69 or 70 filled, in IBM code page 437 like Oddysee's editions; `LCDFONT.FNT` is redrawn in every level and `ABE2.FNT`, the menu font, is the base's.
- **Sprites.** French and Italian draw the Necrum rope differently and Spanish the air explosion; German draws all 202 animations as the base does.
- **Code.** 13 to 21 blocks of the executable and at most 6 functions of a level overlay differ.

## Decided

- **The item covers every retail release, through one mechanism.** Fourteen releases differ from the base on every layer at once, by amounts no hand census can keep current, and the prototype reads them all in under a minute; so the census and the build are one generic path any release runs through, and nothing in the builder or the viewer names a release. What the site carries is a list in the release table: the English European and Japanese releases first, as below, and any other release later as an addition alone. Their art is the cost to weigh as each is added: about 150 MB for all fourteen beside the base's 204 MB, nearly all of it the translated screens, patched over the base's: 13 to 16 MB for each localized or Japanese Oddysee and 13 to 15 MB for each localized or Japanese Exoddus.
- **A release shares the base art where it only re-encodes.** The map shows a release's picture, not its exact compression. Exoddus's Japanese release re-encodes 799 cameras with nothing changed, the same picture as the base's for about 95 MB; its smallest real edit (22.0 on the window measure) sits well clear of its largest re-encode (11.1), every localized Exoddus edits at 26.3 and above, and a test on the gate's margin keeps the gate from ever deciding on noise. Oddysee, whose Japanese release's smallest edit (6.0) sits too near its re-encodes for any gate, ships every camera whose pixels differ, at most two re-encoded cameras a release.
- **A release's own camera ships as patches over the base's screen.** A redrawn screen is mostly the base's picture, a sign or a caption in a scene, and the fourteen releases' screens shipped whole would cost about 320 MB. So a camera ships the release's pixels over the 16×16 macroblocks it changes, one rectangle over each 8-connected group whose rectangle lies inside no other's, drawn over the base's screen; a camera the base lacks, or one whose patches would cover it all, ships whole, and the masks ship whole, few of them equal to the base's (30 of the Japanese Exoddus's 290). A block counts by its camera's rule. Oddysee has no gate, so any pixel that differs counts, and a patched screen is the release's own pixel for pixel. Exoddus counts a block where a window over it measures at least 12, the gate less its margin, which the margin test holds every camera that only re-encodes under, so the base's encode stands in only for what a re-encode alone could change. It counts them again over the screen the patches compose, until no window there reaches 12: a window across a patch's edge sums the change on both of its sides, and noise that cancelled there stands alone once the patch draws one side (one across the edge of the Spanish Exoddus's patch on BMP01C02 measures 6.6 against the base and 12.8 once the patch is drawn, so the patch takes one more column of blocks). The gate itself, applied a block at a time, would leave 1,716 to 1,919 blocks a release between 12 and 16 to the base, edits among them (a faint arc redrawn on the Japanese MIP02C06's RETURN TO sign measures 16.0 at its strongest block), and taking them costs the Japanese release 0.7 MB.
- **Oddysee takes no block gate.** Its edited screens were re-encoded whole, so about half of a patched screen's blocks differ by noise alone, and a gate leaving those to the base would cut its art again: Abe a GoGo's 16 MB comes to about 14 MB with a gate of 2 on the window measure and about 8.5 MB with a gate of 5, each with the blocks it keeps grown by one. But a gate needs the camera gate's proof, an empty margin around it, and Oddysee has none at either scale: its smallest real edit, D2P03C03's hand print, measures 6.0 against its re-encodes' 2.8 to 4.8, and inside its edited screens every unit of the window measure from 4 to 30 holds 82 to 531 blocks in each localized or Japanese release, so any gate would decide blocks on noise, and how many is what moves the size from 14 MB to 8.5.
- **Every release's screens draw its own glyphs from the first slice; text is read through its code page.** The European editions' code page is IBM 437, a standard one, so their messages read as text from the start. The Japanese code pages are hand-curated, a slice of their own after the release ships: about 475 distinct glyphs (198 Oddysee, 277 Exoddus), mostly kana, a few careful hours. Until a Japanese table exists the sign panel says the text is Japanese and search skips it. Either way a test holds that every code a message uses reads as a character and has a glyph.
- **Every release the map carries is on the switch, Exoddus's English European edition included.** "Same levels, 25 frames a second" is itself what a European player wants to know, and its note adds that the gas countdowns show 240 seconds and last 288.
- **A release whose code is not the base's runs the base's brains.** Every release's code differs from the base's somewhere, Oddysee's English European edition in 79 blocks of its executable and every overlay, so its lines, objects, art and foreground come off its own discs while its creatures run the base's brains on its own clock. That is the map's doing, not the release's, so a release's note leaves it out and says only what the release changes. The map claims nothing it has not read; cataloguing a release's code is a job of its own.
- **The test level stays out.** No executable can load it, in the Japanese release or in the three localized Exoddus editions that carry it, so the census above is its record. It may come later as a curiosity, for which the overlay would need a shape.
- **A release is named for where it was sold, and its link token is that code.** The map shows a release's content, not its video standard, so `pal` names the wrong thing, and where a release was sold is what tells the releases apart: Europe sold each game as five editions, each on a disc and serial of its own and each a build of its own. So `eu` names the English European edition, a localized one takes the ISO code of the country its Redump entry is tagged with (`fr`, `de`, `it`, `es`), as `jp` does, and a US pressing other than the base takes `us` and Redump's revision (`us-r0` for the first, `us-r1` for Rev 1); the base never takes a token. A reissue shares its edition's dump and needs no code. The codes are bare like `graph`, since none can clash with another token, which is the only thing a keyed `region=…` would buy. The same codes name the overlays, the art directories, the disc variables and the edit stores, so a release is added with nothing renamed.

## Design

### The mechanism

- **The release table,** `tools/data/releases.json`, hand-curated and held to its shape by a test: per game and code, the release's name, title, language and Redump entry, its executable's name, each disc image's SHA-1, the code page its messages read through, whether the site carries it, its note, and any verdicts on cameras within the gate's margin (below). It is the only place a release is described; everything else about a release is read off its discs.
- **Identity by SHA-1.** A build hashes the images it is given and refuses any that is not the release's own, so a misnamed or modified image can never build the wrong release, and file names never matter. Given a directory instead of images, it finds each release's discs there by their SHA-1s.
- **The census,** `build_map.py --census`, for one release or all: reads the release, compares every layer with the committed base, and prints the report this item's census tables are made of, writing nothing. Its first proof is this item: run over every release it has to reproduce the census above.
- **The build,** `build_map.py --release <code>`: the same comparison, writing the release's overlay and art. It reads the base from the committed tree, the data file, the cameras' pixels through `read_png`, the masks and the sidecars, so it needs no base disc, and its output is a function of the release's discs and the committed base, byte-deterministic as the base build is.
- **Read, never configured per release:** the path tables off the release's own executable rather than the decomp's PC table and `audit_path_meta`'s search, which Exoddus's Japanese MI P4 is past the reach of; the message tables by shape, the lead run of 31 of the code page's space, and only from the overlays of the levels the build reads (which leaves the European editions' stale `D6.OVL` out); the glyph table by the base's shape or, failing it, the Japanese one; the clock from `VSync(2)` and `SetVideoMode(n)`; the fonts per level, held to agree on the glyphs they share; and the camera-resident animations the sprite table lists, `gather_chunks` holding only those to their first copy, so the English European Oddysee's unlisted resource 1000, differing between D1's and F1's cameras, stops failing the build.
- **Checks that fail loudly:** an image whose SHA-1 is not its release's; a base rebuild that does not match every committed file byte for byte; a camera within the gate's margin with no verdict in the release table, which a look settles once; a message code its code page cannot read or its font has no glyph for; a grid that differs from the base's; an overlay key or field the base does not hold; and a scratch build that is not byte-identical to the committed overlay.
- **What stays manual,** and nothing else: the release table, the Japanese code pages, a verdict for a camera within the margin, and each release's note.

### NTSC-U stays the base

`map_data_{ao,ae}.json`, the cameras, sprites, messages and every sidecar stay what they are, built from the same discs. A release never forks the base: it is a small file of final values over it, and the map with no release chosen is the map as it ships today.

### A release is an overlay of final values

One file per game and release, `release_{ao,ae}_<code>.json` beside the base data, holding only what differs, each value the release's own:

- **Its identity:** its code and name, its title (Abe a GoGo, Abe '99, L'Odyssée d'Abe, L'Exode d'Abe, the base's title elsewhere), its executable's name, its clock (`hz`, 25 or 30), its code page, and its note, which the switch shows.
- **Objects, per path, in the edit sandbox's delta shape** (`{objects: {key: {fields, rect, removed}, "+n": {name, rect, fields}}, next}`, [docs/viewer-editing.md](../docs/viewer-editing.md)). A key is the base object's pristine origin, `Name@x1,y1` with `#n` where the tuple repeats, so it is stable for as long as the base discs are. A changed field carries its final value; a moved or resized object its whole rect; a removed one `removed: true`. An added object is a `+n` entry with its type, rect and every field, and one field the sandbox does not use, `after`: the key of the object it follows in the release's own list, since a release adds objects mid-list and the brains seed their dice from an object's place in it (Exoddus's Japanese gas countdowns each close their camera's run, with other cameras' objects after them). Objects are aligned per camera, as the census aligned them, so an object a release refiles under another camera arrives as a removal and an addition, which is also how the game builds it.
- **Collision lines, per path, whole.** A line has no identity but its index, and the links between lines are indices, so a path whose lines differ at all carries its full list and its links, in the release's order. Oddysee's English European edition's 64 paths make this the largest part of any overlay and still small beside the base.
- **Cameras, per path:** a name the release drops maps to `null`, a name it adds to its cell and art, and a camera whose art the release changes to its patches, `[x, y, file]` each, or to its whole image where it has no patches, and to its masks. Path dimensions never differ, so the overlay has no field for them.
- **Messages, the font and sprites,** whole where they differ: the message tables as the release's own codes, the LCD font sheet and glyph table, and the sprite sidecar's entries that differ with the family sheets they draw from, each named for its pixels as the base's are. The random table is the same in every release, so no overlay carries one.

The materialization is the sandbox's own: the overlay's deltas apply to the base the way stored edits do, through the same functions, with `after` placing an addition. The result is the release's pristine dataset, and the visitor's own edits then apply over it as they apply over the base today.

### What makes a camera regional

A camera is regional where it *looks* different, or where its foreground coverage differs; elsewhere the base's art and masks stand. For Oddysee that is every camera whose pixels differ: its Japanese release's smallest edit, the hand print on D2P03C03's bell song stone, sits at 6.0 on the window measure, too near its re-encodes (2.8 to 4.8 across Oddysee's releases) for a gate to stand between them, and shipping those costs at most 0.12 MB a release. For Exoddus it is a gate of 16 on the window measure, the middle of a gap from 11.1 to 22.0, and a test holds the margin, failing any camera that lands within it until the release table records a verdict. A regional camera ships as patches of its own pixels over the base's screen, a block at a time by its game's rule (any pixel for Oddysee, the gate less its margin for Exoddus), with every mask cut from its own pixels, so a regional foreground sits over its own picture, or for Exoddus over one no further from it than a re-encode. [docs/viewer.md](../docs/viewer.md) says once that a release's screens show its picture, the base's encode standing in wherever the release only re-encoded.

### The viewer

- **The switch** sits on the selected game's row: the releases the site carries for that game, named for where they were sold, the base first, with the selected one's title on the game button, so choosing Japan on Oddysee reads Abe a GoGo, and its note beside it. Switching swaps the dataset, keeps the place and the view (every release shares the base's geometry and identities), and announces itself the way a game switch does.
- **The permalink** carries a release as a trailing bare token, its code, matched by shape like `graph`; no token means the base. A viewer that predates releases ignores the token and lands on the base map at the same world coordinates, which is the right place in every release. An object segment keeps naming the base origin, so a link to an object a release moved opens on it in either; an object a release added is named by its own origin and resolves in that release alone, and one a release removed leaves the link on its path with a toast saying so.
- **The mark** says what a release changes, wherever it shows, as the edit mark does and in its own colour: an outline on an object whose values differ from the base's and a line in its tooltip, the screen list and a search hit naming what changed (`EU: zone_number 31 → 29`); a removed object as a ghost while the mark is shown; a changed collision line drawn in the mark's colour; a corner tag on a screen whose art is regional; a tag on the path button, the chip and the place panel; and the release in every export's name. A Display toggle, on whenever a release other than the base is chosen, shows and hides it.
- **The clock** steps the live map at the release's own rate, so a European edition's patrols, timers and loops run at 25 ticks a second, as a PAL console runs them.
- **The text.** The LCD port draws every release's messages through its own font sheet and glyph table, reading the Japanese Exoddus escape byte, from the first slice. The sign panel, the tooltips and search read a message as text through the release's code page where it has one.
- **Search and the rest** read the release's dataset as they read the base's; the level pages and sitemap stay the base's.

### Edits

The store is keyed by game and release: `owm:edits` stays the base's, and each other release keeps its own key, `owm:edits:<code>`, in the same shape. A separate key rather than a release inside the one object, because `sanitizeEdits` keeps only two-letter game keys and writes back what it kept, so a tab still running a viewer from before releases would erase a release's edits on its next write. Inside a release the sandbox runs unchanged over the release's pristine dataset, its keys that dataset's origins.

### Cache identity

Regional art is named for its pixels, under `cams/{ao,ae}/<code>/`, and lies outside `CACHE_NAME`'s hash, as the sprite sheets do ([99](item-099-sprite-sheets-per-family.md)): a release's rebuild expires no visitor's base cameras, and a base rebuild expires no regional art. The worker stores a regional file beside the base ones and retires that file's earlier copy as its successor is stored, the sheets' rule keyed by the name before the hash, which for a patch is its screen's and its place on it. The offline panel counts a release as the base's files less the ones its overlay replaces, the screens its patches are drawn over staying, plus its own.

### Tests

Without discs: the release table's shape; each overlay's shape; every key resolving to a base object and every field it names existing on that object; every regional file present and named for its pixels, every patch on the block grid inside a screen the base holds and none inside another, a whole camera only where its patches would cover it, and Oddysee's patches the rectangles of exactly the blocks they change; the camera gate's margin and its verdicts; the code pages' coverage; and materializing each release, then switching back to the base, giving back the base dataset itself. With the discs: a full scratch rebuild of both base games matching every committed file, then each release's scratch build byte for byte against its committed overlay, and the census reproducing this item's.

## Slices

1. **The mechanism**, on the disc machine.
   - **The base first.** The release build reaches code the base build runs too (`executable()`, the message tables found by shape rather than by an English anchor, `gather_chunks`' first-copy rule), and an overlay is only as trustworthy as the base under it. So a full scratch rebuild of both base games has to match all 3,305 committed files byte for byte (Oddysee 1,073, Exoddus 2,232, counted 2026-10-20), compared both ways as [docs/builder.md](../docs/builder.md) describes, once the builder changes land and again before the slice closes.
   - **The release table and the census,** which has to reproduce this item's census for all fourteen releases.
   - **The build, one release at a time:** Exoddus `eu` first, its overlay being its identity, clock and note alone, the cleanest test of the plumbing and the disc identities; then Oddysee `eu`, the first overlay of data, its objects, lines and 10 regional cameras; then the two Japanese releases, the gate and its margin test arriving with Exoddus `jp`.
2. **The release in the viewer:** the materialization over the base, the switch, the token, the clock, the mark and its toggle, every release's glyphs on the screens and the European text, the per-release edit stores, the worker's rule for regional art, the docs, and the What's New entry.
3. **The Japanese code pages:** the two hand-curated tables beside `tools/data/sprite_anims.json`, and the sign panel and search reading Japanese as text.
4. **Every further release,** an addition each: turned on in the release table, built, its overlay and art reviewed and committed, with its What's New entry.

## Ruled out

- **Overlays assembled release by release by hand.** Fourteen releases, each differing on every layer, would be fourteen censuses nobody could run again.
- **A release over the release it was built from** (France over the first pressing, the first pressing over the base). It would save little, since each still differs from its parent, and it would make every overlay depend on another's build; each release answers to the base alone.
- **A full dataset per release.** Exoddus's English European one would be a byte-identical copy and the others 95% copies, doubling what a visitor fetches, and every curated name and note would have to follow every file.
- **A release as a game of its own on the game row.** It would split the level pages, the type counts and the world graph by release, and its permalink token would make a viewer from before releases reject the whole link.
- **The release in the game token** (`#AO.eu/…`): the same rejection.
- **Every camera whose pixels differ, for Exoddus.** The Japanese release's 804 re-encodes show the same picture at about 95 MB, and [73](item-073-repo-size-trajectory.md) stands on the artwork being final.
- **A regional camera shipped whole.** About 320 MB for the fourteen releases where patches over the base's screens cost about 150, and history would keep every byte of it.
- **Holding a release until its code page is curated.** Its screens draw the right glyphs without one, which is what the map is for; the table only makes the text readable to search.
- **Cataloguing a release's code before shipping its data.** Its lines, objects and art stand on their own, and its creatures run the base's brains meanwhile.
- **The video standard as a release's name** (`pal`): what the map shows of a release is its content, and the standard is only its clock.
- **The decomp for a release's data.** It is the PC build, and its path table already disagrees with the base discs; each release answers to its own discs.
