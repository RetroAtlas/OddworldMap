# 98. A level made from scratch

**Status:** open — research first, since the one question that decides the shape needs a relive install to answer · **Effort:** large · **Where:** viewer, with the export and import in the edit model; nothing here needs a disc

**Filed:** 2026-10-12, from the record of [42](item-042-level-editor.md)'s third slice, whose *What the maker will need from here* lists what a path made from scratch asks of a sandbox built to edit shipped ones.

## What and why

Editing a shipped path is done: an object's fields, place and size change, an object leaves, arrives from a picker of the game's types or is duplicated, every edit stays on the device and marked, and the path saves as the level editor's own JSON ([42](item-042-level-editor.md)). The next thing a builder wants is a level that was never on the disc. The picture is the sibling map's editor, KulaWorldMap's, which makes a level of its own or copies a shipped one, keeps drafts in the browser until they are saved as the map's own file or as the level the game loads, and lets the game's own rules refuse what it could not load: here, screens chosen from a selector and laid on a grid that opens at a default size and grows as a screen is placed past its edge, each template screen arriving with its objects, which then edit, move, remove and duplicate exactly as a shipped path's do, and the whole saved as the relive JSON the exporter already writes, so the level plays in relive the way an edited path does.

What the sandbox presumes is the gap. Every key in the store names a pristine origin, a shipped object on a shipped path; the type table, the placement rule and the export all read a path record with its grid, its cameras and their artwork files from the dataset. A made path has none of that behind it, and the export carries values no object holds.

## What it needs

- **A pristine stand-in for a made path.** A path record of the dataset's shape (id, grid size, cameras, empty object and line lists, the level it belongs to) that the materialization stands deltas over as it stands them over a shipped path, so `pristineOf`, `objectKey` and the swap keep their one rule and every surface that follows `data-changed` follows a made path for free. Where the record lives, how it persists and which level and path id it claims are the first decisions.
- **The editor's own JSON read back in.** A made level has to outlive `localStorage` and move between devices, and the JSON the site writes is the natural file: imported, it becomes the stand-in's objects and lines, every one marked as the sandbox marks an edit, so nothing read from a file can pass for the game's own. This is a file the builder keeps, not a link ([42](item-042-level-editor.md)'s *Ruled out* keeps edits out of links and patches, and a file import changes nothing there). Reading an edited shipped path back in is the same code and useful on its own.
- **The path's own values.** The export carries Exoddus's Abe start per path, the mud counts and the LCD and hint-fly message arrays from the shipped path; a made path needs a place to set them, and a shipped path being edited may want one too.
- **Screens and their artwork.** The one thing to measure before anything is promised: relive's import finds a camera's artwork by name in the target LVL, so a template screen taken from another level names a CAM the LVL does not hold. Either the maker keeps to the target level's own screens, or the artwork travels with the JSON, which has to be weighed against relive's 640-wide PC cams where the site holds the PS1's 368×240. Whether the import can create a path the LVL does not already hold, or only overwrite one, decides whether a made level stands beside the shipped paths or replaces one.
- **Collision lines.** A made screen without floors and walls holds nothing up; a template screen should carry its lines, and the lines will want editing, which is [42](item-042-level-editor.md)'s one parked slice and belongs here as much as there.
- **Group work.** A marquee and group moves for arranging a template's objects, and changing an object's type in place, both left out of the third slice and both more valuable once there are whole screens to arrange.

## Sketch

Research first: with a relive install and a copy of the game, import a JSON naming a CAM from another level and one naming a path id the LVL lacks, and record what the import does with each; the answers size everything below. Then the pieces in the order each is useful alone: the import of the site's own JSON for shipped paths (save and load of an edit session); the pristine stand-in and the path-level values, which together make an empty path editable; the grid and the screen selector over the target level's own cameras; template screens carrying objects and lines; and the growing grid last, since it is the only part that changes the dataset's geometry under the renderer. Every step exports through the Phase 1 writer and is checked against relive_api's reader as the shipped paths are.
