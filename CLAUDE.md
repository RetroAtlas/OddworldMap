# CLAUDE.md

Guidance for AI agents working in this repo. User-facing docs (controls, rebuild instructions, format overview) live in [README.md](README.md) — read that first; this file covers what is not obvious from the code and the traps that cost hours to find.

## Source vs generated

- Source: the viewer, under `public/` (the deploy artifact — everything in it is served, nothing outside it is) — `index.html`, `css/main.css` and the ES modules under `js/` (dependency-free vanilla JS, no build step; `js/main.js` is the boot entry, `js/state.js` holds shared state and binds `js/geometry.js`'s world→draw transforms to the live layout, `js/model.js` is handed the layout and the dataset, level and path a call depends on rather than reading the live ones from it, and selection announces itself via a `selection-changed` window event so modules stay one-directional) — plus `annotations.json` and the builder: `tools/build_map.py` is the CLI and the build loop, `tools/oddmap/` the package under it (one module per concern, with a one-way import graph), beside `tools/cam2rgba.cpp` and the vendored `PSXMDECDecoder.*` / `Types.hpp`.
- Hand-curated, each held to its shape by tests: `annotations.json` (names, notes and nicknames), `glossary_fields.json` (what each field means, and its unit) and `glossary_types.json` (the type encyclopedia). Their rules are in [docs/curated-data.md](docs/curated-data.md).
- Generated **and committed** (they are the site's data, under `public/` like the rest of it): `map_data_ao.json`, `map_data_ae.json`, `cams/ao/**`, `cams/ae/**`. Regenerate with the builder from disc images; never hand-edit.
- The rest of what is generated is committed too and never hand-edited, each file rewritten by its own step: `field_types_*`, `enum_labels_*` and `relive_export_*` by every build and by `build_map.py --emit-field-data`, which needs no disc and reads the committed `tools/data` caches; `messages_*` and `tools/data/lines_*` off the discs, by a normal build; the `tools/data/{pathdata,objects,enums,relive}_*` caches from the pinned decomp checkout, and only once deleted; `levels/**` and `sitemap.xml` by `node tools/levelpages.js`, due in the same commit as any rebuild or `annotations.json` edit because a test byte-compares them. [docs/decomp.md](docs/decomp.md), [docs/builder.md](docs/builder.md) and [docs/relive.md](docs/relive.md) hold the detail.
- Static site files that are not the viewer or its data (all in `public/`): `favicon.svg` (source of truth for the icon; `favicon-96.png` and `apple-touch-icon.png` are rasterized from it), `og-image.png` (1200×630 social card, rendered by `tools/ogcard.swift` — edit the script and rerun it, don't touch the PNG directly), `404.html` (the not-found page — self-contained, every URL on it root-absolute, since Pages serves it at whatever missing address was asked), `site.webmanifest`, `robots.txt`, `CNAME` (oddworldmap.com).
  - Regenerate the icon PNGs from the SVG if the icon changes (a CoreGraphics Swift script was used; any SVG rasterizer works).
- `backlog/`: **hand-curated** (like `annotations.json` and `glossary_fields.json` — nothing generates it), holding plans, review findings and their outcomes in stable `item-NNN-slug.md` files.
  - Read [backlog/README.md](backlog/README.md) before filing or changing one: an existing id and path never change, its status and index bullet move together, and that README owns the body, provenance and reference rules rather than duplicating them here.

## Build & verify

- The Pages deploy is the last job of [.github/workflows/ci.yml](.github/workflows/ci.yml) and `needs` every check job in it, so a push to `main` publishes only what passed and the site waits on the browser suite; a check that lands in a workflow of its own would gate nothing.
- `npm run lint` — ESLint over the viewer modules, `public/sw.js` and `tests/`, each with its own globals; `tools/` is ignored except `tools/levelpages.js`, its one Node file. CI runs it on every push to `main` and on every pull request. There is no JS build step: the modules are served as-is, so lint is the only static pre-runtime check — the browser suite is what runs them before a visitor does.
- `python3 -m compileall -q tools/` and `pipx run ruff==0.16.0 check tools/` — the builder's static checks; CI runs both on 3.12.
  - The ruff version is pinned exactly, like Prettier's, because which rules fire moves between releases; run it locally the same way or a clean tree can still fail CI.
  - `ruff.toml` selects the defect rules alone (undefined names, unused imports, f-string and syntax errors), not ruff's default set, which fights the parsers' deliberate compactness.
  - The supported floor is 3.8, which CI cannot exercise (EOL, absent from current runner images), so 3.9+ syntax would only surface locally.
- `python3 -m unittest discover -s tools/tests` — stdlib-only tests for the builder's pure functions (chunk walking, the LZ variant, `object_fields`' payload clamp, the label/comment/brace helpers), plus reproducibility tests that re-emit the committed `field_types_*`/`enum_labels_*`/`relive_export_*` sidecars into a temp dir and compare bytes.
- `python3 tools/relive_export.py`, `tools/relive_verify.py` and `tools/relive_diff.py` — every path as the level editor's JSON, each document run through relive_api's own reader, and the structural diff against a reference export; how to run them and what each proves are in [docs/relive.md](docs/relive.md).
- `npm test` — `node --test` unit tests under `tests/unit/` for the DOM-free modules (`imports.test.js` holds the list): geometry transforms, TLV destinations, entry paths, permalink format, settings sanitizing, plus schema checks over the shipped data files.
  - Those modules must stay importable in bare Node — no `window`/`document` at module top level (imports.test.js enforces this; `settings` additionally keeps its localStorage access inside guarded calls).
  - The viewer's import graph runs one way, DOM-bound modules included, and `imports.test.js` reads it off the import statements, failing on a cycle with its modules named in order. A cycle between ES modules links and runs without complaint for as long as no module reads an imported binding mid-evaluation, so nothing else notices one forming; where two modules want each other, one side announces through a window event instead (`selection-changed`, `reveal-field-type`). The sweep also requires `main.js` to reach every module, which is what shows it read the whole graph, so a module nothing imports fails it as well. The same reading fails `model.js` reaching `state.js` by any chain, and names the chain: a model call answers for the layout and the place it is handed, never for the layout or selection that happens to be live. The display filter is the one live input it keeps: `snapTarget` asks `markerShown` and `PENS.on` the way the painter and the hover test do.
- `npm run test:browser` — Playwright (`tests/browser/`) drives the served site headlessly against `python3 -m http.server`, Chromium only; `@playwright/test` is pinned exactly (the browser build decides raster output — the Prettier/oxipng rule), so run `npx playwright install chromium` once after `npm ci`.
- `python3 tools/build_map.py --game AO|AE --disc <image.bin ...>` — AE takes both discs; env fallbacks are `$ODDWORLD_DISC_AO` / `$ODDWORLD_DISC_AE` (2352-byte-sector raw images).

## Traps that reach every area

- The viewer ships as ES modules with no build step, so a browser can run a **half-stale module graph**: one cached module beside a fresh one links without error as long as the names it imports still exist, then misbehaves silently and convincingly. A viewer bug the tests cannot reproduce is this until proven otherwise.
  - The tell is the server handing out the change while the running page misses it. A reload need not settle it, nor re-fetching the modules by hand; the reliable read is a fresh origin, which is `127.0.0.1` where the dev server was `localhost` or the other way round, since neither carries the other's HTTP cache or worker.

## Format gotchas (hard-won)

- Both games address cameras on a grid coarser than the screen, and in both the visible screen is a **368×240 window of world units** inside the cell, world units being PS1 screen pixels and the artwork 1:1 with them. AO's cell is 1024×480 with the window at +256/+120 (camera centers at `cell*1024+440`, `cell*480+240`); AE's is 375×260 with the window at +0/+0. The viewer gets all of this from the `geometry` object in each data file, so never hardcode per-game numbers in drawing code.
  - The authorities are `Map::Get_Camera_World_Rect_481410` (AE, which states the 368×240 box outright) and AO's `Rect_Location_Relative_To_Active_Camera_4448C0`, whose ±184/±120 test around the camera center is the same box. **Do not read AO's own `Get_Camera_World_Rect_444C30` as the window**: it returns a 640-wide box, which is the PC screen width leaking into PSX-space coordinates.
  - Everything outside the window is addressing slack the game never renders and the player never occupies: a camera change teleports the character across it, preserving the within-cell offset (`VOnPathTransition_401470` in AO, `vOnPathTransition_408320` in AE). Level authors still parked objects and ran collision lines through it, so the packed layout draws those over a neighbouring screen, which is what `offScreen` marks.
  - `cellW`/`cellH` are the pitch screens are drawn at, not a scale: a screen's interior is always 1:1, and the pitch being narrower than the cell is what folds the slack away. Giving `visW`/`visH` the whole cell rather than the window is what turns that pitch into a squash, dragging every object and collision line toward its screen's top-left corner by an error that grows with the distance from it.
- PS1 cam images are 12 MDEC strips: `u16` length prefix + BS v3 frames in AO, `u32` prefix + BS v2 in AE; `cam2rgba` auto-detects the framing. Decoded strips assemble to 384×240 but only 368 columns are real (macroblock padding, cropped at build time).
- FG1 foreground blocks: on the discs a partial chunk carries its own RGB555 pixels in **both** games, and every Exoddus block sits inside an LZ-compressed sub-stream — 798 of its 802 cameras carrying FG1 open one and not one block lives outside one, where 332 of Oddysee's 340 open one; `decode_fg1` reads a block at either depth.
  - The per-row `u32` bitmask form, and "Exoddus never compresses", are **PC** facts. relive encodes the second as an outright `ALIVE_FATAL` on meeting `eStartCompressedData` in AE mode, which is the assert a PlayStation cam of either game dies on, `CamConverter` reading them all as Exoddus; the builder reading the first cost Exoddus 97% of its foreground until it was measured.
  - `decode_fg1` reports whether it walked clean and the build prints a line per FG1 stream where it did not. A bail at any depth counts, since the outer stream reaching its own end marker says nothing about a sub-stream abandoned inside it, and losing the stride only ever showed up as a thinner mask — which looks like a screen with little foreground on it rather than like a bug.
- TLV records: 0x18-byte header with payload at +0x18 in AO; 0x10-byte header with payload at +0x10 in AE. Door numbers are only unique **per camera** — a target door must be resolved inside the destination camera or same-screen door pairs cross-wire.
- TLV type ids are per-game (Door is 6 in AO, 5 in AE; numbers overlap with unrelated types). Match objects by `name` in shared code, never by numeric id — except wells, whose names also differ per game (AO `WellLocal`, AE `LocalWell`) and whose arrivals can be either well type: well pairs match by the `well#` field alone, camera-bounded like the engine's arrival scan.
- An express well carries two destinations, one for each state of the switch it answers to (`disabled_well_*` / `enabled_well_*`, reaching the viewer as `to_*` / `alt_*`).
  - Either state can be a dead end, and a dead end is written two ways: naming the well's own id, so you drop back out of the well you entered, or left unpointed at the address the fields were born with.
  - `destOf` therefore prefers the state that *lands on another object* over the one that merely differs from the current path, since a dead end always differs. A state naming the well's own camera is a ride like any other when another well answers to it (the Slig Barracks hub pairs 6↔1, 5↔2, 8↔4, 7↔3 within one screen), and a bounce-back only when nothing but the well itself does.
- A destination whose level field was never set reads as level 1 (AE: Necrum Mines) while its path and camera keep the values that were right for a link inside its own level, so the triple looks plausible — 61 AE links name the Mines from another level and not one of them means it (23 naming `MI P0`, 28 the opening screen).
  - `destTrusted` ([js/model.js](public/js/model.js)) believes a destination only where the partner it names is there to be found, and gates the follow, the tooltip's destination lines, the arrow stubs and `computeEntryPaths` alike.
  - A link naming no partner (`PathTransition`) has nothing to check and stays trusted wherever it points — that is what lets AO's two main-menu links follow into `S1`, whose grid the decomp does not tabulate.
  - `wayThrough` composes the two with the one guard everything reading the level graph needs: a hand stone's view is not a way through. `destOf` mints a destination out of `view1_*` and a view names no partner, so `destTrusted` believes it wherever it points, and a sight left in can elect a level's entrance or make the room it shows reachable. No view survives into consequence on either game's shipped data — not because the predicates filter them out, but because every one that passes all three then names the path it already sits on, which each caller drops for its own reason. That is why the guard has to live in one place: nothing in the sweeps fails when a caller forgets it, and `map-data.test.js`'s own cross-level walk omits it to this day with no consequence. Whether the path a destination names is one the map holds stays the caller's question, since the connection stubs deliberately label an off-path destination the level graph drops.
  - No destination in either game now names a level the map does not render, so the tooltip's off-map clause is unexercised by the shipped data and kept for the subset build that reaches it: a `--levels` tree still holds links naming no partner that point out of it, and the clause is what stops one promising a follow into nothing.
  - The partner check is cross-level only: `resolveTarget` is camera-bounded with a path-wide fallback, so within a level an unresolved partner is that strictness rather than bad data, and dozens of sound same-level follows depend on it.
  - A partner *is* found when nothing at all was set — level 1, path 1, camera 1, pair id 0 is a real screen holding a placeholder numbered 0 — so `targetAt` reads that whole address as the absence it is.
  - Key it on the level id, never on the pair number alone: AO's Monsaic Lines wells ride to `D1 P1 C1` and `F1 P1 C1`, the Paramonia one arrival well 0 and all, and are genuine.
  - Both the entry sets (AO 18 slots, AE 14) and the cross-level follows (AO 19, AE 12 — every crossing the shipped data can follow, which is one short of the games' own: Necrum Vaults to FeeCo Terminal 1 happens in a cutscene and no well pairs for it) are pinned in `tests/unit/map-data.test.js`; the phantoms used to badge four real Mines paths as entry points and to send 26 wells to the Mines from across Exoddus.
  - One probably-genuine link pays for the rule, and shows one-way rather than not at all: `BR P10`'s `Door@500,860` names `MI P24`, an address that read inside the Brewery lands on `BR P24`'s `door# 10`, which points back at it. It is the only link in either game a local re-read would recover, it never followed before the check either, and the `BR P24` side still does — so leave it.
- A BirdPortal's destination words are live only when its `portal_type` is travel: a worker (rescue) or shrykull portal dies where it stands and never changes the map, so its level/path/camera fields are dead data — in Exoddus near-universally the unedited 1/1/1 default, which would read as a link to Necrum Mines P1 C1; in Oddysee all but one zeroed, which would read as the menu level `S1`.
  - Both `tlv_extra_{ao,ae}` withhold `to_*` for non-travel portals; the raw words still reach `fields`.
  - The same trap points the other way for the Shrykull countdown: every portal ships `mudokon_amount_for_shrykull`, near-universally at the unedited 1, and only a shrykull portal ever reads it, so `LIVE_WHEN` in [js/fields.js](public/js/fields.js) gates it on the portal's own kind.
- A TLV carries two decoded buckets. `extra` holds *derived, semantic* fields the viewer's navigation logic reads directly (`to_level`/`to_path`/`to_cam`, `door#`, `well#`, `portal`, `view*_*`, …) — hand-written per type in `tlv_extra_{ao,ae}`, since resolving level ids and pairing doors/wells isn't a raw dump.
  - `fields` holds the *complete raw archive* (every field, s16, dev name) for gameplay types, schema-driven.
  - The display writes both, so a key in both buckets prints its value twice — where the archive grows to cover a word `extra` hand-decodes under the same name, `extra` gives it up (AE's express wells did, for `switch_id`); a twin under a different name is a naming question, not a duplicate (AO's `trigger_id`, the wells' `well#`). A test pins that no object names one key twice.
  - `model.js` reads only `extra`; the field display (`extrasText` in [js/util.js](public/js/util.js), over `fieldEntries` from `js/fields.js`) shows `extra` always plus the `fields` a user's `fieldPrefs` admit, prettifying enums viewer-side.
  - `fields.js` `visibleFields()` is the single indirection: "default", "show more" and the per-type picker (`js/fieldpanel.js`, writing the per-game `fieldPrefs.byType`) are just which set it returns. Search is the exception: it asks for `"all"` and gets that string back rather than a set, which `fieldEntries` special-cases.
  - Two value rules sit under that policy, both applying however a field was admitted: `HIDE_WHEN_ZERO` drops a field whose 0 means absent (an unwired switch id, a flag nothing set), and `LIVE_WHEN` drops one the engine reads only when a sibling field says so, which the value alone can never tell you. A gate has to open on some shipped placements and close on others in each game that places the field, pinned in `tests/unit/fields.test.js` — a rule nothing satisfies hides its field everywhere, and a predicate naming a sibling the type doesn't carry reads the same.
- A message table's strings are 4-byte aligned, so splitting its blob on NUL mints a phantom empty entry per padded string and every id after the first lands wrong. Only the pointer array gives the index, and it is also where the table's empty entries live: they all point at one shared empty string rather than occupying the blob.
- Exoddus disc 1 ships `TL.LVL` as a 68-byte boot-config stub, not a LVL archive; the builder skips it. Archive reads are guarded (EOF raises, directories must fit their file) because a garbage header otherwise spins disc reads forever at end of image.
- Both Exoddus discs list every level, but each disc carries full content only for its half — the other half are stubs with path data and no cam files. Always pick the largest copy of a level across discs (the builder does).
- AE "ender" levels are the endgame revisits of areas the player returns to finish (the two vaults, FeeCo Depot, Slig Barracks, Bonewerkz) — same map geography, a distinct level id, the game's own term. The Brewery Ender (id 10, the Game Ender in the game's own level select) wears the term but is its own archive, `BM.LVL`, listed as the level `BM` and carrying no `section`.
  - The five reuse their base level's archive and the table parser deduplicates them into it, keyed on the level short, so each LVL file appears once in the level list, but TLV destinations still name the ender ids — the builder's id→short map must cover every id, not just the kept ones.
- Exoddus ships 25 paths that only its attract-mode demos play — copies of a real area, unreachable however you play — and holding a `DemoSpawnPoint` TLV is the whole rule for spotting one ([js/demo.js](public/js/demo.js), memoized per path; AO has no such type, so the rule degrades to "no demos" there with no per-game case).
  - The `showDemoPaths` setting hides them from the path buttons and from search (whose summary counts what it dropped).
  - What is listed is [js/pathvisible.js](public/js/pathvisible.js) — the setting and the session reveal — kept apart from the rule so `demo.js` imports nothing. That is what lets `model.js` leave demo copies out of `levelWiring` without the geometry core depending on a setting. With the two in one module, asking the rule would import `settings.js`, and `settings.js` imports `parseHash` from `model.js`: an import cycle.
  - Nothing arrives at one and no level opens on one, both pinned in `tests/unit/map-data.test.js`, so the entry marks and the connection arrows need no demo case of their own.
  - **The path in hand is always listed**: `selectPathById` reveals a hidden path for the session, which is what lets a permalink, a remembered location or a follow land instead of falling back, and is why switching the setting off leaves the path you are standing on visible.
  - That a path is a copy is written into its curated name (`[Demo] …`, test-enforced) rather than composed on at display time, so no caller has to pair a name with a marker.

## Conventions

- One concern per commit; split bundled diffs before committing.
- Everything committed reads as its final state, written once — code comments, docs, backlog items, commit messages and the shape of history alike. A follow-up that reshapes something still unpushed folds into the commit that introduced it, message rewritten to describe only what ships, rather than landing as an add-then-amend pair; narration of rounds, actors and supersessions belongs in no committed text. The test: would it read the same if one author had written it in one sitting?
- A fixup commit names the commit that introduced the text it corrects, and may sit anywhere on the branch: `--autosquash` reorders it into place. Retargeting it at a nearer commit to dodge a conflict is the one move to refuse, since that folds a correction into a commit which never carried the text. A fixup hoisted past later commits that touched the same lines can conflict, and resolving that is ordinary work rather than a reason to reshape the branch. After any history rewrite, diff the old head against the new (only the intended change may appear) and dry-run the autosquash on a throwaway branch before handing the branch over.
- Prose files (README, docs, this file) are never manually line-wrapped — let lines run long.
- A user-facing change ships its docs in the same commit — update the relevant README.md / CLAUDE.md, and add its `changelog.json` entry. Documenting the change is part of the same concern, not a follow-up commit.
- Changelog entries are curated, not generated: draft with `tools/changelog.py`, then rewrite into a player-facing headline + detail. The feed is a date-stamped journal of the site, not a highlights reel — any user-visible change, however small, is welcome on it; what stays out is internal work players can't perceive (refactors, tooling, CI).
- No game owns unsuffixed defaults: everything game-specific carries `ao`/`ae` in its name (files, JS globals, env vars, URL hashes). Do not reintroduce unsuffixed names for AO just because it came first.
- Generated JSON is pretty-printed (`indent=1`) so history stays diffable; keep the format stable.
- Prettier owns js/css/html formatting (`.prettierrc`: printWidth 100, defaults otherwise; exemptions in `.prettierignore` — `public/js/config.js` keeps its hand-aligned tables, `public/levels/` keeps the emitter's bytes, JSON and Markdown keep their own formats).
  - The version is pinned exactly in devDependencies because output is version-dependent (like oxipng for the PNGs); bump it deliberately: upgrade, reformat the tree in a dedicated commit, and add that commit to `.git-blame-ignore-revs`.
  - New clones opt blame in once with `git config blame.ignoreRevsFile .git-blame-ignore-revs` (GitHub reads the file automatically).
- Format only the staged files before each commit, so the commit doesn't drag in formatter drift from unrelated files:
  ```
  git diff --cached --name-only --diff-filter=ACMR | grep -E '\.(js|css|html)$' | xargs -r npx prettier --write
  ```
  then re-stage what Prettier changed. Never run whole-tree `npm run format` as part of a normal commit — whole-tree formatting belongs in its own dedicated commit (CI runs `format:check`, so drift can't accumulate).

### Stylesheet vocabulary

[css/main.css](public/css/main.css) has one shared vocabulary and a new surface reaches for it rather than restating a treatment. A value becomes a `:root` token when components that are otherwise unalike have to agree on it; a treatment that recurs whole becomes a class; a repetition that is only two numbers coinciding is left alone.

- **Controls inherit the page font.** Browsers hand `button`/`input`/`select`/`textarea` a font of their own, so a reset beside the `*` rule gives them the page's, and no rule below it has to name a family to undo that — the three that do name one are asking for something (`--serif` for the What's New masthead and its dates, `inherit` on `kbd` to escape the UA's monospace).
  - Reach for `font-family`, never the `font:` shorthand, which also resets size, weight and line-height — measured, that takes the level and path buttons from 12px to 13px and the close glyph's box from 18x24 to 12x19.
  - `font-family` alone still costs one pixel of height on the 11px controls (the search scope buttons and the search results' "show more" rows), where the page font's normal line-height is a pixel taller than the UA font's.
- **Colour and depth are tokens; size is not.** `--over-rgb` is the one near-black everything floating over the map is tinted from, each surface picking its own alpha over it, `--surface-float` the opaque tier of it the tooltips and the floating panels share, and `--shadow-float` / `--shadow-modal` the two elevations.
  - `--dim` is the last step down in text colour and there is no token below it: something needing to sit under dim fades what it has (`opacity`, as the path buttons' nickname does) rather than minting a fainter grey, and takes the rest of the separation in size, a lever that costs no contrast at all. The tooltip's offscreen note is the deep end of that, faded past the contrast ordinary text keeps — which it can afford only because it restates what the marker's dotted outline and the screen list's `offscreen` tag already say, so a reader who cannot make it out is told anyway.
  - Radii and paddings are deliberately left alone — a scale over 5/6/8px would buy indirection rather than agreement, since nothing breaks when two components pick different ones.
  - `--corner-w` is what the rule's own exception looks like: the room the map's top-right buttons need, which the place chip and the world graph's bar both have to leave them. Something does break when those two disagree — the bar's own controls land under buttons that are painted above it, unclickable.
- **Stacking tiers** are the `--z-*` tokens in `:root`, declared low to high so the block's own order states a system nothing else in the repo did. A surface takes a tier from there rather than writing a bare `z-index`, and `--z-map-chrome` sits above `--z-drawer` because it has to beat the drawer it opens over.
  - `--z-tip` is directly above the map overlays because a hover tooltip is the affordance the pointer is actively producing and must not be clipped by a surface that is merely present; `pointer-events: none` is what makes that safe, since nothing underneath loses a click.
  - Do not try to solve that with `#cv`'s `pointerleave`, which fires only while the *cursor* is inside an overlay: the tooltip's box sits 16px down and right of the cursor and can be 340px wide, so it reaches onto the map overlays from outside them.
  - It stays *below* `--z-map-chrome` and the corner buttons do still cover it: a flat scale cannot put the tooltip over chrome while keeping it under the drawer chrome exists to beat, and being covered by a corner button is the better of the two failures.
- **A dialog** is `.overlay` wrapping `.dialog`, holding `.dlg-head` / `.dlg-body` / `.closebtn` (worn outside the dialogs too, at the class's size or one the surface sets), with `openDialog`/`closeDialog` toggling `.open` on the overlay.
  - The state is on the element rather than on `body` precisely so the stylesheet never names a dialog — another costs no CSS at all unless its width differs from the fallback in `width: var(--dialog-w, 460px)`, written as a fallback rather than a declaration so the token doesn't inherit into every descendant.
  - The reduced-motion group has to name `.overlay.open` beside `.overlay`, because the open state carries a transition that one class cannot outrank.
- **`.linkbtn`** is the shared treatment for a no-chrome underlined text button.
  - It declares no font, deliberately — size is left to the surface (11px in the footer, 12px in the route bar, the heading's own for a heading tool, the UA default in the graph bar), and a `font:` shorthand on the class would reset the weight and line-height of every member that sets no font of its own, while the ones declaring `font: inherit` would not feel it at all.
  - Hover is guarded with `:not(:disabled)` for the members that disable themselves, a disabled one staying dim under the pointer; `:focus-visible` takes the same accent, for every member.
- **`.actbtn`** is the sidebar's full-width action button, the bordered pill spanning the column that the world graph, the edit mode, the numbers panel and the exports open from, worn by the export disclosure's `<summary>` as well as by buttons. It names `line-height: normal`, the one thing a summary does not share with a button, so the pill stands the same height on either. Hover is guarded with `:not(:disabled)` and a disabled member dims, since the exports disable themselves while they run; `#graphBtn.on` and `#editBtn[aria-pressed="true"]` are the states written on an id, each that button's alone.
- **`.rowbtn` and `.listhead`** are the full-width row that behaves as a button, with its hover and `.active` states, and the small uppercase divider above a list's rows; a surface takes both or the divider alone. Each is added alongside the component's own class (`rowbtn cp-row`, `listhead shead`), so what is shared and what is local stay legible in the markup.
- **`.checkrow`** is a checkbox and its wording on one line, wherever one is offered.
  - Selection is suppressed on the class rather than per surface — a label you click repeatedly should not select its wording anywhere — while padding stays per-surface, which is what keeps the narrow query's fatter touch targets on the sidebar surfaces and off the dialog's rows.
- **`.sr-only`** is the clip that takes an element out of the layout and leaves it in the accessibility tree, worn by anything with something to say and nothing to show. `display: none` and `visibility: hidden` both take an element out of that tree, so a region hidden either way announces nothing while the page looks exactly right — which is why the recipe is a clip and why it sits with the resets rather than with a component, having none of its own.

### Code comments

- **Default to no comment**: A comment earns its place only by recording a durable *why* the code can't show: an invariant, a constraint, a non-obvious trade-off.
  - Keep them generic enough that a routine change doesn't force a comment edit — put a per-item note *inline on the item* (`"deaf", // ignores Abe's speech`), never in a const-doc that re-describes the set's members (that rots the moment you add one).
  - Don't name consumers or other modules ("used by X", "the picker reads this"); don't restate a constant's value or units.
  - Comment footprint matches code footprint — a concern touched at one line gets one comment there, not a header paragraph.
  - Before committing, reread each comment and cut any that restates the code, names something that could be renamed, or would lie after a tune/refactor — an absent comment never goes stale.
- **No inter-diff comments**: Comments must describe the code as it is now, not how it got here. Don't write "extracted from X", "moved from Y", "duplicated here", "was previously in Z". A reader who has never seen the git history should find every comment meaningful.
- **Peer items get peer prose**: When a comment or code block enumerates parallel items — payload fields, switch cases, sibling merge loops — treat them uniformly.
  - Don't attach a justifying clause to one item ("…and seen marks (s) — without these, restored unlocks would re-badge as new") while its siblings carry none: the asymmetry falsely flags that item as special, and the odd one out is invariably the one just added — meaning the sentence is a diff justification aimed at the reviewer, not a description aimed at the reader.
  - Same for code shape: when the sibling loops above yours are uncommented, the new one doesn't get an explainer either.
  - The why-this-was-added story belongs in the commit message in short form.
  - Test: would the prose look the same if every item had been written on the same day, by one author? If your addition carries a defense its peers lack, delete the defense.
