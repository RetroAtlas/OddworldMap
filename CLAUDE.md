# CLAUDE.md

Guidance for AI agents working in this repo. User-facing docs (controls, rebuild instructions, format overview) live in [README.md](README.md) — read that first; this file covers what is not obvious from the code and the traps that cost hours to find.

## Source vs generated

- Source: the viewer, under `public/` (the deploy artifact — everything in it is served, nothing outside it is) — `index.html`, `css/main.css` and the ES modules under `js/` (dependency-free vanilla JS, no build step; `js/main.js` is the boot entry, `js/state.js` holds shared state + world→draw transforms, and selection announces itself via a `selection-changed` window event so modules stay one-directional) — plus `annotations.json` and the builder: `tools/build_map.py` is the CLI and the build loop, `tools/oddmap/` the package under it (one module per concern, with a one-way import graph), beside `tools/cam2rgba.cpp` and the vendored `PSXMDECDecoder.*` / `Types.hpp`.
- `annotations.json`: hand-curated names/notes the discs don't provide
  - A curated name deliberately overrides the in-game one but must contain it — refine, don't erase, test-enforced. A `name` is what the game itself calls the place (AO R2's zulags, from the save slots), which is what an override has to answer to.
  - A `section` is the builder's label rather than this file's: which half of a level the path belongs to, the AE ender display name stamped on the paths only the ender id leads to, so it sits beside the curated name rather than inside it.
  - A `nickname` is what players call a place, where the map has adopted their name for it. It stands outside the override rule, the way a `section` does: it is not the curated name, so it has nothing to refine. Keep it out of `name` as well, where a curated colon already means a sub-path of a multi-path zulag — `Zulag 10: Slig High Security` would assert a division that does not exist. It renders dimmed, taking a `·` where a name takes `—`, and only reaches the button face with "Show full names" on; below that, on the button, the tooltip is its only carrier.
  - A path entry is a bare name string or `{name?, note?, nickname?}`, so only the paths with something extra to say expand and any one of the three stands alone.
  - `sanitizeAnnotations` collapses the union, so callers only ever see the object; it is an allowlist copy that names the three keys, so a new one it does not spread is dropped silently.
  - A note is ordinary prose, capitalized and punctuated, reaching the reader through the place panel; a nickname is the opposite, a title-case label that never closes punctuated. Both shapes are test-enforced.
  - A name the map coins itself is not a nickname and belongs in `name` (`Zulag 9: Fleech Ledge`, `Brewery Terminal`).
  - Adopting a nickname needs an entry in `tests/unit/annotations.test.js`'s `CLAIMS` table, which is keyed to exactly the nicknamed paths: a predicate over the shipped data for the fit the name claims (zulag 3 holds more drills than any other area), or the reason written down where the evidence is artwork nothing can count.
- `glossary_fields.json`: **hand-curated** (like `annotations.json`, not generated) plain-English field meanings, one game-agnostic file.
  - Three resolution tiers, most-specific first: `byType` (`"ObjectType.field"`), `byGameType` (a field's decomp game type, e.g. `Path_Slig::StartState` — the group of object types sharing that field's meaning, the same key `enum_labels` uses), `byField` (a global by name).
  - Loaded at boot (`setGlossary` in [js/glossary.js](public/js/glossary.js)); [js/fields.js](public/js/fields.js)'s `fieldHelp(game, type, field)` composes the prose with the field's full value list (from `TRANSFORM`/`enum_labels`) for the picker and screen-list definitions, handed over as a `data-tip` attribute on the field name ([js/anchortip.js](public/js/anchortip.js)).
  - Every shipped field resolves a def, pinned by test — a rebuild that surfaces a new field fails the suite until the glossary covers it — and every key is cross-checked against the shipped data so a typo can't ship. A field the engine never reads says so plainly; the graceful no-def path stays for a missing or garbage file.
  - Adding a definition is one JSON line in the tier that fits; defs are style-checked like the notes and never enumerate values — `fieldHelp` appends the value list itself.
  - A `units` section repeats the same three tiers, giving a bare-int field the unit its value is measured in. The entry is a word rather than prose, resolved by `fieldUnit` and rendered by `UNITS` in [js/fields.js](public/js/fields.js). The section sits in this file rather than a sidecar so a unit cannot drift from the sentence asserting it: `field_types` is derived from the decomp alone and carries enum-typed fields only, and a unit is curation.
    - The vocabulary is closed and the renderer owns it: a unit `UNITS` has no formatter for leaves the value raw, so the closed set is pinned by test rather than guarded in `sanitizeGlossary`.
    - `prettify` asks for a unit only after the label layer misses, so an enum's words can never be displaced by one.
    - `frames` is the only derived reading, `LOGIC_FPS` in [js/config.js](public/js/config.js) being the engine's own clock rather than a measured rate: `ColourfulMeter` multiplies the one field relive_api labels `(Seconds)` by 30, `MinesAlarm` ticks a sound every thirtieth decrement, and both games' gas countdowns divide the global frame counter by 30 for a visible on-screen clock, that counter advancing once per main-loop pass. `fieldHelp` states the factor, being the one unit that owes the reader one.
    - Speeds stay raw and untouched: each carries its own scaling (256ths of a unit per frame, hundredths, whole world units) where this layer's vocabulary is one word per field, and a Drill's exact 250 is special-cased by the engine. Their defs already state the scaling.
- `glossary_types.json`: **hand-curated** (like `annotations.json` and `glossary_fields.json`) — the type encyclopedia, one plain-English paragraph per object type name under a `types` section, game-agnostic; where the two games' copies behave differently, the prose says so in words.
  - The first sentence is the summary and stands alone: the hover tooltip carries it under the object's name ([js/typeinfo.js](public/js/typeinfo.js)'s `typeSummary`), while the card shows the whole paragraph. Write entries summary-first, and keep engine claims to what the decomp confirms — the curation bar is the nicknames': describe what the shipped data and the games show.
  - A count or placement stated in prose follows the map's own counting rule — listed paths, demo copies excluded — so an entry never disagrees with the census line on its own card, and each such claim is pinned in `tests/unit/typeinfo.test.js`'s `CLAIMS` table at the scope the prose uses (a universal over the raw data pins at that scope instead).
  - The card ([js/typecard.js](public/js/typecard.js), a `.overlay` dialog) composes the paragraph with live `census()` placement counts (never hand-written — the demo footnote says what the count leaves out) and the type's glossary field defs; any surface opens it by dispatching the `typecard-open` window event, so none imports the module.
  - Style and coverage are test-enforced (`tests/unit/typeinfo.test.js`): entries read as prose, the first sentence fits a tooltip line, and the keys are exactly the shipped type set — a rebuild that surfaces a new type fails the suite until the encyclopedia covers it.
- Generated **and committed** (they are the site's data, under `public/` like the rest of it): `map_data_ao.json`, `map_data_ae.json`, `cams/ao/**`, `cams/ae/**`. Regenerate with the builder from disc images; never hand-edit.
- `field_types_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each object type to its enum-typed fields' game types (`{"Slig": {"start_state": "Path_Slig::StartState", …}}`).
  - Derived from the decomp alone (no disc) via `build_map.py --emit-field-data`, and re-emitted on every normal build so it stays in sync.
  - The viewer loads it at boot (`setFieldTypes` in [js/fields.js](public/js/fields.js)) and keys value transforms by a field's game type — a value's text written once per type and shared across every object that carries it (Slig/SligSpawner/SligGetPants all share `Path_Slig::StartState`) while an unrelated same-named field stays separate (a Door's `start_state` is `DoorStates`, its own key).
  - Only enum/Choice/Scale fields appear; bare-int fields carry no type.
  - A small `_FIELD_TYPE_OVERRIDES` table applies at emission, giving a field the type it behaves as where the decomp declares one that contradicts its meaning. The schema cache stays faithful to the source either way, and why each entry exists is on the entry. Each entry is keyed to the type the schema derives today (`None` for a bare word), like a layout correction, so an entry naming a field the schema no longer carries, one whose derived type moved, or one the schema now types as the entry says all fail the build; an override type is counted as used when labels are emitted, so it can never ship unlabelled.
  - Correct such quirks here in the builder, never by patching the local `alive_reversing` checkout — a patch would make the emit unreproducible from a clean tree; fixing it upstream and re-pinning is the path to retiring an override.
- `enum_labels_{ao,ae}.json`: generated **and committed** viewer sidecar mapping each enum game type to its `{value: text}` labels (`{"DoorStates": {"0": "open", "1": "closed", …}}`), so enum fields render as words without the viewer hand-maintaining them.
  - Generated by `parse_enum_labels` (`--emit-field-data`, no disc) from the decomp's enum definitions (authoritative values, explicit `= N` or positional) and its `AddEnum` blocks (curated labels, else a label derived from the enumerator name); labels are lowercased to the viewer's style, keyed to line up with `field_types`, and limited to the types some field is actually declared as (the decomp defines many enums that aren't fields).
  - The sweep's whole result is cached in `tools/data/enums_{ao,ae}.json` under the pathdata/objects discipline (re-parsed only when deleted), so the emit — and CI's byte-comparison of the committed sidecars — runs from the committed tree alone. It caches every swept type, not just the used ones, so an override or schema edit never needs the checkout to re-emit; regenerating does, and a checkout missing a swept tree fails rather than sweeping thinner. What is cached is the parse's finished output, so an edit to the label code itself (`_derive_label`, `_VALUE_TYPES`, the curation regex) stales the cache the way an upstream re-pin does — delete it and regenerate; the freshness test is what tells, and CI runs it against a clone of the pinned revision, so a stale cache cannot ship unnoticed.
  - Per game — the same type's values can differ (Slig `start_state` 5 is `falling to chase` in AO, `unused` in AE).
  - The basic value-types (`Choice`/`Scale`) are **excluded**: the viewer owns those semantic transforms (bool, full/half) in `js/fields.js`'s `TRANSFORM`, and a hand transform there wins over a generated label; direction enums are generated like any other (left/right).
  - Definitions are swept from the game's whole AliveLib tree plus AliveLibCommon (the include graph can't reach them all — `SwitchOp` is only ever forward-declared where fields use it), with the sibling game's tree as a fill-only fallback for shared types (AO fields use AE's `XDirection_short`).
  - Comments are stripped before parsing — the word "enum" inside one otherwise swallows the definition that follows it, and a comma inside one once minted a phantom enumerator.
  - A bare enum name defined differently in two headers, or an initializer the parser can't value, makes the type unlabelable, and the emit fails loudly if any field actually uses such a type — labels must never ship silently wrong.
- `messages_{ao,ae}.json`: generated **and committed** viewer sidecar holding the game's own message tables, one array per table indexed by the id an object carries (`{"lcd": ["", "The profits justify the means.", …], "hintfly": [...]}`). AO carries both tables; AE has no HintFly.
  - Read **off the discs**, unlike the sidecars derived from the decomp alone, so it is written by a normal build rather than by `--emit-field-data`. The decomp carries both LCD tables in source, but those are the PC build's and differ from PS1's in wording, not only in button names: PSX AO 52 ends "while you run" where PC adds "using [Run]", and PSX AE 73 spells out a two-button combo where PC names a dedicated key.
  - Each table is a pointer array plus a 4-byte-aligned string blob compiled into the **level overlays** (`*.OVL`), not into `SLUS_*`, and duplicated identically into every overlay whose level needs it. `write_messages` extracts every copy and requires them all to agree, so the per-level question is re-answered on each build rather than trusted from one reading.
  - `string_table` anchors on a known string rather than an address, which derives the overlay's load base from the data; it finds the table by the run of gaps between the first strings and believes it only if the slot past its declared end points nowhere, which is what makes the length self-proving.
  - Messages keep the font's button-command code points (0x08-0x13) rather than any name for them: the viewer owns the naming, as it owns the enum transforms. A code outside that set fails the build. The 31-space scroll-in lead every LCD message opens with is stripped at emit.
  - `message_json` writes those codes `\u00XX`, because json's shorthand would put `\n` and `\t` mid-sentence where they read as whitespace; no message contains a backslash, which is what makes the rewrite exact.
- `relive_export_{ao,ae}.json`: generated **and committed** viewer sidecar carrying everything the page needs to build a relive_api document itself — relive's schema and the collision links verbatim from their `tools/data` caches, the payload layouts the archive's field names join through, the pinned export fallbacks, and (Exoddus alone reading them from data rather than a constant) its Abe starts and mud table.
  - The schema, the layouts and Exoddus's tables come from the committed caches, which is why `--emit-field-data` can write it; the links come from the directory the build in hand has just written them to, the cache itself for the site build, so a scratch `--out` build's sidecar carries that build's links. A test compares both halves against the caches they copy: a served copy that drifted would export documents the builder cannot reproduce.
  - `enum_values` repeats the enum tables as ordered arrays because JS reorders an object's integer-like keys, so the order `schema_blob` reads out of `enums` has to be carried rather than inferred — `Enum_LevelIds` opens at `-1` and would otherwise come back last.
  - `level_short` is the builder's whole level-id → short map, every id of it: the served level list keeps one level per archive, so the Exoddus ender ids a destination names (7, 11–14) reach the page only through this key.
  - It is the one sidecar the page does **not** fetch at boot, unless the device holds saved edits for the game, which apply through its level map before the dataset is shown; otherwise nothing reads it until the JSON export button is pressed or edit mode is entered, and Exoddus' is 37 KB gzipped. `loadEditorData` memoizes one fetch per game, and the worker's shell rule takes it like any other root-level JSON, so an export works offline from the first use onward.
- `tools/data/pathdata_ao.json` / `pathdata_ae.json`: cached level/path tables and TLV type enums parsed from the alive_reversing decompilation, used as-is by builds and only re-parsed when the cache file is deleted — which needs an `alive_reversing` checkout: the one `$ODDWORLD_DECOMP` names, else a sibling directory of this repo (`REPO` in [tools/oddmap/paths.py](tools/oddmap/paths.py), which every decomp read resolves through). A set variable is believed outright, so a wrong path fails rather than falling back to the sibling.
  - The checkout is expected at `DECOMP_COMMIT` (beside `AO_COMMIT` in [tools/oddmap/paths.py](tools/oddmap/paths.py)), the revision every cache was parsed from, and README names both, a test holding its wording to the constants.
    - Only AO's path tables come from the older `AO_COMMIT`, through `git show`, so the clone has to hold both commits: a shallow one is refused before any parse, and fails the freshness tests' AO read.
    - Every cache is read and written through `cached` in [tools/oddmap/decomp.py](tools/oddmap/decomp.py), which asks `pinned_checkout` before it parses: a checkout off the pin, lacking `AO_COMMIT`, or carrying anything under `Source/` the pinned tree does not (a tracked edit, a skip-worktree or sparse gap, an untracked file, an ignored header the sweep would still glob) is refused, so a drifted tree cannot reach a cache.
    - The freshness tests compare content and never the revision, so a checkout elsewhere that parses identically passes; their message names both revisions, because the usual cause of a difference is the checkout having moved rather than the cache being wrong, and "delete it to regenerate" would then re-pin shipped field types unnoticed.
    - A re-pin is one commit: move `DECOMP_COMMIT`, delete and regenerate the caches, retire any override or correction the new revision spends, re-emit the sidecars, and run `npm test` as well as the Python suite, the sidecars feeding the Node tests.
  - The decomp tabulates nothing for AO's `S1`, so `discover_path_meta` reads that grid off the path chunk instead: the camera-name table heads the chunk at one 8-byte slot per cell, and the objects behind it choose among the factorisations of that count, since every object has to land inside the grid. Both halves are checked against the levels that *do* have tables — the slot run is each one's `coll_off` exactly, and the factorisation never contradicts a known grid — and it resolves `S1` to 4x10 uniquely.
  - It runs only where the table is empty, so a tabulated level is never guessed at, and it raises rather than guessing when the objects leave more than one factorisation standing. Deriving it at build time rather than hand-writing the numbers into a table is what keeps a plain rebuild reproducing the committed data.
  - A path carrying collision would break the assumption that objects start where the name table ends; `S1` has none, and one that did would fail the grid check rather than decode wrongly.
  - `audit_path_meta` answers the opposite case: a level the decomp *does* tabulate, whose numbers the PS1 chunk contradicts. The tables are the PC build's, and two Oddysee paths differ from it by a collision line — `R1 P20` has one the table does not count, `R6 P6` one it counts that is really the first object record — which slides the object region and puts the index table 20 bytes from where `idx_off` says. The chunk settles it: the table ends the chunk at 4 bytes a cell, its entries are offsets from the object region, and only the true count puts that region where every entry starts a record. It runs on every tabulated path, is silent on 188 of the 190 the discs carry, and raises rather than guessing where no count answers or several do.
    - Everything else the tables carry lands on both builds — 5,625 Oddysee and 10,602 Exoddus object records walk clean — so this is a correction, not a reason to stop believing the tables. The one other PS1/PC divergence measured is `RingCancel`, whose PS1 record is 28 bytes to the decomp struct's 24 (4 payload bytes, zero on all 10 placements); it sits inside the object region, so it moves `idx_off` alone and the walk never notices.
- `tools/data/objects_ao.json` / `objects_ae.json`: cached per-type field layout (`[payload word, snake_case name]` per field, plus a third element — the field's game type — where the decomp declares an enum/Choice/Scale rather than a bare int), parsed from the relive_api CTOR blocks (`Source/Tools/relive_api/Tlvs{AO,AE}.hpp`) by `parse_object_schema`.
  - Same cache discipline as pathdata (re-parsed only when deleted).
  - Drives the generic `object_fields` extractor, which emits every field of a gameplay object (`GAMEPLAY_FIELD_TYPES`) raw into `t.fields` — it reads only word+name, so the type is metadata and `map_data` is byte-identical whether or not types are present.
  - Values are read as s16 and stored raw — which fields to show and how their values render are the viewer's job ([js/fields.js](public/js/fields.js), driven by the `field_types` + `enum_labels` sidecars), so the disc is never needed again to surface or relabel a field.
  - Parser gotcha: the payload word comes from the `field_XX` hex offset in the member name, but the name lies two ways.
  - The decomp sometimes numbers *sequential* members with one offset (Door's 8 hub ids are all `field_22_hubN`); and a member of an intermediate base struct numbers from that struct's own start, so it computes *below* the payload base (`Path_WellBase`'s `field_0_scale`..`field_6_anim_id`, and ContinueZone's sole `field_10_zone_number` — Path_TLV is 0x18 wide, so the name's 0x10 lands in the rect). Both fail to increase the offset, so the one positional rule — take the next word — answers both; a below-base name must not be skipped, or the fields vanish silently with no `raw=` to show for it.
  - `_SCHEMA_LAYOUT_OVERRIDES` is left for what the CTOR genuinely can't express: an empty layout marking a field-less type (AO RingCancel) so it still retires its raw fallback. Because `object_fields` returns a dict for any schema'd type, empty included, a `GAMEPLAY_FIELD_TYPES` object never falls back to a `raw=` dump. An entry naming a type the game doesn't have, or one the parser now derives on its own, fails the build — which is why `game_setup` resolves the schema after `tlv_names`.
  - `_SCHEMA_LAYOUT_CORRECTIONS` is its sibling for a layout the CTOR expresses *wrongly* rather than not at all: the entry replaces the derived layout with the engine's own reading of the payload, and why any one of them exists is stated on the entry. Each is keyed as `(derived, corrected)`, pinned to what the parser yields today, so an upstream fix spends the entry and fails the build loudly instead of double-correcting. A correction reaches the `field_types` sidecar on any `--emit-field-data` run but the names in `map_data` only at a disc rebuild, so the two can disagree until one runs.
  - The field type comes from `parse_member_types`, which parses the data-struct member declarations across `Tlvs{AO,AE}.hpp` and every `AliveLib*` header it includes. Enum leaf names repeat across the decomp (`StartState` is both a Slig enum and a MeatSaw enum), so a nested enum is qualified with its owning struct (`Path_Slig::StartState`).
  - A member a struct inherits resolves through its base chain, the struct's own body winning — the wells' `scale` arrives typed from `Path_WellBase`. A field whose declared type is an aggregate carries no type, an aggregate being no enum; where the CTOR reads an *arm* of one instead (`mTlv.field_10_data.field_18_behavior`), the arm's own declaration is the field's type, so the sweep follows a data struct's sub-structs and unions wherever they are declared — `Slurg_Path_Data` and the wells' `OffLevelOrDx` carry no `Path_` in the name. The arm is what decides, so AO's two wells read one inherited union word differently: an express well's is a level, a local well's a bare offset.
- `tools/data/relive_ao.json` / `relive_ae.json`: cached relive_api schema for the exporter that writes the level editor's JSON, parsed from the same decomp checkout by `parse_relive_schema` ([tools/oddmap/relive.py](tools/oddmap/relive.py)) — per object type the CTOR literal (relive's `object_structures_type`, not always the name `map_data` carries: our `LCD` is relive's `LCDScreen`, our `Switch` its `Lever` — fourteen placed types differ, seven per game) and its properties as relive reads them (display string verbatim, payload word from the data struct's real layout, byte width, registered type name), plus the AddEnum label tables verbatim and the collision-line structure. Same cache discipline as pathdata (re-parsed only when deleted, from the pinned checkout alone).
  - Property words come from computed struct layouts, never from the ADD order, because the two disagree exactly where a member name lies about its offset — `WordAudit` in `tools/tests/test_relive_export.py` pins the full set of such liars, so a new one fails a test instead of shipping wrong words — and a layout correction that answers one spends its entry there.
  - The parse validates every layout it computes against the decomp's own `ALIVE_ASSERT_SIZEOF` lines and raises on any type it cannot width or any enum registration it cannot value, so a thinner sweep fails rather than caching a guess.
- `tools/data/lines_ao.json` / `lines_ae.json`: generated **and committed** collision links, per level and path — the words trailing each line's coordinates and type, which the exporter needs and no viewer surface draws. Written off the disc by a normal build like `messages_*`, and deliberately kept out of `map_data`, the dataset first paint waits for: inlined on the lines they would add 27 KB gzipped to the Exoddus dataset for data nothing on the map reads. They reach the page only through the `relive_export_*` sidecar, fetched on the first export press.
  - A `columns` key names them in the record's own order, `norm()`ed to the display strings relive registers, so the export joins them by name the way it joins a property.
  - The offsets differ per game (`line_links` in [tools/oddmap/games.py](tools/oddmap/games.py)): AO a pair of s32 at 0x0C and 0x10, AE five s16 from 0x0A. A subset build merges into the file the way `map_data` does, and a scratch `--out` takes its own copy rather than the committed one, so a verification build can `cmp` it.
- `levels/**` and `sitemap.xml`: generated **and committed** search-engine surface — one plain HTML page per level plus the `/levels/` index, each deep-linking into the viewer, and the sitemap naming them all. Emitted by `node tools/levelpages.js` (no disc) from `map_data_{ao,ae}.json` + `annotations.json`, reusing the viewer's own bare-Node modules for names, play order and demo exclusion; never hand-edit.
  - Deterministic over its inputs, and `tests/unit/levelpages.test.js` byte-compares the committed files against a fresh emit — so a rebuild or an `annotations.json` edit needs a re-emit in the same commit, and CI fails until it happens.
  - A page's screen is its entry path's first stored camera, unless the emitter's `SCREEN_OVERRIDES` table pins another as the level's face; a pin naming a level or screen the data doesn't hold, a pin on the default pick, or a page screen without artwork all fail the emit rather than standing stale.
  - The pages are content, not redirects: a crawler indexes a redirect's destination with the `#` fragment dropped, so a redirecting stub would collapse into the homepage.
  - They live nested under `levels/` on purpose — an HTML page reaches the worker's shell rule only at the site root, and nothing else that rule matches (the `js/`/`css/` trees, the named icons) lives here — so no level page can enter or displace the shell cache, and the pages stay out of the offline story entirely.
- Static site files that are not the viewer or its data (all in `public/`): `favicon.svg` (source of truth for the icon; `favicon-96.png` and `apple-touch-icon.png` are rasterized from it), `og-image.png` (1200×630 social card, rendered by `tools/ogcard.swift` — edit the script and rerun it, don't touch the PNG directly), `404.html` (the not-found page — self-contained, every URL on it root-absolute, since Pages serves it at whatever missing address was asked), `site.webmanifest`, `robots.txt`, `CNAME` (oddworldmap.com).
  - Regenerate the icon PNGs from the SVG if the icon changes (a CoreGraphics Swift script was used; any SVG rasterizer works).
- `backlog/`: **hand-curated** (like `annotations.json` and `glossary_fields.json` — nothing generates it), holding plans, review findings and their outcomes in stable `item-NNN-slug.md` files.
  - Read [backlog/README.md](backlog/README.md) before filing or changing one: an existing id and path never change, its status and index bullet move together, and that README owns the body, provenance and reference rules rather than duplicating them here.

## Build & verify

- The Pages deploy is the last job of [.github/workflows/ci.yml](.github/workflows/ci.yml) and `needs` every check job in it, so a push to `main` publishes only what passed and the site waits on the browser suite; a check that lands in a workflow of its own would gate nothing.
- `npm run lint` — ESLint over the viewer modules, `public/sw.js` and `tests/`, each with its own globals; `tools/` is ignored except `tools/levelpages.js`, its one Node file. CI runs it on every push to `main` and on every pull request. There is no JS build step: the modules are served as-is, so lint is the only static pre-runtime check — the browser suite is what runs them before a visitor does.
- `python3 -m compileall -q tools/` and `pipx run ruff==0.16.0 check tools/` — the builder's static checks; CI runs both on 3.12.
  - The ruff version is pinned exactly, like Prettier's, because which rules fire moves between releases; run it locally the same way or a clean tree can still fail CI.
  - `ruff.toml` selects the defect rules alone (undefined names, unused imports, f-string and syntax errors), not ruff's default set, which fights the parsers' deliberate compactness.
  - The supported floor is 3.8, which CI cannot exercise (EOL, absent from current runner images), so 3.9+ syntax would only surface locally.
- `python3 -m unittest discover -s tools/tests` — stdlib-only tests for the builder's pure functions (chunk walking, the LZ variant, `object_fields`' payload clamp, the label/comment/brace helpers), plus reproducibility tests that re-emit the committed `field_types_*`/`enum_labels_*`/`relive_export_*` sidecars into a temp dir and compare bytes.
  - No disc image is needed, and the sidecar reproducibility tests run from the committed caches; only the tests that probe the checkout itself (the member-type parser pair and the four cache freshness checks) skip, and only where no checkout is configured or found — `$ODDWORLD_DECOMP` naming a path that holds none fails them instead, a named location being an assertion rather than a hint — and the tests that encode through oxipng skip where none is on PATH, which is every CI run. CI clones the pinned revision into `$ODDWORLD_DECOMP`, reading `DECOMP_COMMIT` and `AO_COMMIT` off `paths.py` and fetching both by SHA, which is what makes the six run in CI; a clone step gone missing fails them rather than skipping, the variable being set either way.
  - A parser reached only through a nested helper (AE's `positional_rows`, the enum body loop) can't be tested until it's hoisted.
- `python3 tools/relive_export.py --all --out <dir>` — every path as relive_api v4 JSON, the AliveTeam level editor's format, from the committed map data and caches alone (no disc, no site change): the cross-check artifact that lets our extraction be diffed against relive_api's own reader.
  - Which camera an object is listed under is the path chunk's own index table to answer, and the games answer it differently: Oddysee places a rect by its top-left corner, Exoddus by its midpoint. Read off the index table over both archives, each rule is exact on its own game's 5,625 and 10,602 objects where the other misplaces 3 and 835: the rects whose corner and midpoint fall in different cells, a subset of those straddling a boundary, mostly zones. `bucket_cells` follows the game's own rule; the viewer's `tlvCell` is a separate question and keeps the corner in both.
  - A property whose value the archive doesn't hold fails the run with a manifest and withholds that path's file — relive's importer *aborts the process* on a missing numeric key, so an incomplete file must never look whole; `--allow-incomplete` writes it anyway, manifest printed the same.
  - `EXPORT_VALUE_FALLBACKS` in [tools/oddmap/relive.py](tools/oddmap/relive.py) carries the words relive reads that the archive doesn't capture, printed on every run and spent loudly once a rebuild archives the word — except MovieHandstone's, the meaningless high half of an s32 the archive drops by design, which stays; `ExportSweep` pins the set, so a new gap fails a test rather than shipping as a silent zero.
  - `python3 tools/relive_verify.py --dump-lvl AO R1 <out.LVL>` writes the LVL the reference exporter is pointed at, its path data the disc's own bytes and its `.CAM` directory names one letter off so relive cannot open a camera. That is not tidiness: `CamConverter` tells an AO cam by the Bits payload's strip sizes, a test no PS1 cam passes, so it reads every PS1 cam's FG1 in AE mode, and that reader `ALIVE_FATAL`s on an LZ-compressed sub-stream, which the discs open in both games. A camera it fails to find costs only the artwork, which the diff never reads; a camera it finds costs the whole document.
  - Known divergences from a reference export of the same path: instance-name counters can order differently, and the reference's schema arrays are unordered_map-ordered on its side, so any diff must compare structurally, never by byte — `tools/relive_diff.py` is that comparison, holding the fallback-filled values and AE's `num_muds_in_path` — the reference indexes the mud table by the path index it was handed, the engine and our export by level id — as counted non-fatal classes.
  - `--digests <file>` writes one canonical-form sha256 per path instead, which is what pins the page's exporter to this one. [js/reliveexport.js](public/js/reliveexport.js) is that port — the same joins over the same caches, reached through the `relive_export_*` sidecar — and neither language can run the other, so both answer to `tests/fixtures/relive-digests.json`: `tools/tests` regenerates and byte-compares it, `tests/unit/reliveexport.test.js` hashes all 191 documents against it. `canonical` is the shared byte form (keys sorted, no whitespace), exact because no value in a document is a float or non-ASCII.
- `python3 tools/relive_verify.py` — the exporter's oracle: exports every path and runs each document through relive_api's **own** JSON reader (`tools/relive_check`, a shim CMake project over the checkout's `Source/Tools/relive_api` directory alone, which is self-contained and SDL-free unlike the decomp's root project), failing on any exception or silently remapped enum label. Needs cmake and the checkout at the pin (`pinned_checkout` refuses any other, and the five submodules the shim compiles against have to sit at their recorded commits); every run re-drives the build into `~/.cache/oddworldmap/relive_check` — a no-op when nothing changed, and a build dir stamped with another revision, or configured from another checkout of this repo, is wiped first, so neither a re-pin nor a second checkout is judged by the old binary — and outside the repo on purpose, since a binary written into a synced working tree can lose its code signature under it and the kernel kills it on launch. Each document is checked in a subprocess of its own, because relive aborts the whole process on a missing numeric property. The shim points easylogging at nothing but stdout on the way in: `ELPP_NO_DEFAULT_LOG_FILE` leaves the logger with file output on and no file to write to, so relive's first warning would dereference a null stream, and its diagnostics are the only thing that names the record behind a `WrongTLVLengthException`. CI clones the pin but never builds the harness (no cmake step, no submodules), so the unittest suite stays the CI gate.
- `npm test` — `node --test` unit tests under `tests/unit/` for the DOM-free modules (`imports.test.js` holds the list): geometry transforms, TLV destinations, entry paths, permalink format, settings sanitizing, plus schema checks over the shipped data files.
  - Those modules must stay importable in bare Node — no `window`/`document` at module top level (imports.test.js enforces this; `settings` additionally keeps its localStorage access inside guarded calls).
- `npm run test:browser` — Playwright (`tests/browser/`) drives the served site headlessly against `python3 -m http.server`, Chromium only; `@playwright/test` is pinned exactly (the browser build decides raster output — the Prettier/oxipng rule), so run `npx playwright install chromium` once after `npm ci`.
  - `anchors.spec.js` is the alignment anchors as a gate, each pinned twice: its geometry as literals — where the marker draws inside its own 368×240 screen, hand-verified against the artwork once and frozen, never regenerated from `model.js`, which is what they test — and its pixels colour-agnostically, the screen's canvas region matching the committed cam PNG away from the markers and differing from it on the pinned outlines. A transform regression fails the numbers at zero tolerance; a painter regression fails the pixels.
  - `smoke.spec.js` covers what breaks visibly: boot paints a map with a clean console, a view permalink lands where it points and `viewHash()` reproduces it (a plain view hash is never rewritten, so asserting `location.hash` survived would be vacuous), a click on a door follows it, `?embed=1` hides the chrome, a search Enter moves the view (to a plain view hash — a search jump writes no object token), and a settings toggle survives a reload.
  - `graphexport.spec.js` drives the world graph's two save buttons through the real anchor-click download, per game: the filename, the SVG parsing whole with one box per node the diagram shows, Exoddus's ender caption reaching the string, and the PNG header reading the layout `worldgraph.test.js` pins with the title band above it, doubled; Oddysee's reads a background pixel back, because a blank canvas encodes to a perfectly good PNG.
  - `reliveexport.spec.js` presses the JSON export button through the real sidecar fetch and download, per game from the path a game-only hash boots: the filename, the landed document hashed against `tests/fixtures/relive-digests.json`, no sidecar request before the press and exactly one across two, the button's accessible description matching its tooltip word for word, a sidecar that failed to parse fetched again on the next press, and a doctored one refused with a toast naming the property and no download fired — the sidecar URL and the button's wiring are the two seams the Node digest suite cannot see.
  - The specs probe the page through its own module singletons (dynamic import resolved against `location.href`) and settle the way `export.js` does (`preloadPath`, `artworkReady`, a synchronous `draw()`); `deviceScaleFactor` is 1 for every spec, set once in the config; the anchor spec, the one that compares pixels against the artwork, additionally pins the levers that comparison needs: zoom exactly 1, `?embed=1`, every show/cats key seeded explicitly through `owm:view`, and the mouse never moved. In a `waitForFunction` predicate keep to synchronous reads (`location.hash`) — an async predicate returns a Promise, which the poller takes as truthy at once, so the wait resolves with the promise's first value instead of polling.
- `python3 tools/build_map.py --game AO|AE --disc <image.bin ...>` — AE takes both discs; env fallbacks are `$ODDWORLD_DISC_AO` / `$ODDWORLD_DISC_AE` (2352-byte-sector raw images).
  - `cam2rgba` is compiled automatically on first run; `oxipng` must be installed (every emitted PNG is losslessly recompressed with `-o 2 --strip safe --force`, so byte-determinism of images also depends on the oxipng version — committed images were made with oxipng 10.x). The `--force` is what makes every committed byte oxipng's: without it a file oxipng cannot shrink keeps the raw write, whose deflate stream is CPython's zlib's, and four masks did.
- The pipeline is byte-deterministic. To verify builder changes, build into a scratch dir with `--out` and `cmp` the data file (and spot-check PNGs) against the committed outputs.
- `--levels X,Y` subset builds merge into the existing data file — they do not clobber other levels.
- Existing cam PNGs are skipped for speed, so a level whose decode previously half-completed keeps stale outputs; delete `public/cams/<game>/<LEVEL>/` for a clean rebuild of that level.
- `python3 tools/build_map.py --reencode-images` re-emits every PNG under `--out/cams` from its own pixels through `write_png` and restamps `CACHE_NAME`, no disc needed: the committed pixels are the builder's own raw input, and `read_png` reads them back from whatever colour type oxipng reduced them to. It is the encoding half of a rebuild, so it is what re-encodes the tree when the oxipng it encodes with moves, and a scratch `--out` holding no worker stamps nothing, like a build.
- Alignment anchors for eyeballing viewer geometry changes: AO R2 P1 C03 — the LCDStatusBoard box sits on the LED digit panel of the Employees sign; AE MI P1 C24 — the HandStone box sits on the QuikSave stone. If object markers drift toward screen centers, a world-to-art transform regressed.
  - Both of those sit at moderate depth, where a scale error is small enough to still look aligned; a scale anchor has to be near a screen's far edge. Use AE SV P7 C09 with collision lines on, where the floor line lies along the walkway deck at 200 units down, and AE MI P1 C04, where the wide LCD box covers the black panel and the LCDStatusBoard covers the small square under it.
  - All four are pinned by `tests/browser/anchors.spec.js`, so CI catches the drift the eyeball once missed; the prose stays for looking mid-change, and the pinned numbers move only with a deliberate re-verification at these permalinks.
- The viewer ships as ES modules with no build step, so a browser can run a **half-stale module graph**: one cached module beside a fresh one links without error as long as the names it imports still exist, then misbehaves silently and convincingly. A viewer bug the tests cannot reproduce is this until proven otherwise.
  - The tell is the server handing out the change while the running page misses it. A reload need not settle it, nor re-fetching the modules by hand; the reliable read is a fresh origin, which is `127.0.0.1` where the dev server was `localhost` or the other way round, since neither carries the other's HTTP cache or worker.

## Viewer surfaces

- Display against Settings is a taxonomy, not a layout choice. Display is what is drawn on the map right now — overlays and modes flipped mid-reading, carrying the keyboard keys, the reset button and the "Remember display & object filters" snapshot — while Settings is how the app behaves across visits (persistence, naming, field presentation). A lens that changes marker semantics (pens turn barriers from meta boxes into posts, and the ruler snaps to the post line) is still Display: from the user's seat every reading aid is the same "show me this" flip, and the semantics distinction is implementation trivia.

### Boot, caches and settings

- [js/data.js](public/js/data.js) owns which datasets there are and when each is fetched. The game a visit is looking at is decided from the link's own text (`bootGame`: the hash, else the remembered location, else the first id) before anything is awaited, so first paint waits on one game's data instead of both — Exoddus alone is twice Oddysee's size gzipped, and awaiting both spent the whole budget of the one on screen before a line of it was drawn.
  - `loadGame` memoizes one promise per dataset, so a link into a game still in flight awaits that fetch rather than starting a second; the game the visitor is not looking at is asked for at `priority: "low"`, which is not a courtesy to the artwork so much as a refusal to outrank it: an ordinary `fetch` is high priority and the cam bitmaps, never being in the document, are low, so the default would have put the hydration ahead of every screen on the map.
  - `index.html` preloads the **default boot dataset alone**. Preloading both was the whole cost: a saturated pipe transfers the same bytes whatever the order, so what a preload buys is the module graph's latency rather than bandwidth, and a second one spends the first one's bytes ahead of it. Keeping the one is worth a third of the win, and the asymmetry is real — an `AE` permalink gains nothing, since only an inline script could pick the preload and it would restate the boot rule in HTML.
  - `addGame` in [js/navigate.js](public/js/navigate.js) is per dataset and dispatches `games-changed`; every surface that reads more than the current game answers it — search re-runs an active query, an open type card re-renders its per-game counts, the offline panel gains a row. Buttons are appended as datasets land, so the game the visitor came for leads the row and nothing has to insert into an order.
  - A search in the gap says which dataset is still coming. Without that, a query only the other game can answer (`zulag 14` is Exoddus's alone, Oddysee's zulags stopping at 4) reads as a map that has never heard of the place, and then silently gains 10 hits.
  - `applyHash` awaits a dataset the hash names rather than rejecting it, so a permalink pasted into the gap lands, and the boot fallback stops reading a remembered location's unfetched game as a level that no longer exists and clearing it. The pending view write is held across the wait, since a debounced one landing on the address bar would replace the link being answered and leave no `hashchange` to recover it; a hash that changed under the wait is left to the newer link.

- `sw.js` (in `public/` beside `index.html`, so it is served at the site root; a classic script — not an ES module; linted with `serviceworker` globals, no unit tests by design) holds two caches with two disciplines: `cams/**/*.png` cache-first in the Cache API, because GitHub Pages re-stamps HTTP validators on every deploy, and the app shell (page, code, top-level JSONs, icons) network-first in a fixed `shell-v1` bucket that serves only when the network fails — online loads stay as fresh as with no worker, and the map still opens offline.
  - It is opt-in: the worker can't read settings, so `settings.js` gates it on the `cacheMap` setting (off by default) — enable registers the worker and creates the `cams-on` marker bucket the worker checks before storing; disable deletes every `cams-*` and `shell-*` bucket and unregisters. The marker, not unregistration, is what stops caching immediately, since an already-controlling worker keeps handling fetches until reload and module state wouldn't survive an idle-worker restart.
  - Its `CACHE_NAME` is written by the builder: a content hash of `public/cams`, so regenerating a PNG expires the cache and a build that decodes nothing leaves it alone. Both games are hashed however few levels were built, since one worker serves both; a scratch `--out` holds no worker and stamps nothing. Commit the rewritten line with the artwork.
  - The shell bucket carries no such stamp: network-first entries self-refresh on every successful load, so the name only moves to retire an incompatible storage scheme. An app-page navigation stores and matches under the one key `index.html`, which is what lets `/`, `/index.html` and `/?embed=1` all boot offline — a navigation anywhere else on the origin never reaches that key, a root-level page falling to the ordinary shell rule under its own URL, so the SEO statics (og-image, robots, sitemap), which match no rule at all, can neither displace the page nor enter the cache. A redirected response is never stored: a navigation answered from one would throw rather than render.
  - The worker only caches what passes through it, so a user enable always warms — `warmShell` re-fetches everything the page already pulled (from its own performance entries, plus the document and the datasets by name — a resource still in flight has no entry yet, and the hydrating dataset is exactly that) once the worker takes the page, and offline works from the enabling visit onward; a re-enable follows a sweep, so it must warm whatever still controls the page. The boot call never warms: a controlled page's own boot fetches are already the refresh.
  - After rebuilding cams locally, use DevTools → Application → "Bypass for network" (or Clear site data) to see the new images.
- [js/offline.js](public/js/offline.js) is the worker's page-side half: the shell warm on enable, and the Settings panel that stores a whole game's artwork at once, so a place nobody has browsed is kept too.
  - It downloads by plain `fetch`, letting the worker store each response on its way through, which is why the body has to be read (the stored copy is a clone of it) and why nothing starts until the worker controls the page: an uncontrolled page's fetches are spent for nothing. A file that fails stays missing and the next run picks it up, so re-clicking is the resume.
  - Nothing is remembered about what was downloaded: the rows count the cache's own keys against the game's file list, so a sweep, an eviction or a rebuilt cache name can never leave the panel claiming artwork that is gone. `MAX_ENTRIES` in the worker is therefore a feature constraint rather than a browse cap, since a cap below both games' complete artwork would evict the head of what a download just fetched; `tests/unit/offline.test.js` pins it.
  - `persist()` is asked for on a download because artwork this deliberate should outlive the browser's housekeeping; it is advisory (Chrome grants it on engagement alone) and nothing depends on the answer.
  - A registration that fails costs the browsing case only cached artwork, but it costs this panel everything, so `workerRegistered()` keeps the attempt's answer: the download says so at once rather than timing out on a worker that is never coming, and the exception goes to the console, the only surface with room for it.
  - Progress is a `progressbar` and deliberately not a live region: the percent moves several times a second, and the finishing toast is what announces.
- `initSettings`'s `bind` is the funnel for the boolean settings: seeding the checkbox, persisting, marking a row whose value isn't its default, and the apply callback all hang off one call, so a new boolean setting gets the lot by being bound.
  - The show-more checkbox flips `fieldPrefs.mode` rather than a boolean, so it is wired by hand and is the one control that has to be updated alongside `bind`.

### Navigation, routes and the world graph

- `visiblePaths` in [js/navigate.js](public/js/navigate.js) is the one place a level's path order is decided *for the buttons* — the path buttons, the path a level opens on and the `[` / `]` stepping all read it, so an order that reaches one reaches all three. The world graph is the exception and says so on its own bullet: its rows are the walk itself, whatever the setting, because there the order is geometry rather than a listing. The "Paths in play order" setting routes it through [js/pathorder.js](public/js/pathorder.js), which returns a permutation of what it was handed and never filters: visibility and `revealPath` stay the caller's business, which is what keeps the module clear of `demo.js`.
  - `levelOrder` is the order itself, one walk of the level's own trusted transitions out from the way in, memoized over every path the level has; `orderPaths` only sorts what it is handed by that, so a subset comes back in the same order and the demo setting cannot change what the order is. Twelve of the 25 levels come back exactly as they ship, Paramonia and Scrabania among them: their stored order already is the walk.
  - An **area** is what a path's name names with the `[Demo] ` mark and anything after a colon dropped, so a secret area, a sub-room and a demo copy all belong to the area they name, while a path the discs never named is an area of one. An area is walked whole before the walk leaves it, which is what holds Zulag 1's five paths together where the way on out of it sits two rooms in and a dead end is still unvisited behind it.
  - Branches are chosen by **the run the level counts itself in** — the numbered run naming the most of its areas, the Brewery's fourteen zulags rather than its three hubs, since numbers only ever compare inside one run. The branch whose number comes soonest goes first, which puts FeeCo's unnumbered corridor ahead of the terminal beside it (terminal 3 is behind it) and the Brewery's second hub behind the five zulags the first one serves. A branch reaching no number at all is a pocket off the route and is looked into before the walk moves on, which is the Mudomo Vault's third room. After all that, the lowest path id.
  - Inside an area, the same walk again from the path it was entered at, then whatever it missed, a sub-area behind its parent and a demo copy behind both. A path you can only come back from goes before one that carries you on — the pocket rule at path scale — and a way out of the level carries on like any other, which is what puts Rupture Farms Return's Zulag 1 Boom Machine room second and its Zulag 4 exit to the Board Room last, behind the two rooms that unlock it. Those and Zulags 2 and 3 are the only four places in either game where an area offers the walk a choice at all; the two hubs' spokes have nothing to rank them and fall to the path id.
  - An area nothing travels to still slots into its run by number, which is what lands the Mines' `[Demo] Tunnel 5: Blind Mudokons` between `Tunnels 3-5` and `Tunnel 6`, no other path naming the area it copies.
  - An Exoddus level's ender half sits at the level's tail in the order the walk met it, and that is the one thing outranking the walk: `BW P9` is the only path in either game listed ahead of what reaches it, its Executive Office being reachable only through the ender's own approach.
  - `levelEntry` elects one way in per level — an arrival from a level earlier in `data.levels`, else `AbeStart`, else any arrival — and the walk starts there. Deliberately not `computeEntryPaths`' set, which carries a later level's door back in (`R2 P11` is the Board Room's) and an `AbeStart` sitting deep inside a level (Bonewerkz' is in Annex 8); both games' elections agree with the decomp's own level-select tables, `sLevelList_4D0300` and `gPerLvlData_561700`. It is passed `data.geometry` rather than reading `LAYOUT`, so the gaps toggle can never reorder a button.
- A route ([js/route.js](public/js/route.js)) is a list of per-path segments `{lv, pa, pts}`; an armed follow seams two segments (`routeSeam` before the navigation, `routeArrive` anchoring the far side on the partner), and a same-path door pair seams exactly like a cross-path one — the polyline break is the point.
  - The one survival rule: the route lives while the selection stands on **any of its segments' paths** — so the recipient of a shared link can walk it by button, door or the back button, and only a selection the route never visits clears it. The armed follow appends its destination segment before navigating, which is how a seam into fresh territory passes; that only holds because targeted navigation (`navigateToDest`, the jump helpers) switches levels through `setLevel`, which elects no default path — `selectLevel`'s first-path selection in between would fire the rule against a path nobody chose.
  - The token is `route=nCOUNT;sLV.PA;x,y;…;end`: the count first so it outlives a cut, a marker opening every segment so no waypoint can rebind to artwork it wasn't plotted on, `end` proving the payload complete.
- Every coordinate a permalink carries is a **world** coordinate: the view centre, the object anchor and the route's waypoints alike. Draw space is a packing of the world that a change of pitch would slide under a link; a world point names a place in the game.
  - `parseHash` reads the text alone and `hashToDraw` resolves the coordinates, because the geometry is only the link's own once its game has been selected. Converting inside `parseHash` would read a link against whatever game happened to be loaded, and `sanitizeLocationHash` calls it at boot with no geometry at all.
  - There is no version marker and no fallback: a viewer meeting numbers it cannot read drops the view and fits the path instead. Shared links are live, so treat the shape as fixed and add to it rather than redefining what a token means.
  - `scheduleHash`'s push-ness is sticky until the write fires (a follow's history entry must survive the silent writes riding its heels), and the seam calls `flushHash()` first, so the entry left behind holds the route as plotted — both were found by watching the back button lose the follow.
- `#graphView` ([js/graphview.js](public/js/graphview.js), aggregated and laid out by [js/worldgraph.js](public/js/worldgraph.js)) is the whole game as one diagram in place of the map: a column per level in `data.levels` order, its paths stacked in `levelOrder`'s, and an edge for every transition the map already believes between two of them. A mode is not a float, so it takes **no stacking tier** — a positioned sibling after `#cv` covers the canvas, and every tier above it (the toasts, the drawer, the map chrome, the dialogs) keeps standing over it untouched. What that leaves is the map's own furniture. The floats close themselves — each answers `graph-changed` the way it answers a path change, because a panel merely hidden under the mode still answers Escape and comes back describing a view nobody is looking at — so `body.graph` is left with the surfaces that repaint themselves back into sight (`#minimap` unhides from inside `draw()`) and the sidebar buttons that act on the map: one saves the covered canvas, one paints its own image of a map nobody is looking at, and one would put a float the mode has just dismissed straight back over it. The Display toggles stay, since a checkbox records its own new state; that is the same line the swallowed keys are drawn on.
  - The canvas is covered, never unlaid-out: `fitView`, `centerOn` and `navigateToDest` each re-`requestAnimationFrame` while `cv.clientWidth` is 0, so a `display: none` would spin a frame loop for as long as the mode is up and hold a node's own jump until it closed.
  - Rows are the play-order walk whatever the "Paths in play order" setting says, because the walk is what makes the diagram legible: against the order the discs store, over the 62 and 86 undirected pairs inside a column, summing |row(a) - row(b)| on the rows the diagram draws, it comes to 125 against the stored order's 181 in Oddysee and 227 against 406 in Exoddus, and leaves one interleaved pair of arcs per game.
  - An edge is the pair of paths with a count each way, and an arrowhead marks a one-way link and nothing else — 13 Oddysee pairs and 28 Exoddus ones, against the 64 and 69 that run both ways. A head on every travelable end would spend the mark on the pairs that are ordinary and leave nothing for the ones that are not. Which end it goes on is `fwd`/`rev`, never the polyline's own direction: 4 Oddysee pairs and 11 Exoddus ones run *backwards* along the node order, and a head read off the line would point the wrong way on all fifteen.
  - Routes are orthogonal polylines, lane-packed per gutter: a level's own edges hug their column, an edge to the next level along crosses one gutter, and one reaching further travels the band above every column. The lanes are what keep two routes off one line, and a gutter is only as wide as the lanes it carries. Straight centre-to-centre lines are what this buys off: they pass through a box belonging to neither end on 36 of Oddysee's 77 lines and 54 of Exoddus' 97, where the routed ones do it on none. `tests/unit/worldgraph.test.js` sweeps the shipped data for a route that leaves the diagram, crosses a node box on either axis, bends off-axis or shares a line.
  - Each edge leaves a box on a line of its own, spread across the box's own height, up-bound stubs above down-bound ones and the nearer turn where it cannot cut across a farther one. Every edge departing at the box's middle instead put 154 pairs of Oddysee segments and 235 of Exoddus' on top of each other, each pair a stretch of line whose colour was whichever edge painted last. Three quarters of Exoddus' sat at the seven nodes of degree seven and up that the diagram exists to show; Oddysee's split about evenly with the rest, which is why the fix is every box's business and not the hubs'. The ordering is what makes the spread crossing-free rather than merely spread out, and `tests/unit/worldgraph.test.js` sweeps the shipped data for both: no two edges along one stretch of line, and no stub crossing another out of the same side of a box.
  - An Exoddus level's ender half is a contiguous tail of the walk in all five levels that have one, so the break before it is one row offset per column rather than a test per row, and the caption sits in the gap that offset opens. It costs no height: the tallest column in either game has no section.
  - A hover leg is emitted per segment rather than per route, because `#anchorTip` places itself against its anchor's box and a route's whole box can be most of the diagram; the `<g>` around them is what still lights the line entire, through `:has`.
  - Nodes are buttons, so the keyboard reaches every path in the game and a click travels there. The diagram opens scrolled to the path in hand with the focus on it and afterwards only keeps it in view, so `[` / `]` never step the highlight off screen. Focus goes back to whatever opened the mode — and the collapsed drawer being `inert`, an opener behind one hands the keyboard to the menu button instead.
  - It drags to pan like the map, mouse and pen only — touch already pans the scroller with one finger. A plain mouse reaches the bottom of a 3491px-wide diagram with the scrollbar and never the right of it, and the horizontal scroll a trackpad has is no gesture a wheel offers. A drag that ends on a box must not count as a click on it, which is asked of the pointer's own `detail` rather than of a flag the next activation would find: a keyboard Enter reports no presses and so is never the one swallowed.
  - The map's own keys stop at a capture-phase listener of its own rather than at a guard in [js/interaction.js](public/js/interaction.js): they would flip overlays nobody can see, open a panel over the diagram, or — `s` — silently re-centre the map and rewrite the ruler and every route waypoint. It yields Escape to an open dialog by looking for `.overlay.open`, because `interaction.js` imports this module and so every dialog's trap registers after it — and otherwise stops Escape where it lands, so one press closes one thing, dismissing the anchored tooltip itself since it may be showing an edge's.
  - Clicking a box closes the diagram, which hands the rest of that gesture to the canvas underneath: without a guard the second click of a double-click lands on the map and adds a route waypoint or opens a screen list nobody asked for. [js/interaction.js](public/js/interaction.js) arms one on the close and clears it on the next press whose `detail` says it begins its own sequence, so nothing is timed. The covered canvas also gives up its accessible name while the mode is up, or a reader would be told about a map that is not on screen — and told again on every selection, since that name is rewritten each time.
  - The mode rides the hash as a bare `graph` token in the tail, which is what makes the diagram shareable and what closes it on the back button. An older deployed viewer drops an unknown tail token and opens the map at the view the link names.
  - `map-data.test.js`'s pinned cross-level follows are the aggregation's oracle: the graph's own crossings expand back to exactly those strings, and a mismatch is the graph's bug.
  - [js/graphsvg.js](public/js/graphsvg.js) is the diagram's second renderer, and the export is what it exists for: bare-Node importable, it serializes the same `worldGraph` + `graphLayout` into one self-contained SVG — presentation attributes only, the `:root` palette resolved by hand and pinned against the stylesheet by test (`tests/unit/graphsvg.test.js`), since a standalone file cannot ask for `var()`. It owns the edge markup (`marker`/`wirePath`), which graphview imports, so the one-way head rule exists once; a reverse-only route is emitted backwards under a plain `orient="auto"` head, SVG2's `auto-start-reverse` being a feature librsvg gained only in 2.51.3 and older wiki thumbnailers still lack. [js/export.js](public/js/export.js) owns the bar's two save buttons: the SVG is the string in a file, the PNG the same string rasterized through `sizedCanvas` at 2x falling to 1x with a toast — the scale goes into the SVG's root over a constant viewBox, so an engine that rasterizes at intrinsic size is still crisp. On narrow the save pair hides beside the legend: the title is the bar's one caption, and two wrapped labels were what crushed it — check the bar at 320 and 360 alongside the place chip's own narrow widths. The `-demos` filename marker is read off the built nodes, never the setting, so Oddysee never wears it and a session-revealed demo copy marks the file that really differs — `-edited` follows it the same way, off `pathEdited` over the nodes; the standing-here outline and everything hover-produced stay out — the map export's transients rule — so two exports of one game are byte-identical.
  - Deliberately not `.chrome`: an embed on a wiki page is exactly where "how does this place connect to the rest" gets asked.

### Geometry, rendering and interaction

- `#cv`'s `touch-action` is conditional on purpose: `none` normally, `pinch-zoom` while `body.page-zoomed` is set (`js/interaction.js` watches `visualViewport.scale`, and skips both its own pinch and a touch pointer's `setPointerCapture` in that state — capture would keep the gesture from reaching the browser, while a mouse keeps its capture or a drag released off the canvas never ends).
  - `body`'s `touch-action: manipulation` is the other half: it drops double-tap zoom, and with it the tap delay a zoomable page otherwise costs, while leaving pinch alone.
- `#minimap` paints inside [js/render.js](public/js/render.js) at the end of `draw()` — a second, tiny projection of the same frame, so it can never lag the view — while [js/minimap.js](public/js/minimap.js) holds only the scrubbing, through the same exported `minimapScale` factor the painter uses. It hides itself when the whole path fits the window, yields the bottom-right corner to the numbers panel via CSS (`:has`) — and on narrow to the screen list, a bottom sheet across the same corner there — and is deliberately not `.chrome`: an embed is exactly where orientation help is scarce.
- `#exportMenu` is the sidebar's one Export control: a `<details>` holding the three export buttons, closed at every boot and remembered nowhere, sitting after `#toggles` rather than inside it because an export is an action and not a Display flip. It opens on a click rather than a hover, since a hover has nothing for touch (the sidebar is a drawer on a phone, where the tooltips already have to filter hover events to the mouse) and nothing for the keyboard, where the summary is a disclosure button of the browser's own; and it stays open across a press, so a button's own progress label and dimming are in view while its export runs, which a menu closing on the click would hide. The world graph hides the two image exports inside it and leaves the disclosure standing for the third. The browser specs open it before they press.
- The JSON export button (`#exportJsonBtn`, in [js/export.js](public/js/export.js)) hands the standing path over as the level editor's document. It is the one export the world-graph mode leaves standing, by the same line the Display toggles are on: its two neighbours would save a canvas nobody is looking at, while this one reads the path in hand, which the diagram is highlighting. It refuses rather than writing a file whose manifest holds a miss, because relive's importer aborts the process outright on a missing numeric property, and it says on the way out what the artefact costs: `ImportCameraAndFG1` removes every FG1 chunk unconditionally and re-adds one only from layers the JSON carries, so importing an art-free document strips the path's foreground masks.
  - Emitting the layers instead is not a builder change waiting on a rebuild, which is what this looked like from the import contract alone: relive's layer buffers are `u16[4][240][640]` and its masks are screen-space, while a PlayStation screen is 368 wide. What we could emit describes the narrower screen, so the masks cannot be derived from this data at any cost and the download says what it drops.
- `paint` in [js/render.js](public/js/render.js) is the one painter, and `draw()` is only the live canvas's call to it; [js/export.js](public/js/export.js) calls it again into an offscreen canvas sized to a whole path, which is what "Export whole path" saves.
  - Its `transients` flag gates the five affordances a pointer produces — the flash ring, the dashed highlight, a hovered Slig's pen, and the connection-arrow and wire spotlights. The two spotlights are why the flag exists rather than a note: each dims everything it is *not* focused on (a wire to 0.12, an arrow to 0.15), so exporting mid-hover would bake in a near-invisible overlay rather than a stray mark. The ruler and the route do render, being deliberate annotation.
  - `draw()` skips an image that has not arrived and repaints when it does, which is a hole in a paint that happens once. `preloadPath` waits for the artwork first, the foreground masks included whatever `show.fg` says — they are a percent of the bytes, and a toggle that moved mid-preload would otherwise draw masks nothing fetched.
  - Waiting is not sufficient, so `artworkReady` is asked again immediately before the paint: a load that failed reports itself `complete` with no width, and the image cache's own eviction can drop this path's entries while another selection passes through, leaving `img()` to mint blanks the paint silently skips. The same stretch re-checks the path — `paint` draws whatever is standing while the canvas was sized for what was preloaded, and a held `]` autorepeats through the window listener with the button disabled. Nothing may await between those checks and the paint.
  - `sizedCanvas` probes the canvas with one pixel painted and read back before the real paint. A browser past its limit says nothing: drawing into the canvas is ignored, or the size asked for is quietly clamped, and a blank canvas encodes to a perfectly good multi-megabyte PNG. Failing that, the area budget is quartered and the side halved and it asks again.
  - The budget (`EXPORT_MAX_PX`/`EXPORT_MAX_DIM`) follows the pitch on screen, which is what it is for: packed, the largest path in either game is 14.8 MP and nothing scales, while spaced AO lays its screens at the cell's own 1024x480 and the Credits path wants 49.2 MP. Past either bound the image scales to fit and says so.
  - The frame is the cell grid (`pathImage` sized on it, `cellOrigin()` anchoring it), so what the packed layout draws in the slack beyond the outermost screens falls outside the image — 248 AO markers and 526 collision-line pieces, none of them covering a screen. Nothing with screen coverage is ever cropped, pinned in `tests/unit/map-data.test.js`, and the spaced pitch takes that ground in.
  - The filename is read before the encode, not after: an encode this size is long enough for the place it names to move under it.
- The "Gaps between screens" Display toggle (`setSpacing` in [js/state.js](public/js/state.js), off by default, key `s`) lays screens at the cell's own pitch instead of packed edge to edge, so the slack shows at the size the game addresses it. The transform degenerates to `dX(wx) = wx - winX`, draw space becoming world space shifted, and a screen's interior stays 1:1 either way, which is what keeps a permalink's zoom meaning the same thing in both.
  - `LAYOUT` is `GEO` with `cellW`/`cellH` standing for the pitch in force. Anything reading a pitch reads that rather than the data's, which is why `screenRuns` and `lineRuns` default to it: the dotting has to answer to how the map is laid out now, not to how it ships.
    - A geometry invariant is asked at both pitches (`pitches` in `tests/unit/fixtures.js`), because the two disagree in one direction only: a rule that collapses the slack unconditionally is exactly right packed and short by a slack per boundary spaced, so the packed half alone can never say so.
  - Flipping it moves every draw coordinate, so `setPitch` in [js/navigate.js](public/js/navigate.js) brackets the flip: the view's centre (never its corner, which would slide the view), the ruler's ends and every route waypoint are read out as world points and put back after. A route survives it for the same reason a shared link does, its waypoints being world points either way.
  - The fold in `lineRuns` collapses only where the packing leaves it no draw space. Spaced out it is real canvas, so a line crossing the gap draws dotted across it rather than vanishing, and the marking keeps meaning what it meant: this is ground the game never renders.
    - Asked of the axes the fold crosses and no others. Along an axis it stays inside its window it travels real screen distance, which is none of the fold's, so a rule reading that axis keeps every descending line's crossing and packed draws it over the neighbour the fold lands on. Nor is the draw space worth measuring off the fold's own ends: a cut sits exactly on a cell boundary, `at(t)` puts it back an ulp low, and `Math.floor` hands back the cell before it.
  - A screen sits `winX`/`winY` inside its own cell, so `cellOrigin` steps the cell's corner back from the screen's and everything framing a cell reads it: the grid, the minimap, `fitView`'s bounds. Drawing the grid on the screen's corner instead puts the whole gap on one side and reads every leftward overhang as the neighbour's, which is what AO's +256/+120 makes obvious and AE's +0/+0 hides entirely.
  - Centring a camera means centring its screen, never the cell around it (`GEO.visW / 2`, not `CELL_W / 2`). Packed the two are the same point.
  - `cellAt` returns null in the slack, so a click on bare slack opens no screen list — one landing on a marker drawn there opens the marker's own screen instead. Packed there is no slack to land in and the check never fires.
- `screenRuns` ([js/model.js](public/js/model.js)) splits a marker into the part drawn where the object really is and the part drawn over the slack between camera windows, which the packing folds onto a neighbour's artwork. The first is solid and filled like any marker, the second hollow and dotted, and the render clips one pass to each so neither paints over the other's half of a shared edge. Always on, like the background-plane treatment: it says what is being drawn rather than offering a reading, so it earns no Display toggle.
  - `whole` is the common case, and the one that must stay cheap: a marker inside one window, and equally one straddling windows whose runs touch, because the slack between them takes no draw space at all. Straddling does not settle it on its own, since a marker can cross one axis cleanly and still trail into the slack on the other: 1433 AE markers reach a second window and 978 of those come back whole.
  - Dotting whatever leaves a marker's own cell is the tempting rule and is wrong. In AE it would dot real screen coverage on 1506 of the 1783 markers it touches; in AO, on 1 of 1232. Eyeballing the rule on Oddysee, where the slack is far too wide for a marker to cross, would have said it works.
  - `offScreen` is the degenerate case of no run at all: the marker covers no screen, draws wholly dotted, and its screen-list row says so. 276 in AO, and **none** in AE, whose 7x20 of slack is too small to swallow anything whole; both pinned in `tests/unit/map-data.test.js`.
  - The runs are measured against the **drawn** extent, not the world span. A world span that crosses the slack is longer than what is drawn for it, so comparing the two would call every straddling marker partial.
  - The screen list and the numbers panel bucket by the world cell a marker's top-left corner falls in (`tlvCell`), never by where it is drawn, so one folded onto a neighbour's artwork is still listed under its own cell and not the neighbour's. The tag is what says why it is not visible there.
  - A barrier post is a single x with nothing to split, so it dots whole when `offScreen`.
  - `drawSpan` frames a marker's box by the screen it covers rather than by its own two ends, and gives it the leading overhang, that screen, then the trailing one. Framing it end by end walks the box off the very screen it covers whenever those ends fall in different cells, which leaves the solid clip outside the box and inverts the dotting: the part on screen dotted, the part in the slack solid. The covered stretch is the drawn distance between its first and last on-screen point, never the sum of the screens under it: summing folds away slack the spaced layout hands real canvas, and the box stops short of its own far edge. `tests/unit/map-data.test.js` sweeps the shipped data for a run drawn outside its own box.
  - `drawBox` is that framing on both axes and `markerCentre` its middle, and every surface anchored on a marker reads them: the wires and connection arrows, the rect hover tests and the ring a permalink highlights, and the ruler's snap. Re-deriving any of those from `dX(t.x1)`/`dX(t.x2)` puts the marker in one place and its answer in another; spaced the two agree exactly, so the disagreement only ever shows packed.
  - `lineRuns` is the same rule for a collision line, cut wherever it crosses a window edge on either axis. Within a window the transform is a translation, so each piece lands exactly and stays straight, diagonals included, and consecutive pieces of the same kind merge so a dash pattern is not restarted mid-line. A line crossing the slack whole comes back as one piece, since the fold takes no draw space; only one that stops inside the slack has a piece to dot. 1740 of AO's 2895 lines are dotted somewhere, and 812 of AE's 6645; both pinned in `tests/unit/map-data.test.js`, which also sweeps the shipped data for a piece that starts anywhere but where the last one ended, at either pitch — the pieces are one polyline, and a fold given draw space the packing does not have breaks it.
  - A piece in the slack takes the frame of the screen it touches rather than its own ends'. That is load-bearing rather than tidiness: AO's slack straddles a cell boundary, so framing end by end reverses an overhang and draws it back across most of a screen. `tests/unit/map-data.test.js` sweeps the shipped data for a piece that runs against its line or outruns it.
  - Pointing at a line asks `lineRuns` as well: the hover test walks the drawn pieces and the ruler snaps to the polyline's own ends. The straight run between a line's two transformed ends is not where a folded line is drawn, and 42 AO lines and 749 AE ones are drawn more than a unit off it.
  - The fold test asks the neighbouring **spans**, not the points bounding one. A line ending exactly on a window edge touches that screen at a single point and covers none of it, so what it leaves behind is an overhang; reading the endpoint instead would collapse 352 AE lines' overhangs into nothing.
- Barrier markers (the `BARRIERS` table in [js/config.js](public/js/config.js)) render as posts on the boundary the engine enforces — each stamp's top-left x, the same edge a hovered pen band ends on, so posts and band always meet — gated by the "Enemy patrol pens" Display toggle (`PENS.on`, off by default) together with the Enemies category; pens off, they stay ordinary meta boxes. `markerShown` is the one marker-visibility rule (drawing, hover and the ruler's snapping all ask it), so what is drawn is exactly what can be pointed at, and a post snaps on its line rather than its stamp's middle.
  - `patrolZone` ([js/model.js](public/js/model.js)) shades a hovered Slig's pen. The engine pairs bounds to sligs by id — the bound-side key is `slig_id` in AO but `slig_bound_persist_id` in AE — over a camera window that differs per game (AO ±2, AE ±3, Slig.cpp's bound loops), and the viewer honours only a unique pair; the engine's last-match-wins on duplicates is not worth imitating. Scrab bounds ship no ids, so scrabs get posts and no pen.
- The switch wiring overlay (`computeWiring` in [js/model.js](public/js/model.js), reading the per-game `WIRES` table in [js/config.js](public/js/config.js)) draws producer→consumer edges between objects whose wire fields share a live switch id — the "Switch wiring" Display toggle, on by default.
  - The engine keeps one switch-state array per level, reset only on level change (and at game start), so ids are level-scoped: same-path pairs draw as wires, and a cross-path partner reaches the hover tooltip as text ("set in P2") via `levelWiring`, which leaves demo paths out so a note never points somewhere nothing travels.
  - Ids 0 and 1 never wire: the engine hardwires them (never / always on) and producers refuse them, so a consumer's `switch_id = 1` means "always on", not a wire to something numbered 1.
  - The table is curated against the engine's actual read/write sites, and many fields named `switch_id` are not wire ends: Teleporter's `teleporter_switch_id`/`other_teleporter_switch_id` are the `tp#` pair numbers, a placed Slig's or FlyingSlig's spawner id is read only off spawner TLVs (AE's SligSpawner ships its own copy as `id`), and a drill or saw that writes its own id back at cycle end is group timing rather than wiring, so Drill/MeatSaw stay consumers — the cost is that a self-driven pair with no external producer (one exists in the shipped data) shows no wire. The near-miss to remember: HandStone's `trigger_switch_id` *is* a real write (the same Abe.cpp line MovieHandStone uses) even though the stone also copies it into a field marked unused.
  - The tooltip's wiring lines describe the drawn wires — a local partner in a hidden category is neither drawn nor named, while a cross-path note names a path rather than a marker — and state only what exists, never absence: the table is curated from the engine's verified read/write sites, so an id can always drive something it has no evidence for.
  - Hub doors (`DOOR_GATE`: AO `start_state` 2, AE `door_type` 2/3 — Door.cpp's hub/tasks-door update) AND their eight `hub_N_id`s into their own `switch_id`: the hubs are the gate door's inputs and its own id its output alone, since the gate rewrites that id every frame and an external feed could never hold it.
  - An edge hides with either endpoint (`markerShown` both ends), and a wire to a barrier post lands on the post's line, as the ruler's snap does.
  - `tests/unit/wiring.test.js` pins the per-game edge totals and cross-checks every table key against the shipped data, so a typo'd key cannot ship silently.

### Panels, search, dialogs and accessibility

- The collapsed drawer is `inert` (`syncMenu` sets it beside the menu-button state), so the controls it slides off-screen leave the tab order with it. Focus cannot enter an inert subtree at all: closing the drawer out from under the focused element moves focus to the menu button, and `/` has to open the drawer before focusing search rather than after.
- `#a11yStatus` ([js/a11y.js](public/js/a11y.js)) is the one region that says where the map stands: a `.sr-only` `role="status"` div parented on `<body>`, written on a real path change with the game, the level's full name, the path and its curated or in-game name, how many objects the path holds, and that it carries a note where it does — the accent dot on the chip says that last one to everybody else. `#cv` takes the same sentence into its `aria-label` under `role="img"`, so the graphic is named with what was last announced rather than with a second wording free to drift from it; a name is not a live region, so it can be rewritten as often as it likes without a word being spoken for it.
  - Being a `<body>` child that nothing hides is the whole of its reliability. `display: none`, `visibility: hidden` and an ancestor the drawer has taken the screen from all remove an element from the accessibility tree, and a region outside that tree announces nothing at all — a failure with no visible symptom.
  - It settles before it speaks. `selection-changed` fires once per autorepeat of a held `[` or `]`, and a permalink into another level selects that level's first path on the way through, so a region written on every one of them would talk through a whole browse and name places nobody chose. Identity alone answers neither, both being real changes of path.
  - The toasts and the route bar's `role="status"` answer for an action just taken; this one answers for where you are, and it is the only region that does — which is why `#placePanel` gives up being one.
  - Deliberately not `.chrome`: an embed is this map inside someone else's page, where the canvas's own name is the only orientation on offer.
- `#placePanel` ([js/place.js](public/js/place.js)) is disclosed rather than announced: `#placeBtn`'s `aria-expanded`/`aria-controls` pair is the route in, and opening it moves focus onto the panel — `tabindex="-1"` and a `role="group"` with a name of its own — so a reader reaches the section, the nickname, the flags and the note that the announced sentence leaves out. Focus lands on the panel rather than on the chip because the chip's own label is rewritten on every selection change, and an accessible name that changes under the focus *is* announced: parking there would double every step.
  - A re-selection of the path it already describes skips the fill, because the pushed hash rewrite re-fires `selection-changed` on the same path constantly, and a rebuild would throw away the reader's scroll position.
  - Chip and panel are hidden outright under an open drawer on narrow, since the drawer names the place in its own buttons — which means an open panel can be covered rather than closed, and that the focus move has to ask whether the panel is really rendered before making it.
  - Check chip geometry on the longest label either game has, AE BA P4 (`[Demo] Block 3 Slig Bunks: Crawling Sligs`) at 390px and narrower: a representative path is short enough to hide a width regression, and the chip sits above the corner buttons in paint order, so an overlap makes them unclickable rather than merely untidy.
- [js/placesearch.js](public/js/placesearch.js) indexes the map's own places — a level, one path inside it, or one screen of a path — for the search box's Places group; it is not [js/place.js](public/js/place.js), which is the where-am-I chip.
  - A candidate carries two indexes because one blob cannot serve both halves: the *names* (level name, curated or in-game path name, nickname, section) are matched by substring the way an object's fields are, while the `LV Pn` code is held as whole tokens (`["r2", "p1"]`) and answers a term only in full. Blobbed together, the `2` in `zulag 2` is answered by the `R2` every Rupture Farms Return path sits in, and the four the game does call Zulag 2 arrive buried in all eighteen.
  - A screen candidate (`R2 P1 C3`) carries its path's blob plus the tokens naming its camera (`c3`, `c03`, the full cam name), but is listed only when a query term matches one of those camera tokens — its blob is its path's, so a bare name query would otherwise drag every matching path's whole screen list in. Clicking one centers that camera.
  - A path indexes its level's name, so a level name finds what is inside it — but `rankPlace` leaves that name out, which is what puts `Monsaic Lines` above the five paths it just pulled in.
  - The group is counted and capped apart from the objects, taking neither `HIT_CAP` nor a `GROUP_MAX` slot from them, and the summary's hit count stays an object count — which is why it has to say "no object hits" when places are the only thing on screen. Its demo-hidden tally is the one number that counts both, since a place the setting keeps off the map goes missing the way an object does.
  - Scope applies as it does to objects, except that `path` scope drops the group: the only place in scope is the one you are standing on.
- [js/messages.js](public/js/messages.js) resolves what a sign in the world actually says: `objectMessages` is the one place that knows how each type picks from its table, so the hover tooltip, the screen list and search can never disagree about a board's words.
  - It answers `[]` only for a board whose ids are all blank, which is the claim the surfaces render as "runs dark": 20 of Oddysee's 45 boards, every one a Rupture Farms Return copy of a board its first visit taught with, where silence alone would read as the map not knowing. Everything else that cannot answer is `null`, a type that reads no table and a sidecar that never arrived alike, since `loadJson` yields `null` for a file that failed and a map that has not read the table must not assert the board is dark.
  - A line carries a note only where something else contests it. For the two states of an `LCD` that means a switch that can actually flip: the engine hardwires ids 0 and 1 to never and always, so 26 shipped boards no switch can flip would otherwise name a switch state, pinned in `tests/unit/messages.test.js`. A live switch keeps its note even when only one state resolves text, that being exactly what decides whether the line appears at all.
  - The tooltip caps at three lines and the screen list carries the whole rotation, a board reaching fifteen messages; search blobs them all, so a remembered slogan finds the board. Button codes reach search as the words the reader sees, the same rule the raw-values setting follows.
  - The map's own Displays category is off by default, so a marker has to be turned on before it can be hovered; the screen list and search answer either way.
- `#camPanel` ([js/campanel.js](public/js/campanel.js)) answers a coordinate rather than a selection, so it takes one from a click or from `l`. The pointer aims; the keyboard has only the view's centre, and a path's grid is mostly empty — the centre sits over no camera at all on 100 of the 191 shipped paths — so `nearestCam` gives it the closest screen instead of refusing on a coin flip. A click carrying no object keeps its own rule, dismissing on the void; one landing on a marker opens the screen the marker belongs to — not necessarily the screen clicked — and falls back to the clicked screen when that cell holds no camera.
  - Opening it from the keyboard moves focus onto it: `tabindex="-1"` and a `role="group"` named by its own title through `aria-labelledby`, so the camera and the object count are heard before the rows and are not written a second time. The container and not the first row, which would skip both and has nothing to land on at all when a screen holds nothing.
  - Closing hands focus back to whatever `l` was pressed from, which has to be read *before* the hide: hiding a subtree holding `document.activeElement` drops focus to `<body>`, and the next Tab then restarts at the top of the page. Only a keyboard open records an opener, so closing a panel a click opened moves nothing.
  - On narrow the panel is a bottom sheet at `--z-map-overlay`, under both the scrim and the drawer, so `l` closes the drawer first — the same reason `#numbersBtn` does.
- `#numbersPanel` ([js/numbers.js](public/js/numbers.js), counting in [js/census.js](public/js/census.js)) counts picked object types at four tiers at once; the screen tier is the cell under the *view center*, so it listens for `view-changed` — dispatched from `scheduleHash`'s debounced timer, the one funnel every pan, zoom and selection settles through — rather than for any pointer event.
  - A screen's objects bucket by the world cell their top-left corner falls in (`tlvCell`, the same cell rule destination resolution uses — the screen list's inventory rule), so the surfaces agree on what a screen holds and the bucketing cannot move with the pitch; counts ignore the category display filters the way search does, and follow the demo setting, tallying what hidden paths hold as a footnote.
  - The screen list keeps bottom-left and this panel bottom-right, so a desktop holds both; on narrow both become bottom sheets, so a `float-opened` event lets whichever opens close the other — narrow only, by design.
- `#anchorTip` ([js/anchortip.js](public/js/anchortip.js)) explains any element carrying a `data-tip` attribute. The attribute is the entire interface — there is no registration call and none is wanted; a class like `.gloss` is only the visual cue, so a new consumer writes an attribute and no JS.
  - It is the sidebar's one tooltip: an `.actbtn` writes a `data-tip` and never a `title`, pinned in `tests/unit/markup.test.js` with the shape — each line capitalized and punctuated, describing the control or naming the gesture it wants (the ruler and route rows ask for one), and state-neutral, so a toggle's tip reads the same with its mode already up: `#graphBtn` keeps a noun phrase because a press-describing tip would lie while the diagram is up. A `title` remains where its words repeat the element's own `aria-label`, on the icon buttons and the minimap; and, still explaining rather than naming, on the place chip, the route bar's two link buttons and the world graph's two saves.
  - `syncMenu` hides an open tip when the drawer closes, the pointer's half of the focus move beside it. A mouse needs no such call, `pointerout` firing when an element leaves from under the cursor; the tap is what does, being the one gesture that shows a tip and then activates what it sits on, so on narrow a sidebar button can take its own anchor off-screen.
  - Because an attribute carries a string and nothing else, the line break is the content model: the first line is the summary, the rest a dimmer `.detail` block.
  - It is a `<body>` child and `position: fixed` because the surfaces that host one scroll (`#sidebar`, `#camPanelBody`) and would clip a tooltip parented inside them; that is the whole difference from `#tip`, which is absolute inside `#main` and clamps against the canvas. `pointer-events: none` is what stops it costing a click on the chrome it crosses.
  - Nothing here calls `preventDefault`: the tap must still reach whatever the anchor sits inside, so one tap both explains a field and ticks it.
  - `data-tip` is a pointer affordance and reaches no assistive tech, so a control whose tip carries a cost writes the same words into an `.sr-only` span it names through `aria-describedby`, as the JSON export button does for its mask warning; a tip that only explains stays an attribute.
  - `pointerover`/`pointerout` are filtered to `pointerType === "mouse"`: a touch fires both around its own tap, so an unfiltered pair would show the tooltip and hide it again inside one gesture.
  - Leaving is asked of the anchor (`anchor.contains(relatedTarget)`) rather than re-resolved from the attribute, so an anchor with element children doesn't flicker as the pointer crosses between them.
  - Check the placement against the bottom edge, where it flips above the anchor, and at 320px, where the width clamp engages.
- [js/dialog.js](public/js/dialog.js) holds what every dialog shares: `trapDialogKeys` keeps the keyboard inside the open one, and `openDialog`/`closeDialog` toggle its `.open` class while an open dialog stands on a history entry of its own, so the back button closes it exactly as Escape does — going back is a phone's usual way out, and the press would otherwise leave the site, which on a first visit means leaving it with nothing to come back from.
  - The entry carries the URL it was pushed on, so the traversal that closes the dialog fires no `hashchange` and moves nothing on the map. The pending view write is flushed first (the `dialog-opened` event, which [js/navigate.js](public/js/navigate.js) answers), or a pan settling onto that entry afterwards would make the same press undo the pan as well.
  - A close by any other route spends the entry with `history.back()`, so the visitor's next press is theirs again — and only while the pushed state marker says it is still the entry on top. The back press's own close is the one that must spend nothing, which is why the handler drops the entry before closing.
  - One entry and one close serve every dialog, two never being open together, and nothing is wired at import: the module has to stay importable in bare Node.
  - Never in an embed, whose entries land in the host page's back stack, where a dialog of ours has no business.
- `#about` ([js/about.js](public/js/about.js)) is on the `.overlay`/`.dialog` + `trapDialogKeys` pattern, and the first to hold links, which is why the trap's tab set counts `a[href]`: the others hold only controls, so widening it changed nothing for them.
  - Its prose is static markup rather than built by the module, so the notice is in the page source with scripting off, and it is deliberately not `.chrome`, so it survives an embed.
  - The RetroAtlas line says *part of*, never *powered by*: the two sites share an identity and no code, so wording that implies a common engine would claim something untrue.
  - It states no licence, and that is a decision rather than an omission: the repo holds code written here, one vendored file under another author's copyright, and artwork this project cannot license at all, so a single line of terms in the app would claim all three.
  - What keeps two dialogs from ever being open together is not a stacking tier — the sidebar's `z-index` exists only inside the narrow media query — but that an open overlay covers every other opener and `trapDialogKeys` swallows keydown in the capture phase, which is why `?` does nothing behind one.
- `#whatsnewFilter` ([js/whatsnew.js](public/js/whatsnew.js)) builds the What's New tag row from the tags `changelog.json` actually carries rather than from a list in the code, so a new tag needs no JavaScript.
  - Give it a colour rule or it takes the dim default, and add one word to `tests/unit/changelog.test.js`'s tag set, which is the only thing standing between a typo'd tag and a phantom chip nothing catches.
  - The chip's *fill* is what says on or off, because the text colour belongs to the tag. Do not reach for opacity: `fixed` is already dim, so fading it says nothing.
  - `flagship` is an entry's second axis rather than a fourth kind: a `"flagship": true` beside the kind it keeps, a chip appended after the sorted kinds so it lands where a sorted fourth tag could not, and a badge beside that kind on the entry (`labelsOf`, the one place in the module that names it).
  - A flagship answers to **its own chip alone**, which is what lets the three kinds switch off and leave the flagships by themselves. It cannot also answer to its kind's chip: every flagship is new, so an entry surviving on either label would leave the flagship chip inert, and one needing both would make the kinds' chips hide what the flagship chip is there to isolate.
  - `tiny` is the same axis pointing the other way: a second badge beside the kind, reached by the same `labelsOf`, and the one label in the row with no colour rule of its own — the dim fallback is precisely what a mark meaning *minor* wants to say, where flagship needed a foil. It earns no chip, and above all no default-off one: the button's dot is the newest entry's date, so a hidden newest entry would summon a reader to a panel where nothing had changed, and the near-daily rhythm of small refinements is itself what says the map is tended. Saying small is the whole of it: the entry keeps its date, its place and its prose. The two marks are mutually exclusive, test-enforced.
  - One `--foil` token, because the badge, its chip and the entry's rail have to agree on it. The chip takes it as a *fill* where the badge takes it as clipped text: `background-clip: text` would clip the chip's own fill away, and the fill is the on/off signal. Naming the on state (`[aria-pressed="true"]`) outranks the off rule from anywhere in the sheet, so off needs no flagship case at all. In the reduced-motion block the foil stays and only the sweep and the sheen go — the gradient is colour, the travel is motion.

### Editing

- Editing is a **local sandbox** over data that is never mutated. [js/edits.js](public/js/edits.js) holds an edit as a per-field delta keyed by the object's **pristine origin** (`Name@x1,y1`, with `#n` in dataset order where the tuple repeats inside the path: 10 groups in Oddysee, 41 in Exoddus), materializes a path carrying deltas as a new object over the pristine one — unedited TLVs kept by identity, edited ones fresh with `fields` spread and `extra` derived again — and stands it in the dataset by cloning its level into `data.levels[j]`. A path whose deltas are all gone materializes to the pristine object **itself**, so a revert is a swap and an unedited export's digest is structural rather than asserted.
  - Every swap of a standing level goes through `swapLevel`, in either direction: the dataset takes the level, `state.lvl` / `state.path` / `state.sel` follow by short, id and object key, a demo path's session reveal is carried over, `pathorder.invalidateEntry` lets go of both game-wide memos (the elections, and the walks seeded from them: a level's own identity cannot miss a walk whose start another level's door decides), and `data-changed` (`detail: {game, lv, pa}`) tells the page. A memo keyed on path or level identity misses on its own; one keyed on the dataset must answer the event.
  - **The navigation seam resolves by key.** `setLevel`, `jumpToPlace`, `jumpToTlv` and the level and path buttons look their target up by short and id against the dataset, and the place-search index carries places rather than level and path objects, so a captured object anywhere lands on the tree now standing. A "same path" guard (`campanel`, `fieldpanel`, `place`, `a11y`, the edit panel) compares `game/lv/pa`, never identity: `selection-changed` re-fires on the same path after every pushed hash write, and a materialization would otherwise read as a path change.
  - One guard, `validDelta`, decides whether a delta may exist, entered or restored: a field the pristine object has, and either the value it shipped with or an integer the archive's s16 word holds, labelled where `valueMap` has labels; the way back to what shipped is never refused, whatever a rebuild did to the labels. `applyFieldEdit` throws without a level map for the game, so an integer `to_level` can never be derived.
  - The store is one localStorage key, `owm:edits`, read through `settings.js`'s guarded `store` and sanitized on read by shape alone (`{game: {"LV/PA": {objects: {key: {fields}}}}}`, s16 integers) with no version marker, as the settings are: the shape is the version. A delta equal to the shipped value is removed, so the store holds differences only. Stored deltas apply inside `loadGame`'s chain, the one funnel every dataset passes through (`ensureGame`'s arrival included), after the editor sidecar has supplied the level map and the field tables the deltas are validated against — awaited there because the boot's own fetch of the pair can lose the race, and a label check against tables not yet landed waves a stale delta through. They apply by direct assignment rather than through `swapLevel`, nothing yet holding a dataset the page has not seen; `validDelta` refuses at load what a rebuild moved (an object, a field, a label), and a delta the disc has caught up with is refused beside them, since it no longer differs and a per-field revert could never take it away; both are dropped from the store, and `addGame` says how many were forgotten. A sidecar or a field table that fails leaves the dataset pristine and the store untouched, and `addGame` says that too. An embed applies nothing (`setEnabled(false)` in `main.js`) and cannot arm the mode. `warmShell` names the sidecar of a game with saved edits, so an offline boot can apply them.
- [js/extra.js](public/js/extra.js) is the builder's `tlv_extra_ao` / `tlv_extra_ae` over the archive's field names: one rule per game and type naming the payload words the builder's guard counts, in word order, and the bucket read from them, with the builder's range guards, its door-number mask and its express-well alternative rule, the level short read through the sidecar's `level_short`. `tests/unit/extra.test.js` requires every shipped object to re-derive to its committed bucket, key order included (the display renders `extra` in insertion order), which is also the proof that the archive carries everything navigation reads. Key presence is semantic downstream (`destOf` forks on `view1_cam != null`), so a branch leaves a key out rather than zeroing it.
- **Edit mode** (`state.edit`) is a transient mode like the ruler: not a Display toggle, not a Setting, not in the hash, not in `SHOW_KEYS`. `#editBtn` (`aria-pressed`, the mode owning no region; `.chrome`) or `e` enters it; it refuses under `body.embed` and while the world graph is up (whose `MAP_KEYS` swallow `e`), leaves when the graph opens, and shares the click with the measuring tools by a mutual exclusion that runs both ways: `syncShow` leaves the mode when a tool arms, and the sidebar disarms the tools on `edit-changed`, the mode's own notification (`graph-changed`'s shape), which is also what takes the drawer off the map on narrow. The panel imports no module that imports it: `setEditMode` and `selectObject` are reached from above, and what the mode asks of the surfaces it shares the map with rides the event. It arms the level map for the game in hand from the editor sidecar and re-arms on a game switch.
  - The button and the key wait on the `editObjects` setting (off by default, under Objects and fields, bound like every boolean), which **arms the mode and never gates the data**: stored deltas apply and are marked whatever it says, so a visitor's map cannot change under them by flipping it. Turning it off leaves the mode; `editpanel.js` hides the button and refuses `setEditMode(true)` off `getSettings()`, and answers `settings-changed` for the flip. The setting's row is also where the device's edits are counted and forgotten, `#editsHeld` shown only while the device holds some; a `.st-row` is `display: flex`, so its `hidden` needs the `[hidden]` rule.
  - `state.sel` is the selected TLV, re-pointed by `swapLevel` and cleared on a real path change. A canvas click in the mode selects the marker with the smallest `max(w,10)·max(h,10)` over `drawBox`, ties to the last in dataset order (the one painted on top), and never follows; a screen-list row selects as well as jumps, a keyboard activation (`e.detail === 0`) moving the focus onto the panel. The selection outline is a transient drawn whatever `markerShown` says, as the highlight is; an **edited** marker's outline is drawn in the marker pass, outside `transients`, so an image export carries it, and an unedited path's exports stay byte-identical.
  - **Edited state is marked wherever it shows**, exports included, which is the Ruled-out section's rule applied locally: the marker's outline; one line naming the changed fields in the tooltip, the screen-list row and the search hit (`editedFields`); `.edited` and `EDITED_NOTE` on the path button, the chip's tag and the place panel's line with its revert; the a11y sentence's clause (`placeSummary`); and every export name — `-edited` after the kind on the two PNGs and the JSON, and after `-demos` on the graph's SVG and PNG, whose title and node marks say it too, the flag read off the built nodes like `demo`. A copied object link names the pristine origin and its toast says the link opens on the shipped object.
  - `#editPanel` ([js/editpanel.js](public/js/editpanel.js)) follows the numbers panel: `hidden`-toggled, `role="group"` named by its title, the `float-opened` handshake — mutually exclusive with the numbers panel at every width, the two sharing a corner — and a bottom sheet on narrow. It shows every archived field (never `visibleFields`, `HIDE_WHEN_ZERO` or the picker: an editor shows the archive), a `<select>` over `valueMap` or an s16 number input, a `LIVE_WHEN`-closed row dimmed, and "shipped: N" with a ↺ beside a field that differs; a commit re-renders through `data-changed`, the control being worked keeping the focus.
  - **The trail is a trail of the store, never of the map.** A step is what a hand did to a path's deltas through the two funnels, `applyFieldEdit` and `revertPath`, and the trail holds the path's store entry as it stood before each one, cloned because the funnels write into the live entry; it is kept per place (`game/lv/pa`) and for the session only, while the edits themselves persist. `undoEdit` / `redoEdit` put the held entry back into the store and swap, the way a revert does, so every surface follows through the swap that exists and nothing downstream knows a trail is there; a later slice's edit is undoable the moment its funnel records a step. A boot apply and an orphan drop are no steps, an edit to the value already standing is no step and no swap, and `forgetAll` empties every trail. The keys live in [js/editpanel.js](public/js/editpanel.js): Ctrl/Meta chords never reach the map's key handler, and the panel refuses them in a form field, where the browser's own undo keeps the keystroke.

## Format gotchas (hard-won)

- Both games address cameras on a grid coarser than the screen, and in both the visible screen is a **368×240 window of world units** inside the cell, world units being PS1 screen pixels and the artwork 1:1 with them. AO's cell is 1024×480 with the window at +256/+120 (camera centers at `cell*1024+440`, `cell*480+240`); AE's is 375×260 with the window at +0/+0. The viewer gets all of this from the `geometry` object in each data file, so never hardcode per-game numbers in drawing code.
  - The authorities are `Map::Get_Camera_World_Rect_481410` (AE, which states the 368×240 box outright) and AO's `Rect_Location_Relative_To_Active_Camera_4448C0`, whose ±184/±120 test around the camera center is the same box. **Do not read AO's own `Get_Camera_World_Rect_444C30` as the window**: it returns a 640-wide box, which is the PC screen width leaking into PSX-space coordinates.
  - Everything outside the window is addressing slack the game never renders and the player never occupies: a camera change teleports the character across it, preserving the within-cell offset (`VOnPathTransition_401470` in AO, `vOnPathTransition_408320` in AE). Level authors still parked objects and ran collision lines through it, so the packed layout draws those over a neighbouring screen, which is what `offScreen` marks.
  - `cellW`/`cellH` are the pitch screens are drawn at, not a scale: a screen's interior is always 1:1, and the pitch being narrower than the cell is what folds the slack away. Giving `visW`/`visH` the whole cell rather than the window is what turns that pitch into a squash, dragging every object and collision line toward its screen's top-left corner by an error that grows with the distance from it.
- PS1 cam images are 12 MDEC strips: `u16` length prefix + BS v3 frames in AO, `u32` prefix + BS v2 in AE; `cam2rgba` auto-detects the framing. Decoded strips assemble to 384×240 but only 368 columns are real (macroblock padding, cropped at build time).
- FG1 foreground blocks: on the discs a partial chunk carries its own RGB555 pixels in **both** games, and every Exoddus block sits inside an LZ-compressed sub-stream — 798 of its 802 cameras carrying FG1 open one and not one block lives outside one, where 332 of Oddysee's 340 open one; `decode_fg1` reads a block at either depth.
  - The per-row `u32` bitmask form, and "Exoddus never compresses", are **PC** facts. relive encodes the second as an outright `ALIVE_FATAL` on meeting `eStartCompressedData` in AE mode, which is the assert a PlayStation cam of either game dies on, `CamConverter` reading them all as Exoddus; the builder reading the first cost Exoddus 97% of its foreground until it was measured.
  - `decode_fg1` reports whether it walked clean and the build prints a line per FG1 stream where it did not. A bail at any depth counts, since the outer stream reaching its own end marker says nothing about a sub-stream abandoned inside it, and losing the stride only ever showed up as a thinner mask — which looks like a screen with little foreground on it rather than like a bug.
- TLV records: 0x18-byte header with payload at +0x18 in AO; 0x10-byte header with payload at +0x10 in AE. Door numbers are only unique **per camera** — a target door must be resolved inside the destination camera or same-screen door pairs cross-wire.
- TLV type ids are per-game (Door is 6 in AO, 5 in AE; numbers overlap with unrelated types). Match objects by `name` in shared code, never by numeric id — except wells, whose names also differ per game (AO `WellLocal`, AE `LocalWell`) and whose arrivals can be either well type: well pairs match by the `well#` field alone, camera-bounded like the engine's arrival scan.
- An express well carries two destinations, one for each state of the switch it answers to (`disabled_well_*` / `enabled_well_*`, reaching the viewer as `to_*` / `alt_*`).
  - Either state can be a dead end, and a dead end is written two ways: naming the well's own id, so you drop back out of the well you entered, or left unpointed at the address the fields were born with.
  - `destOf` therefore prefers the state that *lands on another object* over the one that merely differs from the current path, since a dead end always differs. A state naming the well's own camera is a ride like any other when another well answers to it (the Slig Barracks hub pairs 6↔1, 5↔2, 8↔4, 7↔3 within one screen), and a bounce-back only when nothing but the well itself does.
- A destination whose level field was never set reads as level 1 (AE: Necrum Mines) while its path and camera keep the values that were right for a link inside its own level, so the triple looks plausible — 61 AE links name the Mines from another level and not one of them means it (23 naming `MI P0`, 28 the opening screen).
  - `destTrusted` ([js/model.js](public/js/model.js)) believes a destination only where the partner it names is there to be found, and gates the follow, the tooltip's destination lines, the arrow stubs and `computeEntryPaths` alike.
  - A link naming no partner (`PathTransition`) has nothing to check and stays trusted wherever it points — that is what lets AO's two main-menu links follow into `S1`, whose grid the decomp does not tabulate.
  - `wayThrough` composes the two with the one guard everything reading the level graph needs: a hand stone's view is not a way through. `destOf` mints a destination out of `view1_*` and a view names no partner, so `destTrusted` believes it wherever it points, and a sight left in can elect a level's entrance or make the room it shows reachable. No view survives into consequence on either game's shipped data — not because the predicates filter them out, but because every one that passes all three then names the path it already sits on, which each caller drops for its own reason. That is why the guard has to live in one place: nothing in the sweeps fails when a caller forgets it, and `map-data.test.js`'s own cross-level walk omits it to this day with no consequence. Whether the path a destination names is one the map holds stays the caller's question, since the connection stubs deliberately label an off-path destination the level graph drops.
  - No destination in either game now names a level the map does not render, so the tooltip's off-map clause is unexercised by the shipped data and kept for the subset build that reaches it: a `--levels` tree still holds links naming no partner that point out of it, and the clause is what stops one promising a follow into nothing.
  - The partner check is cross-level only: `resolveTarget` is camera-bounded with a path-wide fallback, so within a level an unresolved partner is that strictness rather than bad data, and dozens of sound same-level follows depend on it.
  - A partner *is* found when nothing at all was set — level 1, path 1, camera 1, pair id 0 is a real screen holding a placeholder numbered 0 — so `targetAt` reads that whole address as the absence it is.
  - Key it on the level id, never on the pair number alone: AO's Monsaic Lines wells ride to `D1 P1 C1` and `F1 P1 C1`, the Paramonia one arrival well 0 and all, and are genuine.
  - Both the entry sets (AO 18 slots, AE 14) and the cross-level follows (AO 19, AE 12 — every crossing the shipped data can follow, which is one short of the games' own: Necrum Vaults to FeeCo Terminal 1 happens in a cutscene and no well pairs for it) are pinned in `tests/unit/map-data.test.js`; the phantoms used to badge four real Mines paths as entry points and to send 26 wells to the Mines from across Exoddus.
  - One probably-genuine link pays for the rule, and shows one-way rather than not at all: `BR P10`'s `Door@500,860` names `MI P24`, an address that read inside the Brewery lands on `BR P24`'s `door# 10`, which points back at it. It is the only link in either game a local re-read would recover, it never followed before the check either, and the `BR P24` side still does — so leave it.
- A BirdPortal's destination words are live only when its `portal_type` is travel: a worker (rescue) or shrykull portal dies where it stands and never changes the map, so its level/path/camera fields are dead data — in Exoddus near-universally the unedited 1/1/1 default, which would read as a link to Necrum Mines P1 C1; in Oddysee all but one zeroed, which would read as the menu level `S1`.
  - Both `tlv_extra_{ao,ae}` withhold `to_*` for non-travel portals; the raw words still reach `fields`.
  - The same trap points the other way for the Shrykull countdown: every portal ships `mudokon_amount_for_shrykull`, near-universally at the unedited 1, and only a shrykull portal ever reads it, so `LIVE_WHEN` in [js/fields.js](public/js/fields.js) gates it on the portal's own kind.
- A TLV carries two decoded buckets. `extra` holds *derived, semantic* fields the viewer's navigation logic reads directly (`to_level`/`to_path`/`to_cam`, `door#`, `well#`, `portal`, `view*_*`, …) — hand-written per type in `tlv_extra_{ao,ae}`, since resolving level ids and pairing doors/wells isn't a raw dump.
  - `fields` holds the *complete raw archive* (every field, s16, dev name) for gameplay types, schema-driven.
  - The display writes both, so a key in both buckets prints its value twice — where the archive grows to cover a word `extra` hand-decodes under the same name, `extra` gives it up (AE's express wells did, for `switch_id`); a twin under a different name is a naming question, not a duplicate (AO's `trigger_id`, the wells' `well#`). A test pins that no object names one key twice.
  - `model.js` reads only `extra`; the field display (`extrasText` in [js/util.js](public/js/util.js), over `fieldEntries` from `js/fields.js`) shows `extra` always plus the `fields` a user's `fieldPrefs` admit, prettifying enums viewer-side.
  - `fields.js` `visibleFields()` is the single indirection: "default", "show more" and the per-type picker (`js/fieldpanel.js`, writing the per-game `fieldPrefs.byType`) are just which set it returns. Search is the exception: it asks for `"all"` and gets that string back rather than a set, which `fieldEntries` special-cases.
  - Two value rules sit under that policy, both applying however a field was admitted: `HIDE_WHEN_ZERO` drops a field whose 0 means absent (an unwired switch id, a flag nothing set), and `LIVE_WHEN` drops one the engine reads only when a sibling field says so, which the value alone can never tell you. A gate has to open on some shipped placements and close on others in each game that places the field, pinned in `tests/unit/fields.test.js` — a rule nothing satisfies hides its field everywhere, and a predicate naming a sibling the type doesn't carry reads the same.
- A message table's strings are 4-byte aligned, so splitting its blob on NUL mints a phantom empty entry per padded string and every id after the first lands wrong. Only the pointer array gives the index, and it is also where the table's empty entries live: they all point at one shared empty string rather than occupying the blob.
- Exoddus disc 1 ships `TL.LVL` as a 68-byte boot-config stub, not a LVL archive; the builder skips it. Archive reads are guarded (EOF raises, directories must fit their file) because a garbage header otherwise spins disc reads forever at end of image.
- Both Exoddus discs list every level, but each disc carries full content only for its half — the other half are stubs with path data and no cam files. Always pick the largest copy of a level across discs (the builder does).
- AE "ender" levels are the endgame revisits of areas the player returns to finish (the two vaults, FeeCo Depot, Slig Barracks, Bonewerkz) — same map geography, a distinct level id, the game's own term. The Brewery Ender (id 10, the Game Ender in the game's own level select) wears the term but is its own archive, `BM.LVL`, listed as the level `BM` and carrying no `section`.
  - The five reuse their base level's archive and the table parser deduplicates them into it, keyed on the level short, so each LVL file appears once in the level list, but TLV destinations still name the ender ids — the builder's id→short map must cover every id, not just the kept ones.
- Exoddus ships 25 paths that only its attract-mode demos play — copies of a real area, unreachable however you play — and holding a `DemoSpawnPoint` TLV is the whole rule for spotting one ([js/demo.js](public/js/demo.js), memoized per path; AO has no such type, so the rule degrades to "no demos" there with no per-game case).
  - The `showDemoPaths` setting hides them from the path buttons and from search (whose summary counts what it dropped).
  - Nothing arrives at one and no level opens on one, both pinned in `tests/unit/map-data.test.js`, so the entry marks and the connection arrows need no demo case of their own.
  - **The path in hand is always listed**: `selectPathById` reveals a hidden path for the session, which is what lets a permalink, a remembered location or a follow land instead of falling back, and is why switching the setting off leaves the path you are standing on visible.
  - That a path is a copy is written into its curated name (`[Demo] …`, test-enforced) rather than composed on at display time, so no caller has to pair a name with a marker.

## Conventions

- One concern per commit; split bundled diffs before committing.
- Everything committed reads as its final state, written once — code comments, docs, backlog items, commit messages and the shape of history alike. A follow-up that reshapes something still unpushed folds into the commit that introduced it, message rewritten to describe only what ships, rather than landing as an add-then-amend pair; narration of rounds, actors and supersessions belongs in no committed text. The test: would it read the same if one author had written it in one sitting?
- A fixup commit names the commit that introduced the text it corrects, and may sit anywhere on the branch: `--autosquash` reorders it into place. Retargeting it at a nearer commit to dodge a conflict is the one move to refuse, since that folds a correction into a commit which never carried the text. A fixup hoisted past later commits that touched the same lines can conflict, and resolving that is ordinary work rather than a reason to reshape the branch. After any history rewrite, diff the old head against the new (only the intended change may appear) and dry-run the autosquash on a throwaway branch before handing the branch over.
- Prose files (README, docs, this file) are never manually line-wrapped — let lines run long.
- A user-facing change ships its docs in the same commit — update the relevant README.md / CLAUDE.md, and add its `changelog.json` entry. Documenting the change is part of the same concern, not a follow-up commit.
- Changelog entries are curated, not generated: draft with `tools/changelog.py`, then rewrite into a player-facing headline + detail. The feed is a date-stamped journal of the site, not a highlights reel — any user-visible change, however small, is welcome on it; what stays out is internal work players can't perceive (refactors, tooling, CI).
- No game owns unsuffixed defaults: everything game-specific carries `ao`/`ae` in its name (files, JS globals, env vars, URL hashes). Do not reintroduce unsuffixed names for AO just because it came first.
- Generated JSON is pretty-printed (`indent=1`) so history stays diffable; keep the format stable.
- Prettier owns js/css/html formatting (`.prettierrc`: printWidth 100, defaults otherwise; exemptions in `.prettierignore` — `public/js/config.js` keeps its hand-aligned tables, `public/levels/` keeps the emitter's bytes, JSON and Markdown keep their own formats).
  - The version is pinned exactly in devDependencies because output is version-dependent (like oxipng for the PNGs); bump it deliberately: upgrade, reformat the tree in a dedicated commit, and add that commit to `.git-blame-ignore-revs`.
  - New clones opt blame in once with `git config blame.ignoreRevsFile .git-blame-ignore-revs` (GitHub reads the file automatically).
- Format only the staged files before each commit, so the commit doesn't drag in formatter drift from unrelated files:
  ```
  git diff --cached --name-only --diff-filter=ACMR | grep -E '\.(js|css|html)$' | xargs -r npx prettier --write
  ```
  then re-stage what Prettier changed. Never run whole-tree `npm run format` as part of a normal commit — whole-tree formatting belongs in its own dedicated commit (CI runs `format:check`, so drift can't accumulate).

### Stylesheet vocabulary

[css/main.css](public/css/main.css) has one shared vocabulary and a new surface reaches for it rather than restating a treatment. A value becomes a `:root` token when components that are otherwise unalike have to agree on it; a treatment that recurs whole becomes a class; a repetition that is only two numbers coinciding is left alone.

- **Controls inherit the page font.** Browsers hand `button`/`input`/`select`/`textarea` a font of their own, so a reset beside the `*` rule gives them the page's, and no rule below it has to name a family to undo that — the three that do name one are asking for something (`--serif` for the What's New masthead and its dates, `inherit` on `kbd` to escape the UA's monospace).
  - Reach for `font-family`, never the `font:` shorthand, which also resets size, weight and line-height — measured, that takes the level and path buttons from 12px to 13px and the close glyph's box from 18x24 to 12x19.
  - `font-family` alone still costs one pixel of height on the 11px controls (the search scope buttons and the search results' "show more" rows), where the page font's normal line-height is a pixel taller than the UA font's.
- **Colour and depth are tokens; size is not.** `--over-rgb` is the one near-black everything floating over the map is tinted from, each surface picking its own alpha over it, `--surface-float` the opaque tier of it the tooltips and the floating panels share, and `--shadow-float` / `--shadow-modal` the two elevations.
  - `--dim` is the last step down in text colour and there is no token below it: something needing to sit under dim fades what it has (`opacity`, as the path buttons' nickname does) rather than minting a fainter grey, and takes the rest of the separation in size, a lever that costs no contrast at all. The tooltip's offscreen note is the deep end of that, faded past the contrast ordinary text keeps — which it can afford only because it restates what the marker's dotted outline and the screen list's `offscreen` tag already say, so a reader who cannot make it out is told anyway.
  - Radii and paddings are deliberately left alone — a scale over 5/6/8px would buy indirection rather than agreement, since nothing breaks when two components pick different ones.
  - `--corner-w` is what the rule's own exception looks like: the room the map's top-right buttons need, which the place chip and the world graph's bar both have to leave them. Something does break when those two disagree — the bar's own controls land under buttons that are painted above it, unclickable.
- **Stacking tiers** are the `--z-*` tokens in `:root`, declared low to high so the block's own order states a system nothing else in the repo did. A surface takes a tier from there rather than writing a bare `z-index`, and `--z-map-chrome` sits above `--z-drawer` because it has to beat the drawer it opens over.
  - `--z-tip` is directly above the map overlays because a hover tooltip is the affordance the pointer is actively producing and must not be clipped by a surface that is merely present; `pointer-events: none` is what makes that safe, since nothing underneath loses a click.
  - Do not try to solve that with `#cv`'s `pointerleave`, which fires only while the *cursor* is inside an overlay: the tooltip's box sits 16px down and right of the cursor and can be 340px wide, so it reaches onto the map overlays from outside them.
  - It stays *below* `--z-map-chrome` and the corner buttons do still cover it: a flat scale cannot put the tooltip over chrome while keeping it under the drawer chrome exists to beat, and being covered by a corner button is the better of the two failures.
- **A dialog** is `.overlay` wrapping `.dialog`, holding `.dlg-head` / `.dlg-body` / `.closebtn` (worn outside the dialogs too, at the class's size or one the surface sets), with `openDialog`/`closeDialog` toggling `.open` on the overlay.
  - The state is on the element rather than on `body` precisely so the stylesheet never names a dialog — another costs no CSS at all unless its width differs from the fallback in `width: var(--dialog-w, 460px)`, written as a fallback rather than a declaration so the token doesn't inherit into every descendant.
  - The reduced-motion group has to name `.overlay.open` beside `.overlay`, because the open state carries a transition that one class cannot outrank.
- **`.linkbtn`** is the shared treatment for a no-chrome underlined text button.
  - It declares no font, deliberately — size is left to the surface (11px in the footer, 12px in the route bar, the heading's own for a heading tool, the UA default in the graph bar), and a `font:` shorthand on the class would reset the weight and line-height of every member that sets no font of its own, while the ones declaring `font: inherit` would not feel it at all.
  - Hover is guarded with `:not(:disabled)` for the members that disable themselves, a disabled one staying dim under the pointer; `:focus-visible` takes the same accent, for every member.
- **`.actbtn`** is the sidebar's full-width action button, the bordered pill spanning the column that the world graph, the edit mode, the numbers panel and the exports open from, worn by the export disclosure's `<summary>` as well as by buttons. It names `line-height: normal`, the one thing a summary does not share with a button, so the pill stands the same height on either. Hover is guarded with `:not(:disabled)` and a disabled member dims, since the exports disable themselves while they run; `#graphBtn.on` and `#editBtn[aria-pressed="true"]` are the states written on an id, each that button's alone.
- **`.rowbtn` and `.listhead`** are the full-width row that behaves as a button, with its hover and `.active` states, and the small uppercase divider above a list's rows; a surface takes both or the divider alone. Each is added alongside the component's own class (`rowbtn cp-row`, `listhead shead`), so what is shared and what is local stay legible in the markup.
- **`.checkrow`** is a checkbox and its wording on one line, wherever one is offered.
  - Selection is suppressed on the class rather than per surface — a label you click repeatedly should not select its wording anywhere — while padding stays per-surface, which is what keeps the narrow query's fatter touch targets on the sidebar surfaces and off the dialog's rows.
- **`.sr-only`** is the clip that takes an element out of the layout and leaves it in the accessibility tree, worn by anything with something to say and nothing to show. `display: none` and `visibility: hidden` both take an element out of that tree, so a region hidden either way announces nothing while the page looks exactly right — which is why the recipe is a clip and why it sits with the resets rather than with a component, having none of its own.

### Code comments

- **Default to no comment**: A comment earns its place only by recording a durable *why* the code can't show: an invariant, a constraint, a non-obvious trade-off.
  - Keep them generic enough that a routine change doesn't force a comment edit — put a per-item note *inline on the item* (`"deaf", // ignores Abe's speech`), never in a const-doc that re-describes the set's members (that rots the moment you add one).
  - Don't name consumers or other modules ("used by X", "the picker reads this"); don't restate a constant's value or units.
  - Comment footprint matches code footprint — a concern touched at one line gets one comment there, not a header paragraph.
  - Before committing, reread each comment and cut any that restates the code, names something that could be renamed, or would lie after a tune/refactor — an absent comment never goes stale.
- **No inter-diff comments**: Comments must describe the code as it is now, not how it got here. Don't write "extracted from X", "moved from Y", "duplicated here", "was previously in Z". A reader who has never seen the git history should find every comment meaningful.
- **Peer items get peer prose**: When a comment or code block enumerates parallel items — payload fields, switch cases, sibling merge loops — treat them uniformly.
  - Don't attach a justifying clause to one item ("…and seen marks (s) — without these, restored unlocks would re-badge as new") while its siblings carry none: the asymmetry falsely flags that item as special, and the odd one out is invariably the one just added — meaning the sentence is a diff justification aimed at the reviewer, not a description aimed at the reader.
  - Same for code shape: when the sibling loops above yours are uncommented, the new one doesn't get an explainer either.
  - The why-this-was-added story belongs in the commit message in short form.
  - Test: would the prose look the same if every item had been written on the same day, by one author? If your addition carries a defense its peers lack, delete the defense.
