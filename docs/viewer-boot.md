# Viewer: boot, caches and settings

- Display against Settings is a taxonomy, not a layout choice. Display is what is drawn on the map right now ([js/sidebar.js](../public/js/sidebar.js)'s toggles) — overlays and modes flipped mid-reading, carrying the keyboard keys, the reset button and the "Remember display & object filters" snapshot — while Settings is how the app behaves across visits (persistence, naming, field presentation). A lens that changes marker semantics (pens turn barriers from meta boxes into posts, and the ruler snaps to the post line) is still Display: from the user's seat every reading aid is the same "show me this" flip, and the semantics distinction is implementation trivia.
- [js/data.js](../public/js/data.js) owns which datasets there are and when each is fetched. The game a visit is looking at is decided from the link's own text (`bootGame`: the hash, else the remembered location, else the first id) before anything is awaited, so first paint waits on one game's data instead of both — Exoddus alone is twice Oddysee's size gzipped, and awaiting both spent the whole budget of the one on screen before a line of it was drawn.
  - `loadGame` memoizes one promise per dataset, so a link into a game still in flight awaits that fetch rather than starting a second; the game the visitor is not looking at is asked for at `priority: "low"`, which is not a courtesy to the artwork so much as a refusal to outrank it: an ordinary `fetch` is high priority and the cam bitmaps, never being in the document, are low, so the default would have put the hydration ahead of every screen on the map.
  - `index.html` preloads the **default boot dataset alone**. Preloading both was the whole cost: a saturated pipe transfers the same bytes whatever the order, so what a preload buys is the module graph's latency rather than bandwidth, and a second one spends the first one's bytes ahead of it. Keeping the one is worth a third of the win, and the asymmetry is real — an `AE` permalink gains nothing, since only an inline script could pick the preload and it would restate the boot rule in HTML.
  - `addGame` in [js/navigate.js](../public/js/navigate.js) is per dataset and dispatches `games-changed`; every surface that reads more than the current game answers it — search re-runs an active query, an open type card re-renders its per-game counts, the offline panel gains a row. Buttons are appended as datasets land, so the game the visitor came for leads the row and nothing has to insert into an order.
  - A search in the gap ([js/search.js](../public/js/search.js)) says which dataset is still coming. Without that, a query only the other game can answer (`zulag 14` is Exoddus's alone, Oddysee's zulags stopping at 4) reads as a map that has never heard of the place, and then silently gains 10 hits.
  - `applyHash` awaits a dataset the hash names rather than rejecting it, so a permalink pasted into the gap lands, and the boot fallback stops reading a remembered location's unfetched game as a level that no longer exists and clearing it. The pending view write is held across the wait, since a debounced one landing on the address bar would replace the link being answered and leave no `hashchange` to recover it; a hash that changed under the wait is left to the newer link.

- `sw.js` (in `public/` beside `index.html`, so it is served at the site root; a classic script — not an ES module; linted with `serviceworker` globals, no unit tests by design) holds two caches with two disciplines: `cams/**/*.png` cache-first in the Cache API, because GitHub Pages re-stamps HTTP validators on every deploy, and the app shell (page, code, top-level JSONs, icons) network-first in a fixed `shell-v1` bucket that serves only when the network fails — online loads stay as fresh as with no worker, and the map still opens offline.
  - It is opt-in: the worker can't read settings, so `settings.js` gates it on the `cacheMap` setting (off by default) — enable registers the worker and creates the `cams-on` marker bucket the worker checks before storing; disable deletes every `cams-*` and `shell-*` bucket and unregisters. The marker, not unregistration, is what stops caching immediately, since an already-controlling worker keeps handling fetches until reload and module state wouldn't survive an idle-worker restart.
  - Its `CACHE_NAME` is written by the builder: a content hash of `public/cams`, so regenerating a PNG expires the cache and a build that decodes nothing leaves it alone. Both games are hashed however few levels were built, since one worker serves both; a scratch `--out` holds no worker and stamps nothing. Commit the rewritten line with the artwork.
  - The shell bucket carries no such stamp: network-first entries self-refresh on every successful load, so the name only moves to retire an incompatible storage scheme. An app-page navigation stores and matches under the one key `index.html`, which is what lets `/`, `/index.html` and `/?embed=1` all boot offline — a navigation anywhere else on the origin never reaches that key, a root-level page falling to the ordinary shell rule under its own URL, so the SEO statics (og-image, robots, sitemap), which match no rule at all, can neither displace the page nor enter the cache. A redirected response is never stored: a navigation answered from one would throw rather than render.
  - The worker only caches what passes through it, so a user enable always warms — `warmShell` re-fetches everything the page already pulled (from its own performance entries, plus the document and the datasets by name — a resource still in flight has no entry yet, and the hydrating dataset is exactly that) once the worker takes the page, and offline works from the enabling visit onward; a re-enable follows a sweep, so it must warm whatever still controls the page. The boot call never warms: a controlled page's own boot fetches are already the refresh.
  - After rebuilding cams locally, use DevTools → Application → "Bypass for network" (or Clear site data) to see the new images.
- [js/offline.js](../public/js/offline.js) is the worker's page-side half: the shell warm on enable, and the Settings panel that stores a whole game's artwork at once, so a place nobody has browsed is kept too.
  - It downloads by plain `fetch`, letting the worker store each response on its way through, which is why the body has to be read (the stored copy is a clone of it) and why nothing starts until the worker controls the page: an uncontrolled page's fetches are spent for nothing. A file that fails stays missing and the next run picks it up, so re-clicking is the resume.
  - Nothing is remembered about what was downloaded: the rows count the cache's own keys against the game's file list (the cameras and masks `camFiles` lists, plus the sprite sheets the sprites sidecar names once it has been fetched), so a sweep, an eviction or a rebuilt cache name can never leave the panel claiming artwork that is gone. `MAX_ENTRIES` in the worker is therefore a feature constraint rather than a browse cap, since a cap below both games' complete artwork would evict the head of what a download just fetched; `tests/unit/offline.test.js` pins it.
  - `persist()` is asked for on a download because artwork this deliberate should outlive the browser's housekeeping; it is advisory (Chrome grants it on engagement alone) and nothing depends on the answer.
  - A registration that fails costs the browsing case only cached artwork, but it costs this panel everything, so `workerRegistered()` keeps the attempt's answer: the download says so at once rather than timing out on a worker that is never coming, and the exception goes to the console, the only surface with room for it.
  - Progress is a `progressbar` and deliberately not a live region: the percent moves several times a second, and the finishing toast is what announces.
- `initSettings`'s `bind` is the funnel for the boolean settings: seeding the checkbox, persisting, marking a row whose value isn't its default, and the apply callback all hang off one call, so a new boolean setting gets the lot by being bound.
  - The show-more checkbox flips `fieldPrefs.mode` rather than a boolean, so it is wired by hand and is the one control that has to be updated alongside `bind`.
