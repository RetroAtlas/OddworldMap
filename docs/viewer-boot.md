# Viewer: boot, caches and settings

- [js/main.js](../public/js/main.js) is the boot, in two parts. The first runs before anything is awaited and wires the page: whatever a module has to register, set, build or fetch as the page boots it does in the `init` it exports, its top level holding declarations alone, and `main.js` calls every init once. The second waits on the sidecars and the boot game's dataset, hands each table to its module (the annotations ahead of the path buttons' labels, the field tables ahead of any tooltip or search hit), then adds the game, sizes the canvas and applies the hash.
  - The order of the init calls is behaviour: listeners on one target hear an event in the order they were registered, so the list is the order the modules answer `selection-changed`, `data-changed`, a key and the rest in. Nothing derives that order from what each module needs, so a call moves, and a new one joins, only with a look at every event the module shares with those it passes.
  - One dependency in the list is known and held: `initSidebar` greys the toggles whose needs are unmet before `initSettings` has seeded the Settings rows, one of which a toggle needs, so `main.js` calls `syncNeeds` again behind `initSettings`, and `tests/browser/motion.spec.js` boots a visitor who keeps the animation off to find Patrols greyed. What seeds the first paint is in the first part by construction: `initSidebar` fills `state.show`, merges the kept filters into the categories and sets the barrier gate, and `initInteraction` stands the sidebar open, so the map's box is at rest before a view is placed by its size. A handler that has to yield to one registered after it says so where it does, as the world graph's key handler leaves Escape to an open dialog's trap.
  - `initWhatsNew` is async and the boot does not wait on it: the button comes up once the feed is read.
  - What a module does as it is imported is look things up, none of which changes the page and all of which the module script standing at the end of `<body>` makes safe: a handle on a static element through `$`, a media query, a button's own label, and in [js/ui/dom.js](../public/js/ui/dom.js) the stylesheet's tokens. A primitive with nothing to hear until it is first used wires itself on that use and has no init: [js/ui/dialog.js](../public/js/ui/dialog.js) its popstate on the first dialog it opens, [js/ui/keycap.js](../public/js/ui/keycap.js) its keyup and blur on the first cap lit. The registrations of the pure folders, a brain into the engine's tables and a sprite rule into the kit's, run at import too and touch no page, which their import in bare Node holds.
  - `tests/unit/imports.test.js` holds the rule: a top-level statement in a module outside the folders and files it imports in bare Node fails it, the boot's own apart, as does an init that `main.js` does not call or calls twice.
- Display against Settings is a taxonomy, not a layout choice. Display is what is drawn on the map right now ([js/chrome/sidebar.js](../public/js/chrome/sidebar.js)'s toggles) — overlays and modes flipped mid-reading, carrying the keyboard keys, the reset button and the "Remember display & object filters" snapshot — while Settings is how the app behaves across visits (persistence, naming, field presentation). A lens that changes marker semantics (pens turn barriers from meta boxes into posts, and the ruler snaps to the post line) is still Display: from the user's seat every reading aid is the same "show me this" flip, and the semantics distinction is implementation trivia.
  - The snapshot is a kept set, [js/data/settings.js](../public/js/data/settings.js)'s `getViewSnapshot`, holding only the switches the visitor has set, each until it is set back to its default or its section is reset, so a default that changes reaches whoever left that switch alone and no one who set it; a switch loaded from storage counts as set, so a default moving under a deliberate choice never flips it back. The sidebar records every change into the one live object whether or not remembering is on, so turning it on persists what the session has chosen, and the ruler and route, being tools, never enter it.
- Every Display toggle's flip dispatches `show-changed` (`detail: {key}`) from `syncShow`, so a surface that prints what a toggle governs outside the canvas, the release mark's words and tags, follows it without a repaint of its own. "Release differences" (`show.release`, on by default) is a Display toggle whose row is hidden rather than greyed while the base is in hand: it has nothing to mark there, and no other switch could make it mean something.
- A Display toggle that is meaningless without others on (Patrols without the objects shown, or with their animation off) declares them with `data-needs` naming the checkboxes, a Settings one included; `syncNeeds` in sidebar.js greys it and writes the first unmet need into the row's title ("in Settings" where that is where it lives), a click on the greyed row and its shortcut both toast that reason, and its own checked state survives the greying, so meeting the need again restores what the visitor had. The sprites themselves are Display (what is drawn now) and their animation a Setting (`animate`, on by default), the taxonomy above applied.
- "Label the scenery" is a Setting though it only qualifies the Object labels Display toggle: which objects deserve a name beside them is a naming matter a visitor settles once, like "Show full names" beside it, not a lens flipped mid-reading; with Object labels off the setting shows nothing, and its row says what it does rather than what it waits on.
- [js/data/data.js](../public/js/data/data.js) owns which datasets there are and when each is fetched. The game a visit is looking at is decided from the link's own text (`bootGame`: the hash, else the remembered location, else the first id) before anything is awaited, so first paint waits on one game's data instead of both — Exoddus alone is twice Oddysee's size gzipped, and awaiting both spent the whole budget of the one on screen before a line of it was drawn.
  - When the view opens with the objects shown, the boot game's sprite sidecar is asked for beside its data, through `spriteart.js`'s own sentinel so a failure is remembered; a paint at a zoom where a creature reads asks for the sheets the path's records draw from and for its foreground masks, behind the screens showing in its view, and the other game's sidecar waits for a paint that wants it.
  - `loadGame` memoizes one promise per dataset, so a link into a game still in flight awaits that fetch rather than starting a second. The game the visitor is not looking at is not asked for at boot. It waits to be let go (`releaseGames`, which settles `gamesReleased`): by the painter's `view-complete`, said once when the first view has its screens in and its sprite art holding nothing back ([docs/viewer-geometry.md](viewer-geometry.md#the-one-painter-and-the-whole-path-export)), or `GAMES_HOLD_MS` after the boot path stands where no view gets there (a file that hangs, a tab opened in the background, which paints nothing). Asked for behind the first paint, even at `priority: "low"`, it stood in the first view's way: the cam bitmaps, never being in the document, are low themselves, and its request went out just ahead of theirs. A connection serving one response at a time, as the live site's HTTP/2 does, sent its 395 KB before the first screen, and one sharing among them, as its HTTP/3 does, gave it a share of every screen and sheet of the view. On a throttled slow-4G phone the first view stands complete 2.4 s sooner over the first kind and 0.6 s over the second, its sprites 2.4 s and 0.9 s sooner (2026-11-12). Once let go it is asked for at the default priority, ahead of the rest of the path's screens, which are all that is still coming: at low priority it shares with them four to one and lands five to seven seconds later than it did.
  - Whoever reaches for the other game lets it go at once: a search, whose hits may be the other game's (`runSearch`), and a shuffle press, which draws from the games that have landed. A link naming the other game fetches it itself (`ensureGame`), and its button needs no trigger, `addGame` making one only once the dataset lands. The offline warm-up, which names every dataset, waits for the same release (`warmShell`).
  - `index.html` preloads the **default boot dataset alone**. Preloading both was the whole cost: a saturated pipe transfers the same bytes whatever the order, so what a preload buys is the module graph's latency rather than bandwidth, and a second one spends the first one's bytes ahead of it. Keeping the one is worth a third of the win, and the asymmetry is real — an `AE` permalink gains nothing, since only an inline script could pick the preload and it would restate the boot rule in HTML. Nothing is held back for it either: the preload has asked for Oddysee's dataset before the page's first script runs.
  - `addGame` in [js/navigation/navigate.js](../public/js/navigation/navigate.js) is per dataset and dispatches `games-changed`; every surface that reads more than the current game answers it — search re-runs an active query, an open type card re-renders its per-game counts, the offline panel gains a row. Buttons are appended as datasets land, so the game the visitor came for leads the row and nothing has to insert into an order.
  - A search in the gap ([js/panels/search.js](../public/js/panels/search.js)) says which dataset is still coming. Without that, a query only the other game can answer (`zulag 14` is Exoddus's alone, Oddysee's zulags stopping at 4) reads as a map that has never heard of the place, and then silently gains 10 hits.
  - A release is a dataset of its own (`loadRelease`, one per game and release): its overlay stood up by [js/data/release.js](../public/js/data/release.js) over the base **as it shipped** (`pristineLevels`, so the visitor's base edits never leak into it) through the sandbox's own pieces, an object keyed by its base origin, its `extra` derived again and an addition built from the game's type table and placed after the object its `after` names. A camera the overlay patches keeps the base's screen as its `png` and carries the release's `patches` beside it, `[x, y, file]` each, which `screens.js` composes over that screen; one the release ships whole carries its own `png`, and either carries the release's masks in place of the base's. It shares every level and path the overlay leaves alone by identity and never writes into the base, so the base dataset the game loaded is the one a switch back finds. What each object, line and screen owes to the release lives beside it: a changed object's base object and delta in a WeakMap reached through `pristineOf` (so a user edit over it still answers), and a `release` record on every path the overlay changes (its removed objects, its new and gone lines, its dropped cameras), which the sandbox's spreads carry through any edit. The level map a changed object's destinations derive through rides the editor sidecar, so it is fetched only for an overlay that changes objects. `releases.json` names what the site carries, fetched once.
  - `applyHash` awaits a dataset the hash names rather than rejecting it, so a permalink pasted into the gap lands, and the boot fallback stops reading a remembered location's unfetched game as a level that no longer exists and clearing it. The pending view write is held across the wait, since a debounced one landing on the address bar would replace the link being answered and leave no `hashchange` to recover it; a hash that changed under the wait is left to the newer link.

- `sw.js` (in `public/` beside `index.html`, so it is served at the site root; a classic script — not an ES module; linted with `serviceworker` globals, no unit tests by design) holds two caches with two disciplines: `cams/**/*.png` cache-first in the Cache API, because GitHub Pages re-stamps HTTP validators on every deploy, and the app shell (page, code, top-level JSONs, icons) network-first in a fixed `shell-v1` bucket that serves only when the network fails — online loads stay as fresh as with no worker, and the map still opens offline.
  - It is opt-in: the worker can't read settings, so `settingsdialog.js` gates it on the `cacheMap` setting (off by default) — enable registers the worker and creates the `cams-on` marker bucket the worker checks before storing; disable deletes every `cams-*` and `shell-*` bucket and unregisters. The marker, not unregistration, is what stops caching immediately, since an already-controlling worker keeps handling fetches until reload and module state wouldn't survive an idle-worker restart.
  - Its `CACHE_NAME` is written by the builder: a content hash of the cameras and masks under `public/cams`, so regenerating one expires the cache and a build that decodes nothing leaves it alone. Both games are hashed however few levels were built, since one worker serves both; a scratch `--out` holds no worker and stamps nothing. The build summary prints the new name; commit the rewritten line with the artwork.
  - The sprite sheets stay out of that hash, since they change far more often than the cameras. A game's sheets are one per family, each named for the family and for its pixels, so a changed family arrives under a new URL and is stored beside the cameras, and storing a family's sheet retires that family's others and whatever under the game's `sprites/` is no family's sheet (`SHEET`): the cache holds one sheet per family once it has been stored, and an old one stays until its successor arrives, so no list of sheets has to reach the worker. A sheet of a family no sidecar names has no successor, so it stays until the camera stamp next moves; nothing asks for it, and the offline panel counts only the sheets the sidecar names.
  - A release's own art (`cams/<game>/<code>/…`, its patches, whole screens, masks and family sheets) stays out of the hash as the sheets do, each file named for what it is (a patch for its screen and its place on it) and for its pixels, and storing one retires the cache's other copies of that release's file of the same name (`RELEASE_ART`), so a rebuilt release replaces its files one by one and a base rebuild expires none of them; the sheet rule's game match never reaches under a release's code, and no base file answers the release rule, which `tests/unit/offline.test.js` holds over every committed file. `MAX_ENTRIES` clears both games' artwork and every release's together.
  - The shell bucket carries no such stamp: network-first entries self-refresh on every successful load, so the name only moves to retire an incompatible storage scheme. An app-page navigation stores and matches under the one key `index.html`, which is what lets `/`, `/index.html` and `/?embed=1` all boot offline — a navigation anywhere else on the origin never reaches that key, a root-level page falling to the ordinary shell rule under its own URL, so the SEO statics (og-image, robots, sitemap), which match no rule at all, can neither displace the page nor enter the cache. A redirected response is never stored: a navigation answered from one would throw rather than render.
  - The worker only caches what passes through it, so a user enable always warms — `warmShell` re-fetches everything the page already pulled (from its own performance entries, plus the document and the datasets by name — a resource still in flight has no entry yet, and the hydrating dataset is exactly that) once the worker takes the page, and offline works from the enabling visit onward; a re-enable follows a sweep, so it must warm whatever still controls the page. The boot call never warms: a controlled page's own boot fetches are already the refresh.
  - After rebuilding cams locally, use DevTools → Application → "Bypass for network" (or Clear site data) to see the new images.
- A game's row in the offline panel follows the dataset in hand between downloads (`retarget`): its files are `camFiles` of that dataset, the release's patches beside the base screens they are drawn over, its whole screens and masks in place of the base's, plus the sheets of its sprite set with the release's own over the base's, so the panel counts a release as the base's files less the ones its overlay replaces, plus its own, and the size it quotes before a download counts each file at the typical size of its kind (`bytesOf`), a patch's and a release's mask's among them. `warmShell` names `releases.json`, the overlay of every release in hand and, for a game showing a release, the editor sidecar a changed object's destinations derive through, so an offline boot can stand the release up.
- [js/chrome/offline.js](../public/js/chrome/offline.js) is the worker's page-side half: the shell warm on enable, and the Settings panel that stores a whole game's artwork at once, so a place nobody has browsed is kept too.
  - It downloads by plain `fetch`, letting the worker store each response on its way through, which is why the body has to be read (the stored copy is a clone of it) and why nothing starts until the worker controls the page: an uncontrolled page's fetches are spent for nothing. A file that fails stays missing and the next run picks it up, so re-clicking is the resume.
  - Nothing is remembered about what was downloaded: the rows count the cache's own keys against the game's file list (the cameras and masks `camFiles` lists, plus the sprite sheets the sprites sidecar names once it has been fetched), so a sweep, an eviction, a rebuilt cache name or a retired sheet can never leave the panel claiming artwork that is gone. `MAX_ENTRIES` in the worker is therefore a feature constraint rather than a browse cap, since a cap below both games' complete artwork would evict the head of what a download just fetched; `tests/unit/offline.test.js` pins it.
  - `persist()` is asked for on a download because artwork this deliberate should outlive the browser's housekeeping; it is advisory (Chrome grants it on engagement alone) and nothing depends on the answer.
  - A registration that fails costs the browsing case only cached artwork, but it costs this panel everything, so `workerRegistered()` keeps the attempt's answer: the download says so at once rather than timing out on a worker that is never coming, and the exception goes to the console, the only surface with room for it.
  - Progress is a `progressbar` and deliberately not a live region: the percent moves several times a second, and the finishing toast is what announces.
- `initSettings`'s `bind`, in `settingsdialog.js`, is the funnel for the boolean settings: seeding the checkbox, persisting, marking a row whose value isn't its default, and the apply callback all hang off one call, so a new boolean setting gets the lot by being bound.
  - The show-more checkbox flips `fieldPrefs.mode` rather than a boolean, so it is wired by hand and is the one control that has to be updated alongside `bind`.
  - The settings are a kept set like the snapshot: `chooseSetting` records a boolean the visitor sets and drops one set back to its default, and `persistSettings` writes that set, and the field picks with it only while their mode is set away from its default or a type carries a pick, so a default that changes reaches whoever left the setting alone; a boolean loaded from storage counts as set.
