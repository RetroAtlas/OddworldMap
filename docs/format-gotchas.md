# Format gotchas (hard-won)

- Both games address cameras on a grid coarser than the screen, and in both the visible screen is a **368×240 window of world units** inside the cell, world units being PS1 screen pixels and the artwork 1:1 with them. AO's cell is 1024×480 with the window at +256/+120 (camera centers at `cell*1024+440`, `cell*480+240`); AE's is 375×260 with the window at +0/+0. The viewer gets all of this from the `geometry` object in each data file (the per-game block in [tools/oddmap/games.py](../tools/oddmap/games.py)), so never hardcode per-game numbers in drawing code.
  - The authorities are `Map::Get_Camera_World_Rect_481410` (AE, which states the 368×240 box outright) and AO's `Rect_Location_Relative_To_Active_Camera_4448C0`, whose ±184/±120 test around the camera center is the same box. **Do not read AO's own `Get_Camera_World_Rect_444C30` as the window**: it returns a 640-wide box, which is the PC screen width leaking into PSX-space coordinates.
  - Everything outside the window is addressing slack the game never renders and the player never occupies: a camera change teleports the character across it, preserving the within-cell offset (`VOnPathTransition_401470` in AO, `vOnPathTransition_408320` in AE). Level authors still parked objects and ran collision lines through it, so the packed layout draws those over a neighbouring screen, which is what `offScreen` marks.
  - `cellW`/`cellH` are the pitch screens are drawn at, not a scale: a screen's interior is always 1:1, and the pitch being narrower than the cell is what folds the slack away. Giving `visW`/`visH` the whole cell rather than the window is what turns that pitch into a squash, dragging every object and collision line toward its screen's top-left corner by an error that grows with the distance from it.
- PS1 cam images are 12 MDEC strips: `u16` length prefix + BS v3 frames in AO, `u32` prefix + BS v2 in AE; `cam2rgba` auto-detects the framing. Decoded strips assemble to 384×240 but only 368 columns are real (macroblock padding, cropped at build time).
- FG1 foreground blocks: on the discs a partial chunk carries its own RGB555 pixels in **both** games, and every Exoddus block sits inside an LZ-compressed sub-stream — 798 of its 802 cameras carrying FG1 open one and not one block lives outside one, where 332 of Oddysee's 340 open one; `decode_fg1` reads a block at either depth.
  - The per-row `u32` bitmask form, and "Exoddus never compresses", are **PC** facts. relive encodes the second as an outright `ALIVE_FATAL` on meeting `eStartCompressedData` in AE mode, which is the assert a PlayStation cam of either game dies on, `CamConverter` reading them all as Exoddus; the builder reading the first cost Exoddus 97% of its foreground until it was measured.
  - `decode_fg1` reports whether it walked clean and the build prints a line per FG1 stream where it did not. A bail at any depth counts, since the outer stream reaching its own end marker says nothing about a sub-stream abandoned inside it, and losing the stride only ever showed up as a thinner mask — which looks like a screen with little foreground on it rather than like a bug.
- Sprite animations are `Anim` chunks in a level's BAN, BND and CAM files, the same chunk container `parse_chunks` walks for the cameras, and [tools/oddmap/sprites.py](../tools/oddmap/sprites.py) reads them: a file header `{s16 max_w, s16 max_h, u32 frame_table_offset, u32}`, then the frames (a `FrameHeader` `{u32 clut_offset, u8 w, u8 h, u8 bpp, u8 compression}` and its payload from byte 8, whose first two words are the payload's own, type 0's first pixels, the LZ's length for types 4 and 5 and a count for 3, 6 and 7, only type 2 skipping them, the CLUT `{u32 count, u16 RGB555[count]}` beside them), the 20-byte frame-info records `{u32 frame_header_offset, s16 magic, s16 count, s16 x_off, y_off, min_x, min_y, max_x, max_y}` plus `count` eight-byte callback points, and the animation tables `{u16 fps, s16 num_frames, s16 loop_start, u16 flags, u32 frame_info_offsets[n]}`. Every offset is from byte 0 of the chunk data.
  - **The header names the last table, not the first.** The tables pack contiguously after the final frame-info record and the header's offset points at the one the game reads first, which is the last of them, so `walk` steps back from that table's own frame infos and walks forward until it passes through the named table; a zero-frame table keeps its eight-byte slot, since the PC tables count it. The same chunk is byte-identical wherever its file name recurs, in both games, so one copy stands for every level.
  - `fps` is a hold count in 30 Hz ticks, not a rate: frame k shows from tick `1 + k·fps`, flag `2` loops back to `loop_start`, and a table without it parks on its last frame. Flags `4` and `8` are flip bits no engine code reads. A motion that switches animations does so the tick after the old one's last frame was decoded, since objects update before the animations step and the last-frame flag is read a tick late, so a one-shot shows its last frame for one tick and a one-frame animation lasts one tick.
  - **The engine's dice are a table, not a generator.** `Math_NextRandom` returns the next byte of a 256-entry permutation of 0..255 and wraps, so a brain's `rnd % 64` timers are that table's bytes in order from wherever the global index stood. The table sits in the executable (`SLUS_*`) on every disc, identical across the three, and is the only 256-byte permutation in it.
  - **Exoddus compresses its frames with two schemes the decomp never saw.** PS1 Oddysee frames use compression ids 0, 2, 3 and 4, the PC algorithms; PS1 Exoddus tags 10,392 of its 11,045 frames 6 or 7, a pair-substitution coder in eight- and six-bit variants that alive_reversing aborts on (its ids 7 and 8) and only paulsapps/alive ever implemented, from the PS1 demo. `decode_psx67` is that port, and it reads every frame on both discs clean with nothing of alive's one-row clip: the output runs to wherever the input ends and the frame's remainder stays zero. Each codec is pinned by a frame lifted off a disc in `tools/tests/fixtures/sprite_frames.json`.
  - **260 Exoddus chunks are one pre-rendered sheet.** A non-zero header word followed by ten zero bytes marks it: the word is the single frame's header offset, and each frame info's header-offset slot holds a sub-rectangle instead, packed `x, y, w, h` from the low byte up. Oddysee never ships the shape; its header word is the CLUT size.
  - A CLUT entry of `0x0000` is a transparent texel and bit 15 is the PlayStation's semi-transparency bit, which blends the texel only on a polygon the object flagged semi-transparent; about a quarter of an ordinary sprite's pixels carry it (the soft edges), and a Dove's whole palette does while the Dove clears the flag. The atlas keeps it as a third alpha state, 254, and the viewer decides per object.
- The LCD screens' font is `LCDFONT.FNT`, one `Font` chunk per level archive: a header `{s16 width, height, depth, colours}`, a 16-entry CLUT and the 4bpp texels, low nibble first, 112×109 and identical across a game's levels, the two games' differing in one glyph: Exoddus drew a colon where Oddysee had a stray mark, and Oddysee's table points its colon at a blank cell, so an Oddysee colon draws nothing. The CLUT is dead data: a screen colours its glyphs through two palettes compiled into its own code and swaps them at every message end, the first drawing the letters green and the second red. **The glyph rectangles are not in the file.** They are a 157-entry `{u8 x, y, w, h}` table in `SLUS_*`, which `glyph_table_windows` finds by its shape rather than an address, as `read_dice` finds the random table: entry 0 is the gap drawn after every glyph and entry 1 the width of a space, a printable code's glyph is the code less 31 and a button code's the code plus 137 (Exoddus's measure and draw take a button code from 0x07 and Oddysee's from 0x08, the engine spacing 0x07 as a space there; the port takes Exoddus's bound for both, which only a code no message carries could tell apart), the lowercase entries repeat the uppercase ones, so every letter draws as a capital, the twelve button codes draw the PlayStation's own buttons, and the slot past the end is zero.
  - **The decomp's font and LCD numbers are the PC build's.** Its glyph tables are for a font re-rendered at 14 texels a glyph on a 640-wide screen, its screens step 3 PC pixels a tick, its `LCD_PS1_SPEED` guess of 6 is wrong, and it measures an Exoddus character two pixels wider than it draws one. The PS1 overlays step an Oddysee screen 2 pixels a tick and an Exoddus one 3, advance the pen by a glyph's width plus the gap and by the space width alone for a space, measure a character the same way, so the scroll is seamless, read the message's end on the character they have just stepped onto, flicker every glyph's colour by ±50 a channel a frame rather than ±40, and draw the text additively, every palette entry carrying the semi-transparency bit. Verified by disassembling the `LCDScreen` update and render in `R1.OVL` and `MI.OVL` and the font's draw and measure in the executables; the overlay's load address falls out of its message table's pointers, as `string_table` derives it.
- TLV records (`games.py`'s `tlv` block): 0x18-byte header with payload at +0x18 in AO; 0x10-byte header with payload at +0x10 in AE. Door numbers are only unique **per camera** — a target door must be resolved inside the destination camera or same-screen door pairs cross-wire.
- An express well carries two destinations, one for each state of the switch it answers to (`disabled_well_*` / `enabled_well_*`, reaching the viewer as `to_*` / `alt_*`).
  - Either state can be a dead end, and a dead end is written two ways: naming the well's own id, so you drop back out of the well you entered, or left unpointed at the address the fields were born with.
  - `destOf` therefore prefers the state that *lands on another object* over the one that merely differs from the current path, since a dead end always differs. A state naming the well's own camera is a ride like any other when another well answers to it (the Slig Barracks hub pairs 6↔1, 5↔2, 8↔4, 7↔3 within one screen), and a bounce-back only when nothing but the well itself does.
- A destination whose level field was never set reads as level 1 (AE: Necrum Mines) while its path and camera keep the values that were right for a link inside its own level, so the triple looks plausible — 61 AE links name the Mines from another level and not one of them means it (23 naming `MI P0`, 28 the opening screen).
  - `destTrusted` ([js/model.js](../public/js/model.js)) believes a destination only where the partner it names is there to be found, and gates the follow, the tooltip's destination lines, the arrow stubs and `computeEntryPaths` alike.
  - A link naming no partner (`PathTransition`) has nothing to check and stays trusted wherever it points — that is what lets AO's two main-menu links follow into `S1`, whose grid the decomp does not tabulate.
  - `wayThrough` composes the two with the one guard everything reading the level graph needs: a hand stone's view is not a way through. `destOf` mints a destination out of `view1_*` and a view names no partner, so `destTrusted` believes it wherever it points, and a sight left in can elect a level's entrance or make the room it shows reachable. No view survives into consequence on either game's shipped data — not because the predicates filter them out, but because every one that passes all three then names the path it already sits on, which each caller drops for its own reason. That is why the guard has to live in one place: nothing in the sweeps fails when a caller forgets it, and `map-data.test.js`'s own cross-level walk omits it to this day with no consequence. Whether the path a destination names is one the map holds stays the caller's question, since the connection stubs deliberately label an off-path destination the level graph drops.
  - No destination in either game now names a level the map does not render, so the tooltip's off-map clause is unexercised by the shipped data and kept for the subset build that reaches it: a `--levels` tree still holds links naming no partner that point out of it, and the clause is what stops one promising a follow into nothing.
  - The partner check is cross-level only: `resolveTarget` is camera-bounded with a path-wide fallback, so within a level an unresolved partner is that strictness rather than bad data, and dozens of sound same-level follows depend on it.
  - A partner *is* found when nothing at all was set — level 1, path 1, camera 1, pair id 0 is a real screen holding a placeholder numbered 0 — so `targetAt` reads that whole address as the absence it is.
  - Key it on the level id, never on the pair number alone: AO's Monsaic Lines wells ride to `D1 P1 C1` and `F1 P1 C1`, the Paramonia one arrival well 0 and all, and are genuine.
  - Both the entry sets (AO 18 slots, AE 14) and the cross-level follows (AO 19, AE 12 — every crossing the shipped data can follow, which is one short of the games' own: Necrum Vaults to FeeCo Terminal 1 happens in a cutscene and no well pairs for it) are pinned in `tests/unit/map-data.test.js`; the phantoms used to badge four real Mines paths as entry points and to send 26 wells to the Mines from across Exoddus.
  - One probably-genuine link pays for the rule, and shows one-way rather than not at all: `BR P10`'s `Door@500,860` names `MI P24`, an address that read inside the Brewery lands on `BR P24`'s `door# 10`, which points back at it. It is the only link in either game a local re-read would recover, it never followed before the check either, and the `BR P24` side still does — so leave it.
- A BirdPortal's destination words are live only when its `portal_type` is travel: a worker (rescue) or shrykull portal dies where it stands and never changes the map, so its level/path/camera fields are dead data — in Exoddus near-universally the unedited 1/1/1 default, which would read as a link to Necrum Mines P1 C1; in Oddysee all but one zeroed, which would read as the menu level `S1`.
  - Both `tlv_extra_{ao,ae}` withhold `to_*` for non-travel portals; the raw words still reach `fields`.
  - The same trap points the other way for the Shrykull countdown: every portal ships `mudokon_amount_for_shrykull`, near-universally at the unedited 1, and only a shrykull portal ever reads it, so `LIVE_WHEN` in [js/fields.js](../public/js/fields.js) gates it on the portal's own kind.
- A TLV carries two decoded buckets. `extra` holds *derived, semantic* fields the viewer's navigation logic reads directly (`to_level`/`to_path`/`to_cam`, `door#`, `well#`, `portal`, `view*_*`, …) — hand-written per type in `tlv_extra_{ao,ae}`, since resolving level ids and pairing doors/wells isn't a raw dump.
  - `fields` holds the *complete raw archive* (every field, s16, dev name) for gameplay types, schema-driven.
  - The display writes both, so a key in both buckets prints its value twice — where the archive grows to cover a word `extra` hand-decodes under the same name, `extra` gives it up (AE's express wells did, for `switch_id`); a twin under a different name is a naming question, not a duplicate (AO's `trigger_id`, the wells' `well#`). A test pins that no object names one key twice.
  - `model.js` reads only `extra`; the field display (`extrasText` in [js/util.js](../public/js/util.js), over `fieldEntries` from `js/fields.js`) shows `extra` always plus the `fields` a user's `fieldPrefs` admit, prettifying enums viewer-side.
  - `fields.js` `visibleFields()` is the single indirection: "default", "show more" and the per-type picker (`js/fieldpanel.js`, writing the per-game `fieldPrefs.byType`) are just which set it returns. Search is the exception: it asks for `"all"` and gets that string back rather than a set, which `fieldEntries` special-cases.
  - Two value rules sit under that policy, both applying however a field was admitted: `HIDE_WHEN_ZERO` drops a field whose 0 means absent (an unwired switch id, a flag nothing set), and `LIVE_WHEN` drops one the engine reads only when a sibling field says so, which the value alone can never tell you. A gate has to open on some shipped placements and close on others in each game that places the field, pinned in `tests/unit/fields.test.js` — a rule nothing satisfies hides its field everywhere, and a predicate naming a sibling the type doesn't carry reads the same.
- A message table's strings are 4-byte aligned, so splitting its blob on NUL mints a phantom empty entry per padded string and every id after the first lands wrong. Only the pointer array gives the index, and it is also where the table's empty entries live: they all point at one shared empty string rather than occupying the blob.
- Exoddus disc 1 ships `TL.LVL` as a 68-byte boot-config stub, not a LVL archive; the builder skips it. Archive reads are guarded (EOF raises, directories must fit their file) because a garbage header otherwise spins disc reads forever at end of image.
- Both Exoddus discs list every level, but each disc carries full content only for its half — the other half are stubs with path data and no cam files. Always pick the largest copy of a level across discs (the builder does).
- AE "ender" levels are the endgame revisits of areas the player returns to finish (the two vaults, FeeCo Depot, Slig Barracks, Bonewerkz) — same map geography, a distinct level id, the game's own term. The Brewery Ender (id 10, the Game Ender in the game's own level select) wears the term but is its own archive, `BM.LVL`, listed as the level `BM` and carrying no `section`.
  - The five reuse their base level's archive and the table parser deduplicates them into it, keyed on the level short, so each LVL file appears once in the level list, but TLV destinations still name the ender ids — the builder's id→short map must cover every id, not just the kept ones.
- Exoddus ships 25 paths that only its attract-mode demos play — copies of a real area, unreachable however you play — and holding a `DemoSpawnPoint` TLV is the whole rule for spotting one ([js/demo.js](../public/js/demo.js), memoized per path; AO has no such type, so the rule degrades to "no demos" there with no per-game case).
  - The `showDemoPaths` setting hides them from the path buttons and from search (whose summary counts what it dropped).
  - What is listed is [js/pathvisible.js](../public/js/pathvisible.js) — the setting and the session reveal — kept apart from the rule so `demo.js` imports nothing. That is what lets `model.js` leave demo copies out of `levelWiring` without the geometry core depending on a setting. With the two in one module, asking the rule would import `settings.js`, and `settings.js` imports `parseHash` from `model.js`: an import cycle.
  - Nothing arrives at one and no level opens on one, both pinned in `tests/unit/map-data.test.js`, so the entry marks and the connection arrows need no demo case of their own.
  - **The path in hand is always listed**: `selectPathById` reveals a hidden path for the session, which is what lets a permalink, a remembered location or a follow land instead of falling back, and is why switching the setting off leaves the path you are standing on visible.
  - That a path is a copy is written into its curated name (`[Demo] …`, test-enforced) rather than composed on at display time, so no caller has to pair a name with a marker.
