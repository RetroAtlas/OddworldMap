# Visiting a place in the game

- [tools/visit.py](../tools/visit.py) turns permalinks into a memory card, `visit.mcd`, holding one save per permalink that starts Abe at the linked place in either game, so what the map shows there can be checked against the game itself without playing your way to it; [tools/oddmap/savegame.py](../tools/oddmap/savegame.py) writes what both games' saves share and Oddysee's body, [tools/oddmap/quicksave.py](../tools/oddmap/quicksave.py) Exoddus's, and [tools/oddmap/memcard.py](../tools/oddmap/memcard.py) the card, laid out the way [DuckStation](https://www.duckstation.org) formats and writes one.
  - `python3 tools/visit.py --launch 'https://oddworldmap.com/#AO/D1/7/4637/1709/1.60/ContinuePoint@4625,1638'` writes the save and boots the game at it. The card is `visit.mcd` under `--out` (`$ODDWORLD_VISITS`, else `OddworldMap/visits` in your home folder), and the disc images come from `--disc` or `$ODDWORLD_DISC_AO` / `$ODDWORLD_DISC_AE`, both Exoddus discs in the latter, as for [a build](builder.md). Permalinks of one game go on one card. Without `--launch`, mount the card in any emulator.
- Both games save 0x2000 bytes, one card block, opening on the PS1 file header (title frame, palette, icon), the first of the two `SC` headers in the game's executable (`SLUS_001.90`, `SLUS_007.10`), the one a save whose alternate-header flag is clear wears. The word at 0x200 is a checksum, the wrapping sum of the 1919 words after it, in Exoddus too, where the PC build keeps an object count there. Measured against fifteen saves on a real Oddysee v1.1 card and forty-three from a full Exoddus playthrough: every checksum agrees, the fields read as the decomp lays them out, and `write_card(read_saves(card))` reproduces a card byte for byte.
- An Oddysee save is AliveLibAO's `SaveData`. Loading one runs the game's own path start (`SaveGame::LoadFromMemory`, then Abe's `Motion_62_LoadedSaveSpawn`): it clears the objects, moves to the saved level, path and camera, puts Abe at the saved x and searches 60 units above and below the saved y for a line of the saved type (`1 << mode_mask`), standing him on it or letting him fall, and rewrites the switch states and every object record's flag and state bytes for the whole level from the block at 0x2B0. Whichever records that block leaves uncreated spawn afresh, which is what makes a visit start the path the way a first arrival does.
  - **The block cannot be zeros.** It rewrites each record's flags byte whole, the end-of-list bit included, and a list left without its end bit runs on into the next camera's. `tlv_flags` copies the disc's own bytes in the order the game walks them: every path the level's table names (`tools/data/pathdata_ao.json`), camera by camera through the index table, each list to its end bit, entries at or past 0x100000 skipped.
  - The walk covers every path in the table, as the decomp's `kMaxPaths` loop does, not the path count `gMapData` carries: that count would leave out D2 P10 and R6 P6, and real saves carry both. Real saves for D2, R2 and R6 put every end bit where the disc walk does.
  - Every Oddysee level's block fits the 7501 bytes the struct gives it (R2, the largest, takes 3634). S1, the menu, has no table and is refused.
  - A continue point brings its zone, clear range and rectangle, as touching it in the game would, and Abe faces the way it respawns him. Any other place gets zone 0 and a continue-point-sized rectangle at the landing spot, so a death respawns Abe where the visit began.
- An Exoddus save is AliveLibAE's `Quicksave`: the world at 0x204 and the copy Restart Path returns to at 0x244 (level, path, camera, the continue point's save number, Abe's position and the mudokon tallies), Abe's 216-byte record for that copy at 0x284, the switch states twice (0x35C for the restart, 0x45C), then the list of objects whose state the game keeps from 0x55C, each record opening on its type (Abe's is 69), ended by a zero word and followed by the flag and state bytes of every object record of the level whose type the save keeps. Most real saves list Abe alone, as a visit does.
  - Which types keep their bytes is `ATTRIBUTES`, AliveLibAE's `kObjectTypeAttributesTable` (1 clearing the created state, 2 as they stand). The executable carries its 128 entries byte for byte; the PC table's last eight are zeros where the PS1 one holds the next data, and no record type on either disc passes 111. `tlv_flags` walks the level as for Oddysee, keeping those types alone, and every real save's block sits where the walk puts it and agrees with it but for the states play changed.
  - Loading one (`Quicksave_LoadFromMemory`) moves to the saved camera, rebuilds each listed object, and Abe searches 20 units above and below his saved height for a line of the type his record names. A death reloads the save, so it returns Abe to the visit's spot, and Restart Path brings back the restart copy, which a visit fills the same way.
  - A visit's Abe is a newly made one at rest, nothing of play carried in: no vault-ender bits, no hand-stone fields, no mood raised by rescues. His tint is his level's row of `sTintTable_Abe`, which the restore sets afresh from the table anyway.
  - The title is the game's own: `Abe2`, its name for the level, the play time, spaces to the 21st character, then a name of up to seven characters in quotes. The names come from the executable's table by level id, an ender taking its base's (Scrab, Paramite, Feeco, Barracks, Bonewerks, Brewery), and all forty-three real titles rebuild byte for byte from their parts. A visit writes `000:00` and the path and camera (`"P23C01 "`). The card file name is `BASLUS-00710AB2` and five characters, the prefix being what the game lists the card by.
  - A path the map files under an ender's section saves under that ender's level id. The enders share their base's path table, so the flag block is the base's; a real save's restart copy carries the Mudomo Vault Ender's continue point (PV P13, save 322) under level 11. A continue point brings its save number, and Abe standing on one the save leaves untouched saves the game again at once, as touching it would.
  - The second half of the game is on the second disc, each disc holding stubs for the other's levels, so `--launch` boots the disc carrying the level's archive whole.
  - Checked in the game at MI P1 C4 (the first disc, a foreground floor), PV P13 C1 (the Mudomo Vault Ender) and BR P23 C1 (the second disc, a half-scale Abe on a background floor): each arrived on its screen, the pause menu named it, and Abe walked off along his line.
- The place is the permalink's object (its rectangle's centre x, searching down from its top), else its view's centre, else `--at X,Y`. Abe stands on the first floor or background floor at or below that point (`floor_under`), at half scale on a background floor, in the camera whose cell holds his feet, facing right unless `--face` or an Oddysee continue point says otherwise. A floor of the same type within the game's reach above that one would catch its search first, and the tool reports it, as it does a place outside the camera's 368×240 window.
- `--launch` points DuckStation at `<out>/profile` through the variable its data root is picked by (`Core::SetDataRoot`): `HOME` on macOS, whose root is `$HOME/Library/Application Support/DuckStation`, and `XDG_CONFIG_HOME` on Linux, whose root is `$XDG_CONFIG_HOME/duckstation` whenever that is absolute. The profile is made once from a copy of the real folder's `settings.ini`, found by the same rule, with the achievements login stripped, card 1 a shared card at `visit.mcd` and the BIOS images copied, and nothing in the real folder is written. `--app` names the program (`/Applications/DuckStation.app` on macOS, `duckstation-qt` on the PATH on Linux, by default); on the game's main menu choose Load, then Load again and the save, which is titled with its level, path and camera. Deleting the profile folder remakes it from the current settings on the next launch. Checked on macOS; the Linux path follows the source and has not been run.
  - Windows picks its root from known folders no variable moves, and a portable install (a `portable.txt` or `settings.ini` beside the program) always uses the program's own folder, so `--launch` refuses both and names the card to mount instead.
  - Both games' Load screens open on slot 1 and offer Switch Memory Card, so the card mounted in slot 2 of another profile should serve as well; that is untried.
