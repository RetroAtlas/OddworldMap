# Test suites

## `python3 -m unittest discover -s tools/tests`

- No disc image is needed, and the sidecar reproducibility tests run from the committed caches; only the tests that probe the checkout itself (the member-type parser pair in `test_schema.py` and the four cache freshness checks, three in `test_caches.py` and one in `test_relive_export.py`) skip, and only where no checkout is configured or found — `$ODDWORLD_DECOMP` naming a path that holds none fails them instead, a named location being an assertion rather than a hint — and the tests that encode through oxipng skip where none is on PATH, which is every CI run. CI clones the pinned revision into `$ODDWORLD_DECOMP`, reading `DECOMP_COMMIT` and `AO_COMMIT` off `paths.py` and fetching both by SHA, which is what makes the six run in CI; a clone step gone missing fails them rather than skipping, the variable being set either way. One file runs alone with `python3 -m unittest tools/tests/test_sprites.py`.
- A parser reached only through a nested helper (AE's `positional_rows`, the enum body loop) can't be tested until it's hoisted.
- `test_sprites.py` pins each sprite codec against a frame lifted off a disc (`fixtures/sprite_frames.json`, with the sha1 of the rows it decodes to), the animation-table walk over a synthetic chunk, the texel alpha states, the packer and a family's sheet, each sheet's name and the directory it leaves holding nothing else (a family renamed only in case among what it clears), the shape of the curated animation list and the random-table search over a synthetic executable; the atlases themselves reproduce only on a disc machine, like the cameras.
- `test_release.py`'s `CommittedOverlays` holds every committed overlay to the committed base: every image an overlay names is decoded and held to its name, and every camera it draws over to the base's screen beneath it. Each image's folder and name are held in turn to the release whose overlay lists it and the camera, corner, layer or family its entry gives it, which no pixel check could see out of step, a patch moved by whole blocks still changing every block it covers. It runs in full every time and skips nothing on the record of an earlier run, since its pass is what lets the deploy publish and a skip is only as sound as the list of files it keys on. Decoding is nearly all of its cost, so its pixel checks decode over a process pool of one worker a core, their work in module-level functions the workers can import, and a new check over the committed art goes through the pool the same way.

## `npm test`

- Node's own runner, handed no path, walks the whole tree (`node_modules` apart) and collects every file named `test.js` or `test-*.js`, every `*.test.js`, `*-test.js` and `*_test.js`, and any `.js` under a directory named `test`; the suite is the `*.test.js` under `tests/unit/` because nothing else in the tree takes one of those shapes, and a helper module beside the tests takes none of them, as `fixtures.js` does not. Each file runs in a process of its own, so a file's top-level setup reaches no other. The files share `fixtures.js`: the two games' geometries beside a synthetic one unlike either, `pitches`, which gives a geometry at both layouts, the cross-level follows, the `tlv`, `path`, `level` and `dataset` builders, and `at`, which stands a TLV at a world point; `creatures.js`: the brain tests' animation tables, the worker, the creature and the walker it builds, and the flat world they stand in; and `aeworld.js`: the edit tests' two-path Exoddus world, which sets the level names and the one typed field as it is imported. A file that reads the shipped JSON reads it itself, none lending a loader. One file runs alone with `node --test tests/unit/destinations.test.js`.
- Seven files hold the repo to its conventions: `imports.test.js` the one-way import graph, the layer table (which folder under `public/js` may import from which, with the root's `config.js` the one file a row may name from outside the folders beneath it), the pure modules' import in bare Node, that `model.js` never reaches `state.js`, and every module's parse as the Wayback Machine serves it; `sizes.test.js` every module, stylesheet partial, spec, unit test and tool to its size, with the table of the files still over their cap (how a row moves is under The budgets below); `docs.test.js` the topic docs' index and every relative link; `backlog.test.js` the backlog's numbering, statuses, index, links and cited commits; `changelog.test.js` the feed's shape against What's New; `markup.test.js` the page's tooltips; `stylesheet.test.js` the stylesheet's partials, every file under `public/css` linked from `index.html` once and in name order, which is the cascade. The shipped data files are held to their shape by the tests named for them, `annotations`, `glossary`, `map-data`, `field-types` and `enum-labels` among them, and `levelpages.test.js` holds the committed level pages to a fresh emit.
- `sprites.test.js`'s walk over every shipped record's animation, and every sidecar animation drawn, is most of the suite's time; the rest runs in a few seconds.

## Where a check lives

- A check lives where what it checks is computed, as CLAUDE.md's Conventions put it: a unit test holds anything a module computes, a browser test only what only a browser shows, and a browser test asserts the wiring, never replaying what a unit test replays. Two cases from the suites show the line. A slig's patrol, the walk to its zone's edge, the rolled pause, the turn and the walk back, is held step by step by `patrolkit.test.js`'s patrol tests over a synthetic world, and `motion.spec.js` asserts that the hover over a Zulag 4 slig lands where the creature has walked to and not where its marker was placed. The LCD's text effect, the glyphs it carries and the panel it names, is held by `lcd.test.js`, and `motion.spec.js` asserts that the pixels inside the Mines panel have changed from the artwork once the scene has run past the lead. What reaches the device's storage is wiring too, until a unit test stubs `localStorage` and reads it back: `settings.test.js` holds the settings' and the view's writes that way, and `edits.test.js` every write of the edit store, the boot's drop of a stale delta among them.
- A computation in a DOM-bound module that no unit test can reach stays in the browser until the module gives it a seam, and the commit that adds or keeps such an assertion says so; `export.js`'s file names (the graph's come from `graphsvg.js`, which `graphsvg.test.js` holds), the object permalink's origin in `navigate.js`, the picker's placing of an added object on one of the path's screens in `editpanel.js`, the Display store's drop-at-default rule in `sidebar.js` and the carried copy standing in its first frame (`holding` in `render.js`, `still` in `spritepaint.js`) are held that way.
- A change to the painter or the modules it draws from that is to draw exactly as before, a move, a re-wiring or a speed-up, is proven with `npm run pixels`, which renders a matrix of views at the working tree and at a ref (`HEAD` unless one is named) with the clock stopped, the ref served straight from the repository and the page's modules found by name in each tree, so the two need not lay them out alike, and names any view whose canvas, minimap, export paint or object boxes differ; the matrix is in `tools/pixels.js`, and a new transient or layer earns a view there. No spec holds this: a spec pins what a view must show, the proof only that two trees show the same. A stylesheet change that is to show exactly as before is proven with `npm run styles`, which opens the page in a set of interface states at the working tree and at a ref, with the clock stopped, and compares the computed style of every element and pseudo-element, naming any that differs and the properties; the states are in `tools/styles.js`, the map and each panel, dialog, mode and layout the page opens, each waiting for what it opened to stand, so a state that fails to open fails the run, and a new surface earns a state there. Each state is read three times: as it stands under reduced motion, with motion allowed and every animation held at its first frame, so the transitions and animations reduced motion switches off are compared too, and with the hover, focus and active rules forced on every element, so a rule under those pseudo-classes is held wherever its element exists. The pseudo-elements read are `::before` and `::after`, and the layouts shown are a phone, a laptop and a wide screen, the last two with the route planner open, since the one breakpoint between them concerns the route bar. The two trees must build the same page for a state to agree, so it proves a change to the stylesheet, or to markup that is to look as it did, and shows a change to the data as a difference too.

## How a test is added

- A spec file is one subject, named for it: a new browser test goes in the spec of its subject, and a new spec is made only for a subject no spec holds; `smoke.spec.js` is the one spec of several subjects, the base viewer's wiring (boot, the permalink, the view's resize, a door's follow, the embed, search, the keys and the two stores), and a new test of one of those goes there until the file reaches its cap. A pin (a rect, a filter set) or a helper that specs of different areas share lives in `tests/browser/helpers.js` (the quiet view and the filter sets, the slig, its bound and the tally board above it the sprite specs pin, the filter set that shows every category, `trackErrors`, `pixels` and `digest`, `seedView`, the settles, `POLL` and `probeAnchor`); the plumbing one area's specs share lives in a module named for the area beside them, `edithelpers.js` for the editing specs; a helper one spec needs stays at that spec's head. Read the helper modules' exports before writing a helper of your own.
- A new browser test is one behaviour; a test that would assert a second is cut in two, the second taking the first's setup through a helper. It probes and settles the page as the bullets above say, and where it depends on movement it waits on the engine's clock through the page's own motion module.
- A new DOM-free module lands in one of the four folders `tests/unit/imports.test.js` imports in bare Node (`engine/`, `model/`, `rules/`, `data/`) or, outside them, joins the files the test names in the same commit, and what it computes is held in a unit test: `tests/unit/<module>.test.js`, built from `fixtures.js`'s builders or the shipped JSON, for a module that is a subject of its own, or the test that already holds its subject for a module split out of or gathered by another, as `demo.test.js` holds `pathvisible.js`; a module that paints or touches the DOM at import stays out of those folders.
- A feature commit adds a unit test where the change is arithmetic, one assertion to the browser test of the same behaviour where it is wiring, and a new browser test only for a new behaviour the browser alone shows; its body names the unit test, by file and title, that holds what the change computes. A browser assertion is retired as a replay only once the code it protected has been disabled and the unit test named for it seen to fail: a unit test that still passes reads the same computation without holding the effect the assertion read, and the assertion stays until one does.

## The budgets

- A file's size: every module under `public/js`, partial under `public/css`, file under `tests/browser` and `tests/unit`, and Python or JavaScript file under `tools/` is held under a cap by `sizes.test.js`, 800 lines under `public/js`, `public/css` and `tests/browser` and 1,000 under `tests/unit` and `tools/`. A file already over its cap stands in the test's table at the next hundred above its size; a commit that shrinks it lowers its row, none raises one, and the commit that brings it within the cap takes the row out, the test's message saying which move is due. A change that would push a file past its cap or its row splits the file first, in a commit of its own, where the sections it already has join, a subject to a file; a hand table that outgrows its file is split by what its rows are, never by count alone; and no section comment is added to make a cut possible.
- A browser test's time: a test is timed out at ten seconds here and twenty in CI (`timeout` in `playwright.config.js`), and `budget.js`, the reporter beside `list`, fails the run on any passed test over five seconds here or ten in CI unless it carries `test.slow()` with a line saying what it waits for, printing the wall time, the tests' summed time and every test over the budget. The CI figures are the local ones doubled, as the timeouts are, and the suite's floor in CI is the tests' summed time over its workers, so a test that waits on a long window costs every run its wait.
