# The PlayStation's own code

- The decomp is the PC build's source, so where the viewer has to move as the console does, the routine is read off the disc ([format-gotchas.md](format-gotchas.md) records what differed). A reading is a claim until the disc's code has run beside it, and the tools here are that run, in three links: an interpreter of the console's processor, a model of the routine in Python that the interpreter's run of the disc's code is compared with, and the model's runs, which the viewer's unit test holds the JavaScript port to. The comparison needs a disc and is run by hand; the unit suites need none, and hold the port's numbers to the model's over the tables the viewer ships.

## The interpreter

- [tools/oddmap/r3000.py](../tools/oddmap/r3000.py) is the console's two megabytes of RAM at `0x80000000`, its registers and the instructions compiled code is made of. `load` puts bytes where the console loads them, `call` runs a function with up to four arguments to its return and gives what it leaves in `v0`, and the readers and writers (`r8` to `s32`, `w8` to `w32`) lay out and read back whatever the function works on.
- An executable's text loads at the address its header names and an overlay at the one its message table gives (`Image` in [exe.py](../tools/oddmap/exe.py) reads either by address). An Oddysee overlay opens 0x68 bytes before the executable's file ends, over its padding, so the executable is loaded first.
- It runs compiled code and nothing else, which is what lets it leave out the load delay (a compiler never reads a register in the instruction after its load), the overflow traps and a branch in another's delay slot. There are no coprocessors, no hardware registers, no interrupts and no BIOS: an instruction or an address it does not have is a `Fault` naming the instruction's address, as are a word off its boundary and a run past `limit` instructions.
- `stubs` cuts a routine off from the rest of the game: where the code calls or jumps to an address named there, the caller's own function answers, given the machine once the delay slot has run, and what it returns is `v0`, or `RUN` to let the function run after all, its arguments seen. The function `call` is handed always runs, the stubs are the ones set as the call begins, and a stub may not call in its turn. Which callees run as the disc's code and which are answered is the port's decision: the engine's arithmetic runs, and what reaches for the hardware or the objects around it is answered.
- A set in `stores` gathers every address the code stores to, which is how the globals a routine writes are found without reading for them.
- An instruction is decoded once, into a function, and decoded again if anything is stored or loaded over it. A run is a few million instructions a second.
- `text_codes` in exe.py keeps a reader of its own for the fonts' measuring routines: a leaf run over the memory it is handed, refusing any read beyond it, which a whole machine of zeroed RAM would let through.
- `tools/tests/test_r3000.py` holds every instruction to what the console does with it, bar the load delay and the trap left out, over hand-assembled code. A hint fly's run executes thirty-five of its fifty-six instructions, so for the rest that file is all there is.

## The hint fly's model and its check

- [tools/oddmap/hintfly.py](../tools/oddmap/hintfly.py) holds the model: a `World` of what the swarm shares with the game (the frame counter, the chant, the sounds asked for, the dice and the two cursors into them), and a `HintFly` built as the constructor leaves one, with `update` a tick and `sprites` the corners the render draws from. Its fields carry the names the check compares by. The dice, the alphabet and the messages are a disc's own (`tables`); the engine's quarter wave is the model's constant, as it is the viewer's, so a disc whose wave differed would fail the check rather than pass on a table of its own.
- No address is written down. `code` finds the routines in an overlay by their shape, since each of the base disc's eleven overlays links them somewhere else and a release links its executable differently too: the routines that spell build the alphabet's address less the first letter's code; of those the update is the one a table of virtual functions names, with the render in the slot after it; the update calls the one that forms a word; its other callees are the flies' tick and, making no call, a fly's setup; and the one that measures the longest word is the speller called by what also sets a fly up, the constructor. Outside the overlay the update calls only the event query and loads only the frame counter, and the render calls the engine's drawing and loads one pointer. The flies' tick passes the literal 60 to the routines that make a sound, which all call the engine's player; of what the player calls, the one the flies' routines call too is the roll of the dice and the rest are the voices it plays on, and the one word it loads is where its sounds are kept. A shape that is off in one of those is refused by naming it. The sound routines are gathered only to reach the player, and of the engine's drawing only the call handed each fly's sprite matters to the check, its loss showing as sprites that never come.
- [tools/hintfly_verify.py](../tools/hintfly_verify.py) runs the two side by side. Its `Console` loads the executable and one overlay, lays the object out in spare RAM as the constructor leaves it (the constructor itself is the engine's for the most part and is not run: the flies' block, the point, the message, then the disc's own measure of the longest word and setup of the twenty), and answers three kinds of call: the event query with the chant, the voices with none free, and the engine's drawing by recording what it is handed. The dice roll, the two waves, the fixed-point product, the sound routines and the engine's player run as the disc's code, the player seen as it is called. The two cursors are found by what the routines store to: the one byte outside its fly that a fly's setup writes, and the one byte a roll does.
- After every tick it compares every field of the object and of every fly the swarm has reached, both cursors, each sound's volume and the pitch given it, and each sprite's corner in the order the engine is handed them, and names the first that differs with its message and tick.
- A run is every overlay the paths load that holds an alphabet, over every message that alphabet spells, from cursors, at a point and under a chant drawn from `--seed`. Each message is first spelled through under a held chant, on to the word of nothing the console forms with twelve flies once the message is over and to a second, formed with no sizing left to do, then run for `--ticks` more under a chant that comes and goes, which is what breaks it in every state and lets go of words as they stand. What a run meets too seldom to count on is put there. The chant is broken once on a tick the swarm reaches a word's size, where the console lets go before it would form. And the last eight flies of every word, never the first, which is the one that sounds, are stood by their dots: four exactly a pixel off, either way across and down, which keep the speed they formed with and fly on past, and four a fraction nearer, which arrive. Each overlay's line counts the words formed and the ones let go of, and says whether all eight changes of state were seen.
- `python3 tools/hintfly_verify.py` takes the disc from `$ODDWORLD_DISC_AO`, or a release's image by `--disc`, spreads the messages over the machine's cores and exits non-zero where an overlay differs or will not run; `--overlay` and `--message` narrow it. The base disc is 3.1 billion instructions, a minute and a half on a machine of fourteen cores, and it is the one disc run so far.
- What a pass leaves open: two steps of the console's that change nothing in any state a run reaches, the scatter stopping at the first fly already looping and the flies a word leaves over being set looping as it forms, which the model keeps because the disc has them; and what no message of the base disc reaches, a letter outside the alphabet, a word of nothing inside a message and arithmetic past its range, which `tools/tests/test_hintfly.py` holds instead.
- What it does not hold: that a path's overlay builds the object at all, which is its factory table's matter; where the constructor puts the point; the event that marks the object dead, which the update asks for before all else and the check answers with none; a sprite's frame, layer and blend, the render being compared by its corners alone; what the voices do with a sound; and that the tables the viewer ships are the disc's, which is the build's.
- `tools/tests/test_hintfly.py` holds the model to hand-worked runs over a three-letter alphabet, and `code` to a synthetic overlay and executable and their refusals. They guard the model against a slip; only the disc proves it.

## The runs the port is held to

- [tools/hintfly_trace.py](../tools/hintfly_trace.py) prints a run of the model as JSON, over the tables the viewer ships for the base game or, with `--disc`, a disc's own. `tests/unit/hintfly.test.js` holds the viewer's brain to such runs: the test's `run(hint(id, at, screen, seed), ticks, flips, shots)` is `hintfly_trace.py <id> <ticks> --chant <flips> --shots <shots> --seed <seed>`, with `--at` the hint's point less its screen's corner; `line`, `sum`, `rolls`, `own`, `dice` and `shots` mean the same on both sides and the test's `words` are the ticks of the tool's; and the two swarms at rest are `--shots` with no `--chant`, under any message.
- The chant it runs under is the map's and lives in the tool, not the model: a hint with no message hears none, and one that has spelled every word of its message lets go by itself as the last word's hold ends and is heard again once the swarm is at rest, where the console's goes on while Abe chants. The frame a fly's sprite shows, its layer and its blend are the viewer's own too, and come from no run.
- `PortLiterals` in `tools/tests/test_hintfly.py` makes every run the JavaScript test makes, the hint of no message over a table of one empty message, and looks for each number in the test's source, where it has to stand once and whole, so the Python suite fails when the model and the test's literals part, with no disc. The test's `run` calls are counted against its `RUNS`, which a run added to the test joins. `rolls` folds both dice cursors after every tick because where they end hides a roll that differs and is made up later.
- A change to how the console's hint fly is read goes model first, then the check against the disc, then the runs printed and the test's literals replaced, and the port last.

## The falling item, the render and their check

- [tools/oddmap/fallingitem.py](../tools/oddmap/fallingitem.py) models the falling item's constructor, which is what decides where one waits: a `World` of what it shares with the game (the level and path, the frame counter, whether an item already hums for the rest) and a `FallingItem` as the constructor leaves one, at its record's corner whatever the camera. The update, and with it the rumble, the fall and the smash, is not modelled.
- [tools/oddmap/render.py](../tools/oddmap/render.py) models what a waiting item shows, which is no matter of the item's: both games draw every animated object through one routine of the executable, the one an object's table of virtual functions names in the slot after its update. `bounding` is the frame's rect stood at the object, `side` where the engine finds that rect by the camera's window, `quad` the corners the drawing hands the GPU, and `render` the three as the routine runs them, a quad or nothing. A `Sprite` is what the routine reads of an object and a `Stage` what it shares with the game, with the one difference between the games' drawing, that Oddysee's upends no frame. [format-gotchas.md](format-gotchas.md) has where the decomp's drawing is the PC build's.
- No address is written down here either. `fallingitem.code` takes the update to be the one routine of an overlay that builds both the gain of a fall and the multiplier its hum's period compiles to, the second of which Oddysee's meat saw builds too; a table of virtual functions names it, with the executable's render in the slot after; and of the routines that build that table's address the constructor is the one that reads through its second argument, a record. Of the words the constructor loads by name, the one outside the overlay is the frame counter and the one inside names the item that hums. `render.code`, handed the render, takes the test of where a rect lies to be its one callee that makes a single call, the event query, and the drawing to be the one that makes calls and is called again by another callee, the shadow's render, its last call handing a quad to the ordering table; the address the render hands the test is the map's, and the one word it loads is the pointer it finds the camera through. A shape that is off is refused by naming the part.
- [tools/fallingitem_verify.py](../tools/fallingitem_verify.py) runs the two beside the disc's code, an overlay at a time with its disc's executable: every overlay that holds an update, eleven of Oddysee's and fifteen of Exoddus's over its two discs. The constructor runs with the two constructors beneath it, and every other call the three make is answered, among them the object's entry in the game's list, the animation the item asks for, its setup and its shadow. It builds every record the game places, 21 and 93, read off the path chunks with the camera whose list holds each, and a record whose camera is not the one the builder's rule files it under is refused. Each is built under its own camera and under another, in four levels of which two are Oddysee's farms and one its lines, with and without an item already humming, and every field the model names is compared, with what the constructor stores to outside its object and the table of functions it leaves there.
- The item so built is then drawn by the executable's render, standing in every frame of the chunk of animations its constructor asked for, which is found in the level archives by the table it was set up from and is one to an overlay whatever the level. What the render hands the ordering table is compared with the model's quad corner by corner, and the disc's own answer to where the frame's rect lies with the model's. The test and the drawing run as the disc's code, the event and the hand-over are answered, and so is everything else the render calls, the colour, the shadow and the dirty rects, with nothing.
- What placed records cannot be relied on to reach is put there. Three records are made up: at the other scale, at a scale that is neither, and with a rect left of the path's origin whose sides sum odd. And `render.by_hand` stands an object, frame by frame, either side of each edge of the window and off each of its corners, on whole and on half units, at its own scale and two others, mirrored each way; half a unit over the left and the top of a window away from the origin, where cutting the screen's position and cutting the world's part ways; in the window at each scale that puts a measure of the frame a 65536th either side of where its rounding carries, which is what holds a rounding's 0.499 to the bit; with its render's offsets moved; and hidden, made in another level, made in another path and under the event that ends a life. An overlay's line counts its records, builds, frames rendered and drawn, and scales, and says whether a rect was found on the window and on every side of it.
- `python3 tools/fallingitem_verify.py --game AO`, or `AE`, takes the discs from the builder's variables or from `--disc`, and exits non-zero where an overlay differs or will not run; `--overlay` narrows it. Oddysee's disc is 88 million instructions and 26 seconds and Exoddus's two are 127 million and 39, on one core, and those three are the discs run so far.
- What a pass leaves open: arithmetic past sixteen bits, which no path's coordinates reach; and a rounding's last bit where no frame has an odd measure for it, since only an odd one can be put a 65536th either side of a carry. Exoddus's art has one for each of its six roundings and Oddysee's for four of its five, every frame of its items being of an even height.
- What it does not hold: that a path's overlay builds the object at all; Exoddus's second constructor, which an explosion set makes its rubble with and is handed no record; which animation an overlay's items stand in, which is read off the constructor and compared with nothing; a frame's texture, its colour on the screen and its place among the layers, the render being compared by its quad's corners alone; what the GPU makes of the quad; and that the tables the viewer ships are the disc's, which is the build's.
- `tools/tests/test_render.py` and `tools/tests/test_fallingitem.py` hold the two models to frames and records worked by hand, `by_hand` to the places it is to reach, and the two finders to a synthetic executable and overlay and their refusals. They guard the models against a slip; only the disc proves them.

## The next port

- Read the routine off its overlay or the executable: the load address falls out of the message table's pointers, a function runs to its `jr ra`, and what the decomp calls the object's functions are the slots of its table of virtual functions.
- Write the model beside `hintfly.py`: the object's fields under names of their own, a step a tick, and a `World` of whatever it shares with the game, with every table the disc holds passed in rather than read.
- Find the routines by a shape only they have (data only they index, the slot that names them, what they call and are called by) and refuse any other shape by the part that is off, so that each overlay and each release runs with no address given.
- Decide callee by callee what runs and what is answered, and run whatever rolls the dice: a call answered at its entry hides every roll beneath it, as the engine's player rolls a pitch for a sound given none. Find the globals a routine writes with `stores`.
- Compare every field after every tick under inputs that reach every branch, counting what was reached, and put the state a run cannot be relied on to reach there by hand.
- Change the model one line at a time and see the check fail on each before believing a pass, and ask of each change it passes whether a run could have reached it.
- Print the model's runs over the tables the viewer ships and hold the port's unit test to them, with a test in the builder's suite that makes the same runs and looks its numbers up in the port's test, so the two cannot part unseen.
- An object drawn as an animation needs no model of its render: `render.code` finds the routine's parts from the slot after the object's update, `render.Console` runs the disc's over an object laid out as its own constructor leaves it, with `LAYOUT` naming where each game keeps what the routine reads, `render.by_hand` stands it where placed ones do not reach, and the port's model is only of what is the object's own.
- What a port shares with the others stands apart from each of them: the interpreter, exe.py's readers of compiled code (a function's `entry` and `end`, its `calls`, the `words_loaded` by name, and `one`, which refuses a shape by the part that is off), the engine's 16.16 arithmetic in [tools/oddmap/fixed.py](../tools/oddmap/fixed.py), and the instructions a test assembles its synthetic overlay and executable from, in `tools/tests/synthetic.py`.
